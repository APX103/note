# 前言

你翻开这本书，是想让编程功力再进一步。这个选择没错——书中的实战知识注定让你受益。如果你 C 编程经验丰富，你会学到优秀设计决策的细节，以及它们各自的收益与代价；如果你刚接触 C 不久，你会得到关于设计决策的指引，并看到这些决策如何一点一点地落实到一个又一个运行示例中，搭建出更大规模的程序。

本书回答这样的问题：C 程序怎么组织、错误处理怎么应对、灵活的接口怎么设计。随着 C 编程的深入，这类问题会不断冒出来，比如：

- 手头的错误信息要不要都返回出去？

- 要不要用全局变量 `errno` 来做这件事？

- 函数该少而参数多，还是反过来？

- 灵活的接口怎么搭？

- 迭代器这种基础的东西怎么实现？

对面向对象语言来说，这些问题大多已被"四人帮"的《Design Patterns: Elements of Reusable Object-Oriented Software》（Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides 著，Prentice Hall，1997，中译《设计模式》）回答得很透彻。设计模式为程序员提供了最佳实践：对象之间如何交互、谁拥有谁、对象又如何分组。

然而对 C 这类过程式语言，这些设计模式大多没法照"四人帮"描述的方式实现——C 没有原生的面向对象机制。在 C 里模拟继承或多态是做得到的，但那未必是首选：习惯 C、不习惯 C++ 这类面向对象语言及其继承、多态概念的程序员，面对这种模拟会觉得别扭。他们更愿意坚守自己熟悉的原生 C 风格。可一旦坚守原生 C 风格，面向对象设计模式的指引就不能照单全收——至少，设计模式里呈现的思想并没有为非面向对象语言给出具体实现。

我们的处境就是：想用 C 编程，却又无法直接搬用设计模式里记载的大部分知识。本书讲的就是如何跨过这道沟壑，为 C 语言落实可以上手的设计知识。

# 为什么写这本书

让我讲讲这本书里汇集的知识为什么对我如此重要，以及这样的知识为什么难找。

中学时代，C 是我学的第一门编程语言。和每个新学 C 的人一样，我纳闷过数组下标为什么从 0 开始，也一度近乎碰运气地试验 `*` 和 `&` 该怎么摆，才终于让 C 的指针魔法转起来。

大学里我学会了 C 语法的真实运作方式，以及它如何落到硬件的比特和字节上。凭这些知识，我能写出运转良好的小程序。但我还是搞不懂：那些较长的代码为什么长那样？反正我自己是断然想不出下面这样的方案的：

```
typedef struct INTERNAL_DRIVER_STRUCT* DRIVER_HANDLE;
typedef void (*DriverSend_FP)(char byte);
typedef char (*DriverReceive_FP)();
typedef void (*DriverIOCTL_FP)(int ioctl, void* context);

struct DriverFunctions
{
  DriverSend_FP fpSend;
  DriverReceive_FP fpReceive;
  DriverIOCTL_FP fpIOCTL;
};

DRIVER_HANDLE driverCreate(void* initArg, struct DriverFunctions f);
void driverDestroy(DRIVER_HANDLE h);
void sendByte(DRIVER_HANDLE h, char byte);
char receiveByte(DRIVER_HANDLE h);
void driverIOCTL(DRIVER_HANDLE h, int ioctl, void* context);
```

看到这样的代码，会冒出一堆问题：

- `struct` 里为什么放函数指针？

- 这些函数为什么需要那个 `DRIVER_HANDLE`？

- IOCTL 是什么？为什么不用几个独立的函数？

- 为什么要显式的创建和销毁函数？

这些问题在我开始编写工业应用后集中爆发。我不断撞见这样的时刻：发现自己缺少 C 编程知识——比如决定迭代器怎么实现、函数的错误处理怎么应对。我意识到：语法我懂，可怎么用我一无所知。想做成一件事，不是做得笨手笨脚，就是干脆做不成。我缺的是"用 C 语言完成特定任务"的最佳实践，比如：

- 资源的获取和释放怎么做得轻松？

- 错误处理用 `goto` 是好主意吗？

- 接口该设计得灵活，还是等需要时再改？

- 该用 `assert` 语句，还是返回错误码？

- C 里的迭代器怎么实现？

有意思的是：经验丰富的同事们对这些问题的答案五花八门，却没人能给我指出一份文档，记载这些设计决策及其收益与代价。

于是我转向互联网，结果又一次惊讶：C 语言问世几十年了，这些问题却依然难找到像样的答案。我发现关于 C 语言基础和语法的文献浩如烟海，讲 C 进阶主题、讲"怎么写出配得上工业应用的漂亮 C 代码"的却寥寥无几。

这正是这本书的立足点。本书教你如何从编写基础 C 程序，进阶到编写考虑错误处理、对未来的需求与设计变化保持弹性的大规模 C 程序。本书借助设计模式这一概念，把设计决策连同它们的收益与代价一点一点交到你手上。这些模式被应用到一个又一个运行示例中，让你看到诸如前面那段示例代码是如何演化而来的、为什么最终长成那个样子。

书中模式适用于任何 C 编程领域。我本人来自多线程实时环境下的嵌入式编程领域，部分模式难免偏向这个领域。不过你会看到，模式的总体思想同样适用于其他 C 编程领域，甚至超出 C 编程的范围。

# 模式基础

本书的设计指引以模式的形式呈现。以模式来记载知识和最佳实践的思想，来自建筑师 Christopher Alexander 的《The Timeless Way of Building》（Oxford University Press，1979，中译《建筑模式语言》之道篇）。他用一块块久经考验的小方案，去攻克他那个领域里的巨大难题：如何设计和建造城市。应用模式的方法后来被软件开发领域采纳，模式领域的会议（如模式语言程序设计大会 PLoP）持续为模式的知识体系添砖加瓦。尤其是"四人帮"的《Design Patterns: Elements of Reusable Object-Oriented Software》（Prentice Hall，1997，中译《设计模式》），影响深远，让设计模式的概念在软件开发者中家喻户晓。

可模式到底是什么？定义很多。如果你对这个话题深感兴趣，Frank Buschmann 等人的《Pattern-Oriented Software Architecture: On Patterns and Pattern Languages》（Wiley，2007）能给你精确的描述和细节。就本书而言：模式是对一个现实问题的久经考验的解。本书的模式采用[表 P-1](#tab_pattern_sections) 所示的结构。

| 模式小节 | 说明 |
|----|----|
| 名称 | 模式的名字，应当好记。目标是让这个名字进入程序员的日常语言（正如"四人帮"模式那样——你会听到程序员说"让抽象工厂来创建对象"）。本书中模式名首字母大写。 |
| 上下文 | 上下文小节为模式布置场景，告诉你什么情况下可以应用这个模式。 |
| 问题 | 问题小节交代你要解决的难题。它以加粗的问题主句开头，再补充这个难题为什么不好解。（在别的模式格式里，这些细节放进单独的"作用力"小节。） |
| 方案 | 这一节给出攻克难题的指引。它以加粗的方案主旨开头，再展开方案的细节，并附代码示例，给出非常具体的指导。 |
| 后果 | 这一节列出应用所述方案的收益与代价。应用一个模式之前，你应当确认这些后果自己吃得消。 |
| 已知应用 | 已知应用向你证明：提议的方案是好的，在现实应用中真实有效；也给你具体的例子，帮你理解如何应用该模式。 |

表 P-1  本书模式的组成结构

以模式的形式呈现设计指引，一大好处是模式可以一个接一个地应用。面对一个巨大的设计难题，你很难找到恰好对症的那份指引文档、那个完美方案。换个思路：把你那个庞大而特定的难题，看成许多更小、更通用的问题之和，然后一个模式接一个模式地各个击破。翻翻各模式的问题描述，选一个正对你的问题、后果你又吃得消的应用即可。这些后果也许又引出新问题——没关系，再用另一个模式去解。这样，你的代码是增量设计出来的，而不是写第一行代码之前就憋出一个面面俱到的前期设计。

# 如何阅读本书

你应当已经掌握 C 编程基础：懂 C 语法、知道它怎么运作——比如，本书不会教你指针是什么、怎么用。本书交付的是进阶主题的提示与指引。

本书各章自成一体，可以任意顺序阅读，也可以只挑你感兴趣的主题。下一节有全部模式的总览，从那里可以跳到你感兴趣的模式。如果你明确知道自己在找什么，从那儿直接开始即可。

如果你不是要找某个特定模式，而是想纵览 C 的设计选项，那就通读本书[第一部分](Part_01_C模式.md)。那里每章聚焦一个主题：从错误处理、内存管理这类基础话题起步，走向接口设计、平台无关代码这类更进阶、更专门的话题。每章给出该主题相关的模式和一段运行示例，展示模式如何一步步应用。

本书[第二部分](Part_02_模式故事.md)给出两个较大的运行示例，应用了[第一部分](Part_01_C模式.md)的许多模式。在这里你可以学习如何借助模式的应用，一点一点搭建起较大的软件。

# 模式总览

表 [P-2](#tab1a) 至 [P-10](#tab1i) 给出了本书全部模式的总览。表中是模式的简写形式：先用一句话概括核心问题，接着是关键词"因此"，然后是核心方案。

| 模式名 | 摘要 |
|----|----|
| [“函数拆分”](Chapter_01_错误处理.md) | 函数身兼数职，导致难以阅读和维护。因此，把它拆开：把函数中一段看起来能独立成篇的部分拿出来，新建一个函数放进去，再调用这个新函数。 |
| [“卫语句”](Chapter_01_错误处理.md) | 函数把前置条件检查和主逻辑混在一起，难以阅读和维护。因此，先梳理出必须满足的前置条件，一旦条件不满足就立即从函数返回。 |
| [“武士道原则”](Chapter_01_错误处理.md) | 返回错误信息时，你默认调用方会检查这些信息；可调用方完全可能省略检查，错误就此被埋没。因此，函数要么凯旋而归，要么根本不返回；如果遇到你明知无法处理的错误，就直接终止程序。 |
| [“goto 错误处理”](Chapter_01_错误处理.md) | 在函数内部多处获取和清理多个资源，代码会变得难以阅读和维护。因此，把所有资源清理和错误处理集中到函数末尾；一旦某个资源获取失败，就用 `goto` 语句跳转到清理代码。 |
| [“清理记录”](Chapter_01_错误处理.md) | 当代码要获取和清理多个资源、尤其当这些资源彼此依赖时，很难让这段代码易读易维护。因此，连续调用资源获取函数直到失败为止，并记录哪些资源需要清理；再根据这些记录决定调用哪些清理函数。 |
| [“基于对象的错误处理”](Chapter_01_错误处理.md) | 资源获取、资源清理和资源使用挤在一个函数里，会让代码难以实现、阅读、维护和测试。因此，把初始化和清理拆到独立的函数中——类似面向对象编程里构造函数与析构函数的概念。 |

表 P-2  错误处理模式

| 模式名 | 摘要 |
|----|----|
| [“返回状态码”](Chapter_02_返回错误信息.md) | 你需要一种向调用方返回状态信息的机制，让调用方能够据此做出反应；机制要简单易用，调用方还要能清楚区分各种可能出现的错误情形。因此，用函数的返回值承载状态信息，返回一个代表特定状态的值——被调方和调用方对这个值的含义必须有共识。 |
| [“返回相关错误”](Chapter_02_返回错误信息.md) | 一方面，调用方应能对错误做出反应；另一方面，返回的错误信息越多，你和你调用方的代码要处理的错误就越多，代码就越长——代码一长就难读、难维护，还容易引入新 bug。因此，只把对调用方有用的错误信息返回给它：调用方能据之采取行动的信息，才是有用的信息。 |
| [“特殊返回值”](Chapter_02_返回错误信息.md) | 你想返回错误信息，但显式返回状态码并不可取——那意味着函数的返回值没法再返回别的数据，那些数据得靠输出参数传出，函数调用也随之变麻烦。因此，用函数返回值承载函数计算出的数据，另外保留一个或多个特殊值专用于表示出错。 |
| [“记录错误日志”](Chapter_02_返回错误信息.md) | 你希望出错时能轻松查明原因，但又不想因此把错误处理代码搞复杂。因此，把两类错误信息分走不同通道：对调用代码有用的错误信息正常返回；对开发者有用的错误信息（如调试细节）写进日志文件，不返回给调用方。 |

表 P-3  返回错误信息模式

| 模式名 | 摘要 |
|----|----|
| [“栈优先”](Chapter_03_内存管理.md) | 为变量选择存储类别和内存区域（栈、堆……）是每个程序员都要反复做的决定。如果每个变量都得把所有备选方案的利弊细细掂量一遍，迟早会把人耗干。因此，默认把变量放栈上，坐享栈变量自动清理的好处。 |
| [“永久内存”](Chapter_03_内存管理.md) | 持有大量数据并在函数调用之间传递它并不容易：你得保证数据的内存足够大、生命周期跨越所有函数调用。因此，把数据放进程序整个生命周期内都可用的内存里。 |
| [“惰性清理”](Chapter_03_内存管理.md) | 需要大块内存、或事先不知道所需大小时，动态内存不可或缺。但动态内存的清理是个苦差事，也是许多编程错误的源头。因此，分配动态内存，然后把释放工作留给操作系统，等程序结束时统一收拾。 |
| [“专属所有权”](Chapter_03_内存管理.md) | 使用动态内存的强大能力，伴随着把它妥善清理的重大责任。在大型程序中，要确保所有动态内存都被妥善清理并不容易。因此，就在实现内存分配的那一刻，明确并记录：这块内存将在哪里清理、由谁清理。 |
| [“分配包装器”](Chapter_03_内存管理.md) | 每次动态内存分配都可能失败，所以你应当在代码中检查分配结果并做出反应。但这样的检查点遍布代码，不胜其烦。因此，把分配和释放调用包装起来，在包装函数里统一实现错误处理或额外的内存管理组织。 |
| [“指针检查”](Chapter_03_内存管理.md) | 访问非法指针的编程错误会导致程序行为失控，且极难调试。而 C 代码到处都是指针，这类错误几乎难以避免。因此，显式地把未初始化或已释放的指针置为无效，并在访问指针前始终检查其有效性。 |
| [“内存池”](Chapter_03_内存管理.md) | 频繁从堆上分配、释放对象会导致内存碎片化。因此，在程序整个生命周期内持有一大块内存；运行时从这个内存池中取固定大小的块，而不是直接从堆上分配新内存。 |

| [“返回值”](Chapter_04_从C函数返回数据.md) | 你要拆分的函数各部分并非彼此独立。过程式编程的常态是：一部分产出结果，另一部分接着用。想拆开的函数各部分需要共享一些数据。因此，直接使用 C 中专为获取函数调用结果而生的那个机制——返回值。C 的返回值机制会复制函数结果，把这份副本交给调用方。 |

| [“聚合实例”](Chapter_04_从C函数返回数据.md) | C 的函数调用只支持返回单一类型，要返回多条信息就麻烦了。因此，把彼此相关的数据统统放进一个新定义的类型。定义这个聚合实例来承载要共享的全部相关数据，并把它定义在组件接口里，让调用方直接访问实例中的全部数据。 |

| [“调用方拥有的缓冲区”](Chapter_04_从C函数返回数据.md) | 你想把大小已知、并非不可变（运行期会变）的复杂数据或大数据提供给调用方。因此，要求调用方向返回这些数据的函数提供缓冲区及其大小；函数实现中，缓冲区够大就把所需数据拷贝进去。 |
| [“被调方分配”](Chapter_04_从C函数返回数据.md) | 你想把大小未知、并非不可变（运行期会变）的复杂数据或大数据提供给调用方。因此，在提供这些数据的函数内部分配所需大小的缓冲区，把数据拷贝进去，返回指向该缓冲区的指针。 |

| [“调用方拥有的实例”](Chapter_05_数据生命周期与所有权.md) | 你想让多个调用方或线程访问一组彼此依赖的函数，而调用方与这些函数的交互会积累状态信息。因此，要求调用方把一个存储资源和状态信息的实例传给你的函数。为创建和销毁这些实例提供显式函数，让调用方决定它们的生命周期。 |
| [“共享实例”](Chapter_05_数据生命周期与所有权.md) | 你想让多个调用方或线程访问一组彼此依赖的函数，调用方与这些函数的交互会积累状态信息，且各调用方想共享这些信息。因此，要求调用方把一个存储资源和状态信息的实例传给你的函数。让多个调用方使用同一个实例，并把实例的所有权留在你的软件模块手里。 |

表 P-6  数据生命周期与所有权模式

| 模式名 | 摘要 |
|----|----|
| [“头文件模式”](Chapter_06_灵活的API.md) | 你想让自己实现的功能能被其他实现文件的代码访问，又想对调用方隐藏实现细节。因此，把想提供给用户的每个功能的函数声明放进 API；把所有内部函数、内部数据和函数定义（实现）藏进实现文件，且不把实现文件交给用户。 |
| [“句柄”](Chapter_06_灵活的API.md) | 你的函数实现必须共享状态信息或操作共享资源，但又不想让调用方看到、更不想让它访问这些状态信息和共享资源。因此，提供一个创建上下文的函数，向调用方返回指向内部数据的抽象指针；要求调用方把这个指针传给你的所有函数，函数便可使用内部数据来存储状态信息和资源。 |
| [“动态接口”](Chapter_06_灵活的API.md) | 应当可以调用行为略有差异的实现，又不该复制任何代码——连控制逻辑实现和接口声明也不复制。因此，在 API 中为这些有差异的功能定义一个公共接口，要求调用方为该功能提供一个回调函数，你在函数实现中调用它。 |
| [“函数控制”](Chapter_06_灵活的API.md) | 你想调用行为略有差异的实现，又不想复制任何代码——连控制逻辑实现和接口声明也不复制。因此，给函数加一个传递函数调用元信息的参数，用它指定实际要执行的功能。 |

表 P-7  灵活 API 模式

| 模式名 | 摘要 |
|----|----|
| [“下标访问”](Chapter_07_灵活的迭代器接口.md) | 你想让用户便捷地遍历你数据结构中的元素，且数据结构内部的变化不牵连用户代码。因此，提供一个接收下标、寻址底层数据结构中元素并返回其内容的函数；用户在循环里调用它即可遍历全部元素。 |
| [“游标迭代器”](Chapter_07_灵活的迭代器接口.md) | 你想向用户提供一个迭代接口：元素在迭代期间变化也稳如泰山，底层数据结构日后更换也不要求用户改一行代码。因此，创建一个指向底层数据结构中某元素的迭代器实例；迭代函数以该实例为参数，取出迭代器当前指向的元素，并把实例改为指向下一个元素。用户循环调用这个函数，一次取一个元素。 |
| [“回调迭代器”](Chapter_07_灵活的迭代器接口.md) | 你想提供一个稳健的迭代接口：用户不必在代码里写循环来遍历全部元素，底层数据结构日后更换也不要求用户改一行代码。因此，在实现内部用你既有的数据结构专属操作遍历所有元素，并在遍历中对每个元素调用用户提供的外部函数。该函数以元素内容为参数，对元素执行操作。用户只需调用一个函数触发迭代，整个遍历都发生在你的实现内部。 |

|----|----|
| [“包含保护”](Chapter_08_模块化程序中的文件组织.md) | 头文件很容易被包含多次；同一头文件包含多次，若其中有类型或某些宏，编译时就会因重复定义而报错。因此，保护头文件内容不被重复包含，让使用头文件的开发者不必操心"它是不是被包含了多次"。用一个互锁的 `#ifdef` 语句或 `#pragma once` 语句实现。 |
| [“软件模块目录”](Chapter_08_模块化程序中的文件组织.md) | 代码拆成多个文件后，代码库里的文件越来越多。全部挤在一个目录里，文件总览就难了——大代码库尤其如此。因此，把属于紧耦合功能的头文件和实现文件放进同一个目录，并以头文件所提供的功能为目录命名。 |
| [“全局头文件目录”](Chapter_08_模块化程序中的文件组织.md) | 要包含其他软件模块的文件，就得用 *../othersoftwaremodule/file.h* 这样的相对路径，还得知道对方头文件的确切位置。因此，在代码库里设一个包含所有软件模块 API 的全局目录，并把它加进工具链的全局包含路径。 |
| [“自包含组件”](Chapter_08_模块化程序中的文件组织.md) | 从目录结构看不出代码里的依赖：任何软件模块都能随手包含任何其他软件模块的头文件，因此无法通过编译器检查代码依赖。因此，识别出功能相近、应一起部署的软件模块，把它们放进公共目录，并为调用方相关的头文件设一个专门的子目录。 |
| [“API 拷贝”](Chapter_08_模块化程序中的文件组织.md) | 你想让代码库的各部分独立开发、独立版本化、独立部署。为此，各代码块之间需要定义清晰的接口，并能拆分进不同的仓库。因此，要用另一个组件的功能时，拷贝它的 API：单独构建那个组件，把构建产物和它的公共头文件拷过来，放进你组件内的一个目录，并把这个目录配置为全局包含路径。 |

表 P-9  模块化程序中组织文件的模式

| 模式名 | 摘要 |
|----|----|
| [“避免变体”](Chapter_09_逃离ifdef地狱.md) | 每个平台用一套不同的函数，代码就越写越难、越读越难。程序员得先理解、正确使用并测试这多套函数，才能在各平台上实现同一个功能。因此，使用所有平台都有的标准化函数；没有标准化函数，就考虑别实现这个功能。 |
| [“隔离原语”](Chapter_09_逃离ifdef地狱.md) | 用 `#ifdef` 组织代码变体会让代码没法读：程序流程为多个平台实现了多遍，极难跟进。因此，隔离你的代码变体——在实现文件中，把处理变体的代码放进独立的函数，由主程序逻辑调用它们；主程序逻辑里就只剩平台无关代码。 |
| [“原子原语”](Chapter_09_逃离ifdef地狱.md) | 那个装着变体、被主程序调用的函数依然难懂——复杂的 `#ifdef` 代码只是从主程序挪进了它。因此，让原语原子化：每个函数只处理恰好一种变体。若要处理多种变体（比如操作系统变体加硬件变体），就为每种各写一个函数。 |
| [“抽象层”](Chapter_09_逃离ifdef地狱.md) | 你想在代码库的多处使用处理平台变体的功能，又不想复制这段功能的代码。因此，为每个需要平台专属代码的功能提供一个 API：头文件里只定义平台无关的函数，平台专属的 `#ifdef` 代码全部放进实现文件。函数的调用方只包含你的头文件，不必包含任何平台专属文件。 |
| [“拆分变体实现”](Chapter_09_逃离ifdef地狱.md) | 平台专属的实现里仍用 `#ifdef` 区分代码变体，看不清、也选不准哪部分代码该为哪个平台构建。因此，把每种变体实现放进单独的实现文件，按文件为单位选择为哪个平台编译什么。 |
