Agent-Native SDLC 研究笔记

整理自 OpenAI、Anthropic 官方博客及第三方深度访谈。
聚焦一个问题：当 AI Agent 一天产出上万次变更时，代码质量、合并、冲突、一致性如何保障？

  • OpenAI — Harness engineering: leveraging Codex in an agent-first world（官方，2026-02）
  • Anthropic — Redesigning source control at Anthropic（官方，2026-10）
  • Anthropic — Agentic coding is straining CI（官方）

  • Pragmatic Engineer — How Codex is built（访谈 Tibo Sottiaux）

二、一些核心数字

这些数字部分是官方披露，部分是团队访谈自述，引用时需区分。

  • Anthropic monorepo：2026 年 5 月日均 2,500 次合并，9 月超过 30,000 次/天。
  • Scion：7 人团队 5 个月自研并迁移完成，同时日均合并量增长 10 倍。
  • Claude Code 团队：十几人，~60–100 内部发布/天，每个工程师 ~5 发布/天，1 外部发布/天。
  • Codex 团队：内部一天 3–4 版，典型工程师同时跑 4–8 个并行 agent。
  • AI 生成代码占比：Codex 和 Claude Code 都声称约 90% 代码由 AI 生成（团队估算，非第三方审计）。
关键结论：速度不是来自人写代码更快，而是来自人类设计环境、定义验证规则、管理 agent 舰队；代码本身大量由 agent 生成。

三、代码质量怎么做

3.1 不是审每一行，而是建分层验证

Anthropic 把它叫做 Swiss Cheese Model，多层叠加，每层抓不同类别的错误：

  1. AI 自验证：在 PR 出现前，agent 先跑测试、build、截图对比，给出可运行的证据。
  2. CI 自动 evals：把配置变更（CLAUDE.md、skills、hooks）当作代码一样做回归测试。
  3. 自动 security review：每个 diff 过安全扫描。
  4. 选择性人工 review：只关注架构决策和 novel risk，常规改动由 agent 处理。
  5. 活的 institutional memory：把 AI 常犯的错误、过去事故编码成 eval 和规则。

3.2 用机械规则（invariants）代替人工品味

OpenAI 在仓库里直接编码 golden principles：

  • 偏好 shared utility packages，不鼓励手搓 helper。
  • 不 YOLO-style probe 数据，必须在边界 parse/validate，或用 typed SDK。
  • 严格架构分层：Types → Config → Repo → Service → Runtime → UI，依赖方向机械 enforced。
  • 自定义 linter，错误信息里直接注入修复指导，让 agent 自纠正。

3.3 把事故变成 eval

Claude Code 团队的做法：

  • 每次生产事故的 PR 被收集起来，由熟悉代码的人确认 bug 和位置。
  • reviewer agent 每天跑这个 eval set。
  • reviewer 的 prompt、工具、模型变更后，要重新打分。

3.4 噪声控制

Agent reviewer 如果太吵，会导致 agent author 无限修复。Claude Code 的做法：

  • 多个 agent 同时找 bug，然后投票，只有足够多 agent 同意才报。
  • 只关于 style、diagnostics、cleanup 的 finding 直接丢掉。
  • inline comment 按 severity 排序。
对普通团队的启示：不要指望人工 review 每一行 agent 代码。要把团队品味变成可执行、可自动修复的规则。

四、合并与冲突怎么解决

4.1 Anthropic 的解法：放弃全局锁，靠事后修复

当一天 30,000 次合并时，传统 merge queue 全局锁不可行：

  • Scion 架构：changeset 服务器端创建，无需 push；ref 移动是独立的 compare-and-swap。
  • 文本冲突不允许：Scion 会阻止纯文本层面的冲突。
  • 语义冲突承认不可避免：比如 A 改函数逻辑，B 同时新增调用点。
  • 策略：放弃"测试通过才能合并"的全局锁，改为 post-merge + pre-deploy 自动化测试。
  • 修复机制：Claude 自动修复冲突，配合自动 bisect 和 revert pipeline。

4.2 代码 review 工具 Antique 的语义审批

  • 区分 comment-only change 和敏感逻辑变更。
  • 对敏感路径要求人工审 intent，不读每一行。
  • 人类角色变成"告诉 Claude no"，阻止 agent 为迎合局部模式破坏系统约束。

4.3 OpenAI 的合并哲学

OpenAI 的实验仓库采用：

  • 最小化阻塞合并门：PR 短生命周期，测试 flake 重跑而不是无限阻塞。
  • Agent-to-agent review：Codex 自己 review 自己，人类只在需要判断时介入。
  • 自动化修复循环：agent 拉取 review 反馈、回复、push 更新、merge。
关键认知：当 agent 吞吐量远超人类注意力时，等待比修复更贵。他们的选择是快速合并、快速检测、快速回滚。

五、不同 Agent / Prompt 产出不一样怎么办

这是你最关心的问题。他们的答案不是"统一 prompt"，而是用强制约束把结果收敛。

5.1 架构约束优先于 prompt

  • 固定模块分层和依赖方向，用 custom linter / 结构测试机械执行。
  • 跨领域 concern（auth、telemetry、feature flags）只能通过单一 Provider 接口进入。
  • agent 不需要"记住"规则，规则由工具强制执行。

5.2 共享抽象抑制发散

  • 优先 shared utility packages，把不变量集中。
  • 用 typed SDK / frozen dataclass / Pydantic extra="forbid" 让 agent 无法乱猜形状。
  • parse at boundary，不要 validate later。

5.3 定期垃圾回收（entropy control）

OpenAI 早期每周五 20% 时间清理 "AI slop"，后来改成：

  • 把 golden principles 编码进仓库。
  • 后台 agent 定期扫描偏差，更新质量评分。
  • 自动开 targeted refactoring PR，大部分 1 分钟内可 review 并 auto-merge。

5.4 把 drift 变成可测量的问题

Claude Code 团队：

  • 测量 revert rate 和 incident rate，作为速度 guardrail。
  • 从 6 月到 9 月，合并 PR 数翻倍，revert 比例下降 40%+。
  • 目标是最小化人类 review 时间，同时不提高 revert/incident。

5.5 人类工程师的新角色

  • 不是写代码，而是设计环境、定义成功标准、验证结果。
  • 看到 agent 挣扎时，问："缺什么能力、工具、guardrail、文档？"
  • 让 agent 自己写修复，而不是人类动手修。

六、对普通团队的启示

50 人团队不要照搬 Anthropic 的 Scion 或 OpenAI 的"无手写代码"。但可以 borrow 思想：

  1. 先把发布从事件变成按钮：trunk-based + feature flags，让 main 始终可发布。
  2. 把规范变成工具：custom linter、dependency rules、architectural tests，而不是靠人记。
  3. 用 agent 做第一层 review：在人工看之前，先让 Claude/Codex 过一遍，抓常规问题。
  4. 事故必须变成回归：每个线上问题写入 eval 或测试，防止复发。
  5. 测量正确指标：不要只看速度，要看 revert rate、incident rate、human review time。
  6. 减少阻塞点：如果 merge queue 是瓶颈，考虑更小的 batch、path-based CI、或把部分测试移到 post-merge。
一句话：敏捷没有死，但它从"人的流程"变成了"agent 的流程"。人类的职责从"写代码"转向"设计约束和验证系统"。
