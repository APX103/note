JSON-RPC 之上的 Agent 会话标准

从“有固定 Schema 的 JSON-RPC”出发，理解 ACP 如何让编辑器、脚本和其他程序以统一方式驱动 Coding Agent。

一句话结论

ACP 是一套有固定、版本化 Schema 的 JSON-RPC 协议。JSON-RPC 规定消息如何包装，ACP 规定客户端与 Agent 可以调用哪些方法、交换哪些数据，以及这些消息按什么生命周期出现。

它解决的是“客户端怎么驱动 Agent”，不是“Agent 内部怎么思考”，也不是“Agent 怎么调用工具”。

1. ACP 是什么？

ACP（Agent Client Protocol）标准化了代码编辑器、IDE 等客户端与 Coding Agent 之间的通信。这里的 Agent 是使用生成式 AI、能够自主完成编程任务的程序；Client 通常负责用户界面、工作区、权限确认和资源访问。

没有共同协议时，每个编辑器都要为每个 Agent 编写专用适配。ACP 把中间接口统一后，支持 ACP 的客户端可以接入不同的 ACP Agent，Agent 也不必分别实现每家编辑器的私有 API。

没有 ACP：编辑器 A ──专用适配── Agent X
          编辑器 A ──专用适配── Agent Y
          编辑器 B ──专用适配── Agent X

有了 ACP：任何兼容 Client ──标准协议── 任何兼容 Agent

官方用 LSP（Language Server Protocol）作类比：LSP 统一编辑器与语言服务器的集成，ACP 则统一客户端与 Coding Agent 的集成。

ACP 不是 Agent 框架。它不规定使用哪家模型、如何规划任务、系统提示词怎么写、上下文如何压缩，也不要求 Agent 内部采用某种架构。

2. 三层技术结构

理解 ACP 最有效的方式，是把“传输”“消息信封”“业务语义”分开。

ACP Schema

定义方法名、参数、结果、通知内容、会话生命周期与错误语义。

JSON-RPC 2.0

定义 Request、Response、Notification 如何包装，如何用 id 对应请求与响应。

Transport

负责字节如何送达。本地 Agent 常见方式是编辑器启动子进程，通过 stdio 交换消息。

因此，“ACP 使用 stdio”和“ACP 使用 JSON-RPC”并不矛盾：stdio 是传输通道，JSON-RPC 是消息格式，ACP Schema 是消息语义。

JSON-RPC 提供信封

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "session/new",
  "params": { "...": "由 ACP 定义" }
}
  • Request：带 id，期待对端返回 result 或 error。
  • Notification：不带 id，单向发送，没有响应，例如进度更新。

ACP 提供固定词汇

ACP 把 method 固定为 initialize、session/new、session/prompt 等具体方法，并用 Schema 定义每种消息的字段。它不是“随便定义几个方法、碰巧用了 JSON-RPC”的私有接口。

3. 两个角色，双向调用

角色典型实现主要职责
Client编辑器、IDE、测试器、脚本、另一个 Agent发起会话和任务，展示更新，处理权限与用户交互，提供受控资源
AgentCoding Agent 进程执行任务，报告消息和工具进度，在需要时请求权限或客户端能力

最容易忽略的一点是：Client 与 Agent 都可以向对方发送 Request。

  • Client → Agent：初始化、创建会话、发送提示词、取消任务。
  • Agent → Client：请求权限；在客户端声明支持时，还可以请求文件系统或终端操作。
  • Agent → Client：通过 Notification 持续发送助手消息、工具活动等更新。

所以 ACP 不是简单的“客户端调用一个远程函数”，而是一个带状态、可持续交换事件的双向会话协议。

4. 一次完整会话

下面以当前稳定版 ACP v1 为主线。Schema 回答“每条消息长什么样”，生命周期回答“它们在什么时机出现”。

Client→initialize协商协议版本、能力和认证方式
Client→session/new创建会话，提供工作目录等配置
Client→session/prompt发送一轮用户任务
Agent→session/update持续通知助手消息与工具进度
Agent→request_permission需要时请求客户端作出权限决定
Client→permission result允许或拒绝，Agent 再继续执行
Agent→prompt result本轮结束，返回 stopReason

在 v1 中，session/prompt 的最终响应在本轮结束时返回。客户端可以在此期间发送 session/cancel 请求中断；恢复已有会话则使用 session/load，前提是对端声明支持。

版本提醒：官网同时提供 v2 文档，但官方仓库目前明确标注稳定协议版本为 1。学习时应先锁定 v1，避免把 v2 的提示词结算方式与 v1 混用。

5. 消息实际长什么样？

以下是帮助理解的简化示例，省略了部分字段；实现时应以对应版本的官方 Schema 为准。

创建会话：Request 与 Response

Client → Agent
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "session/new",
  "params": {
    "cwd": "/workspace/demo",
    "mcpServers": []
  }
}

Agent → Client
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "sessionId": "sess_01"
  }
}

相同的 id 把响应与请求对应起来，sessionId 则标识后续交互所属的会话。

发送任务：内容块数组

Client → Agent
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "session/prompt",
  "params": {
    "sessionId": "sess_01",
    "prompt": [
      { "type": "text", "text": "帮我修复这个测试" }
    ]
  }
}

提示词不是只能装一个字符串。ACP 使用结构化内容块表达文本、图片、资源等内容。

报告进度：Notification

Agent → Client
{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess_01",
    "update": {
      "sessionUpdate": "agent_message_chunk",
      "content": { "type": "text", "text": "我先定位失败原因。" }
    }
  }
}

这条消息没有 id，因为客户端不需要回复。持续发送这类通知，客户端就能展示流式进度。

6. 固定 Schema 不等于完全僵硬

ACP 通过三组机制兼顾稳定性与演进：

  • 协议版本：initialize 协商 protocolVersion，决定线上消息使用哪个主版本的语义。
  • 能力协商：双方通过 capabilities 声明可选能力。支持 ACP 不代表支持所有 ACP 功能，客户端不能假定对端一定支持文件、终端或会话恢复。
  • 扩展机制：_meta 可携带扩展数据，_ 前缀可用于自定义方法，自定义能力也可以在初始化时公布。

因此，接入方既要看版本，也要看能力。只确认“双方都写了 ACP”还不足以保证某项具体功能可用。

7. ACP、MCP 与 A2A 的区别

协议连接对象核心问题典型动作
ACPClient ↔ Coding Agent怎样驱动 Agent 并呈现其工作过程会话、提示词、进度、权限、取消
MCPAI 应用 ↔ 工具 / 数据源怎样让模型或 Agent 发现和使用外部能力工具调用、资源读取、提示词模板
A2AAgent ↔ Agent不同 Agent 怎样发现、通信和协作Agent 发现、任务委派、消息与产物
用户
  ↓
编辑器 / 自动化程序
  ↓ ACP：驱动 Agent、接收进度、处理权限
Coding Agent
  ↓ MCP：发现和使用工具与数据
文件系统 / 浏览器 / 数据库

ACP 管“怎么驱动 Agent”，MCP 管“Agent 怎么驱动工具”，A2A 管“Agent 怎么与另一个 Agent 协作”。三者可以同时出现在一个系统中，并非互相替代。

8. 标准协议与具体实现要分开

“标准 ACP 支持某能力”与“某个 Agent 实现了该能力”是两个问题。以 DeepSeek Harness 为例，其 dsh-acp 将 DSH Agent 暴露为 ACP 服务，支持持久会话、文本与图片提示、模型选择、MCP 挂载、语义更新、权限和取消，但明确定位为仅自动化接口。

这意味着它选择了标准协议中的一个子集，刻意不提供 DSH 专属展示数据和交互式 UI 功能。另一个包 dsh-subagent-acp 则站在 Client 一侧，启动并驱动独立进程中的 ACP Agent。

DSH 包ACP 角色用途
dsh-acpAgent 端让外部程序通过 ACP 驱动 DSH Agent
dsh-subagent-acpClient 端让 DSH 驱动进程隔离的 ACP 子 Agent

读具体实现时，始终区分三件事：协议要求什么、对端声明了什么、当前产品选择暴露什么。

9. 最短学习路径

1

先掌握 JSON-RPC 的三个概念

弄清 Request、Response、Notification，以及 id、method、params、result、error。

2

通读 ACP v1 Overview

先画出版本协商、会话、提示词、更新、权限、取消和结束原因的主流程，不要从完整 Schema 第一页开始背。

3

把 Schema 当字典查

优先查 initialize、session/new、session/prompt、session/update、权限与取消相关方法。

4

写一个最小 Echo Agent

使用官方 SDK 完成初始化、创建会话、接收提示词、发送两条更新、返回 end_turn；之后再加入权限和取消。

5

最后读生产实现

观察真实项目如何进行能力协商、内容转换、并发控制、取消、持久化和资源清理，并运行兼容性测试工具。

记住这三句话

  • 传输、JSON-RPC、ACP Schema 是三个层次。
  • Schema 定义消息结构，生命周期定义消息顺序。
  • ACP 是双向会话协议，能力支持以版本协商和 capabilities 为准。
