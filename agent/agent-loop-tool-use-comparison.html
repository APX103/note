01概念框架：Agent Loop、Tool Use 与 ACI

1.1 什么是 Agent Loop —— 三个权威定义说的是同一件事

  • Anthropic《Building Effective Agents》：Agent = "LLMs using tools based on environmental feedback in a loop"——LLM 基于环境反馈在循环中使用工具，自主掌控控制流；与之相对的 workflow 是"LLM 通过预定义代码路径编排"。谁决定下一步，是二者的分界线。
  • Amp（Thorsten Ball）《How to Build an Agent》：Agent = "an LLM, a loop, and enough tokens"。工具调用本质是一个"眨眼协议"（blink protocol）：告诉模型"想做 X 就按这个格式回复"，执行方解析、执行、把结果发回去。
  • Braintrust：模型所见内容里工具定义占大头（system prompt ~70% + 工具定义 ~11%），工具输出设计决定 Agent 上限。

标准循环的骨架，各家实现全部是这个形状：

messages = [system_prompt, tools, user_input]
while True:
    response = LLM(messages)                # 流式返回 content blocks
    if response 没有 tool_use:
        break                            # end_turn，控制权交还用户
    for tool_call in response.tool_uses:  # 只读工具并行，写工具串行
        result = execute(tool_call)         # 过权限闸门 / 沙箱
        messages.append(tool_result)        # append-only，保 KV-cache
    # 自动 compact 检查：接近窗口上限则摘要化

术语对照（各家叫法不同，横向对比时容易踩坑）：
Step / Iteration = 一次"模型请求 + 它触发的工具执行"（OpenCode 的 AI SDK step、dsh 的 step）；Turn = 从用户输入到模型给出无工具调用的最终回复（Codex 的 turn）；Session / Thread / Rollout = 跨 turn 的会话持久化单元（Codex 的 Thread + rollout JSONL、Claude Code 的 session JSONL、dsh 的 session log）。

三个容易被忽略的工程事实：① 并行工具调用已是标配——Claude Code 里只读工具（Read/Glob/Grep/带 readOnlyHint 的 MCP 工具）并发执行，写工具（Edit/Write/Bash）串行；② 工具定义参与 prompt cache 前缀，迭代中途增删工具会炸缓存（Manus 为此用"logits mask 屏蔽"而非"从上下文删除"）；③ 工具描述本身就是提示工程——Claude Code 的 Bash 工具描述里内嵌了完整的 git commit 工作流，Read 工具描述要求模型只读需要的部分。

1.3 ACI：Agent-Computer Interface（本调研最重要的概念）

SWE-agent（Princeton，NeurIPS 2024）的核心论点：决定 Agent 上限的往往不是模型，而是"Agent-计算机接口"的设计。他们不微调模型，只为 GPT-4 设计了一小组带 guardrail 的工具（search / lookup / 受限 100 行窗口的 open / 自带语法 lint 的 edit），就在 SWE-bench 上大幅超越裸 shell 方案——edit 命令改坏语法直接拒绝提交，这就是防呆设计（poka-yoke）。

Anthropic在《Building Effective Agents》里引用了同一思想：像投入 HCI 一样投入 ACI——工具命名与描述按"给初级工程师写文档"的标准写、提供示例与边界情况、在 workbench 里大量测试模型的误用并迭代。

02Anthropic Claude Code —— "强 harness + 精细打磨"的标杆

闭源内核Agent SDK 开放丰富内置工具终端 CLI + IDE 扩展；内核以 Claude Agent SDK 形式开放，循环结构完全暴露。

Loop（来源：官方 Agent SDK 文档）

  1. 请求 = 用户输入 + system prompt + 工具定义 + 对话历史；
  2. 模型返回若干 content block（文本 / tool_use），SDK 逐 block yield；
  3. SDK 执行工具（hooks 可拦截/短路），每个工具结果作为 UserMessage 回填，不需要把控制权还给你的代码；
  4. 重复 2–3 直到出现无工具调用的回复；最后给 ResultMessage（含成本、token、session id）。
  • 终止条件：end_turn（自然结束）、max_turns、max_budget_usd（预算含子代理开销）、refusal。
  • 社区逆向发现其 StreamingToolExecutor 在模型还在流式输出的同时就开始执行工具——延迟优化的细节。

工具系统（约 17+ 内置，五大类）

类别工具设计要点
只读Read / Glob / Grep / WebFetch / WebSearch / TodoWrite / KillShell / BashOutput 等只读工具可并行；Read 默认 2000 行、超长行截断；Grep 基于 ripgrep、三种输出模式；WebFetch 把 HTML 转 markdown 交给小模型提取（15 分钟缓存）；禁止模型在 Bash 里用 grep/cat/ls/find（专用工具省上下文）
编辑Edit / Write / NotebookEditEdit 必须先 Read（保证模型见过最新内容）；old_string 不唯一则失败；支持 replace_all
执行Bash持久 shell 会话；默认 2 分钟超时；输出 30000 字符截断；支持后台运行（run_in_background + BashOutput 轮询）；工具描述内嵌 git commit / gh PR 完整工作流
编排Task / AskUserQuestion / ExitPlanModeTask 每次调用无状态，子代理只见 prompt，只回传最终报告
规划TodoWrite三态 todo，同一时刻只允许一个 in_progress；3+ 步任务强制使用

上下文管理

  • 组装顺序：system prompt → CLAUDE.md（分层：企业/项目/用户）→ 工具定义（MCP 工具延迟加载，先只给工具名，靠 tool search 按需展开）→ 历史 → Skills 描述（仅摘要，调用才加载全文——渐进式披露）。
  • 稳定前缀走 prompt cache；auto-compact 接近上限自动摘要（逆向显示其压缩 prompt 要求产出九段结构化摘要：Primary Request / Key Technical Concepts / Files and Code / Errors and fixes / Pending Tasks / Current Work / Next Step 等）。
  • 子代理是最重要的上下文隔离手段：探索性搜索在子代理（如 Explore 类型，用更便宜的 Haiku）里烧掉几万 token，主代理只收 1–2k 浓缩结论。
  • 会话为明文 JSONL，支持 resume / fork；编辑前自动 checkpoint（文件快照，独立于 git）；跨会话记忆 CLAUDE.md + MEMORY.md（前 200 行注入）。

权限模型与系统提示词

  • 四种模式循环切换：Auto（分类器后台审查拦截高风险）/ Manual（全部确认）/ Accept edits / Plan（只读探索）；组织→项目→用户三级 settings 的 allowlist / denylist；hooks（PreToolUse / PostToolUse / Stop）可在应用进程编程化拦截，不占模型上下文。
  • 系统提示词风格（逆向，多家交叉验证）：极简 tone（<4 行回答、无 preamble）、proactiveness 拨盘（"不惊吓用户"）、跟随代码库惯例、"除非要求否则不写注释"、批量并行调用工具、引用代码用 file_path:line。

来源：Agent SDK 文档 · How Claude Code works · weaxsey 逆向分析 · Victor Dibia

03OpenAI Codex CLI —— "协议化 + OS 沙箱"的工程派

开源 Apache-2.0RustOS 级沙箱同一 Rust 内核（codex-rs，~54.9 万行）驱动 CLI / IDE / 桌面 / Codex Web（云端容器）。

Loop（来源：官方《Unrolling the Codex agent loop》）

  • Turn = 从用户输入到 agent 最终回复；turn 内部是"模型推理 → function call → 结果追加 → 再推理"的循环。
  • 调 Responses API；刻意不用 previous_response_id，每轮重发完整历史（服务端零状态，支持 ZDR 零数据保留）——传输量 O(n²)，但靠 prompt caching 摊平。
  • 输入组装（角色优先级 system > developer > user > assistant）：instructions（config.toml 或模型自带 prompt 文件，打包进 CLI）→ tools → input：① developer 角色的 <permissions instructions> → ② 个人配置 → ③ AGENTS.md 链（git root 到 cwd 逐级聚合，上限 32 KiB）→ ④ <environment_context> → ⑤ 用户消息。
  • 缓存纪律：新 prompt 必须是旧 prompt 的精确前缀；配置变更（sandbox/审批模式/cwd）不修改历史而是追加新消息——很值得抄的细节。
  • SSE 流式；reasoning 项带 encrypted_content，ZDR 客户端也能复用前轮推理；超过 auto_compact_limit 自动调 /responses/compact，返回含加密压缩项替换原 input。

进程架构：App Server 协议

JSON-RPC（JSONL over stdio）双向协议；三个原语 Item（started/delta/completed 生命周期）/ Turn / Thread（可 resume/fork/archive）。官方明确放弃用 MCP 作为客户端协议——MCP 语义表达不了 diff、流式进度这类富会话状态；MCP 管工具接入，App Server 管 agent 生命周期。

工具与沙箱

  • 工具精简哲学：shell、apply_patch（自定义补丁格式：*** Begin Patch / *** Update File: path / 上下文行无前缀 / - 删 / + 增，支持 Add/Move/Delete File；文件编辑的唯一入口）、update_plan（内置计划工具）、view_image、web_search（server-side tool）、request_user_input、MCP 工具。
  • OS 级沙箱：macOS 用 Seatbelt（sandbox-exec profile），Linux 用 Landlock + seccomp——内核级约束，不是容器。
  • sandbox_mode 三档：read-only（默认起步）/ workspace-write（网络默认关）/ danger-full-access；approval_policy 四档：untrusted / on-failure / on-request / never。沙箱决定"能做什么"，审批决定"何时问人"，两轴正交——这是 Codex 最值得借鉴的设计。
  • config.toml 的 model_providers 可指向任意 OpenAI 兼容端点；codex exec 非交互模式；rollout JSONL 会话持久化 + resume。

来源：Unrolling the Codex agent loop（HN 讨论）· openai/codex · Sandboxing 文档 · ByteByteGo 图解

04OpenCode（SST/Anomaly）—— "provider 无关 + LSP 反馈回路"

开源 MITTS + GoLSP 集成client/server 架构：Bun + Hono HTTP server，Go TUI 编译为单一可执行文件；SDK 从 OpenAPI spec 自动生成；200+ provider（Vercel AI SDK + models.dev）。

Loop（源码级，社区分析带代码路径）

  • 核心循环在 packages/opencode/src/server/server.ts 的 Session.prompt：基于 Vercel AI SDK streamText，stopWhen: steps.length >= 1000 || shouldStop，maxRetries: 3。
  • processor.process(stream) 消费 fullStream 事件（tool-call / tool-result / tool-error / text-delta / start-step / finish-step）；权限被拒即置 shouldStop。
  • 消息 = parts（text part / tool part），tool part 有 running → completed 状态机，全部持久化到磁盘并经 SSE 广播——UI 只是事件的订阅者。

工具与特色机制

  • 工具：bash / edit / read / write / glob / grep / list / webfetch / todowrite / todoread / task（子代理）/ lsp（实验性）；定义三要素 description + Zod schema + execute。
  • 最大特色是 LSP 集成：edit 执行后自动 LSP.touchFile + 拉取 diagnostics 回喂模型（gopls / pyright / typescript-language-server / ruby-lsp），还暴露 goToDefinition / findReferences——等于给 agent 配了 IDE 的大脑做免费验证回路。
  • plan/build 双 agent（plan 只读，bash 需批准）；子代理用 markdown frontmatter 定义（独立 model / 工具白名单），独立 session、独立上下文。
  • 上下文：token 超过 (context - outputLimit) * 0.9 自动摘要；快照/回滚用临时 git（write-tree 保存、checkout-index 恢复，不动真实历史）；系统提示按 provider 定制。

来源：源码深度分析 · LSP 文档 · sst/opencode

05DeepSeek Harness（dsh）—— "一切皆插件"的极端派

开源 MITCordis 插件运行时developer preview先在 V3.1（2025-08）转向 agent（SWE-bench Verified 从 45.4 → 66.0，Terminal-Bench 13.3 → 31.3，全部用内部极简 harness 跑出），随后把 harness 开源（~280k stars）。

模型侧：harness 与模型协同设计

  • chat template 用特殊 token 表达工具调用：<｜tool▁calls▁begin｜><｜tool▁call▁begin｜>name<｜tool▁sep｜>args<｜tool▁call▁end｜>...<｜tool▁calls▁end｜>；工具描述以 ## Tools 段附在 system prompt 后；支持多 tool call 直排。
  • 混合 think / non-think 单模型；API 提供 Anthropic 兼容端点与严格函数调用。
  • 启示：模板、tokenizer、agent 轨迹训练数据与 harness 是一体两面——不存在模型无关的最优工具设计。

Harness 架构（官方 architecture.md）

  • "Everything is a Plugin"：model adapter、tool registry、session log、agent loop 本身都是可替换插件；"There is no privileged core to patch"。底层 Cordis 框架：插件向共享 context 贡献 services + typed events + 可撤销 effects，卸载自动回滚。
  • Profile / Bundle 组合机制：命名 profile（web / headless / sdk / sdk-minimal / acp）叠加 bundles 与用户 patch——把"发行版组装"变成声明式配置。
  • Loop 生命周期：step = 一次模型请求 + 其工具调用；turn = 0+ steps。事件瀑布：agent/pre-step（可 accept/rewrite/reject）→ agent/request → prompt sections + step 级工具 schema 组装 → deriveMessages() 冻结历史 → llm/stream → tools/pre-execute/execute/post-execute → step/end → turn/end。失败的尝试保留为 assistant/attempt 事件但不进模型可见历史。
  • Session log 是模型上下文的唯一来源："Model-visible means logged"——每个模型请求都必须能从日志重建；JSONL 版本化迁移。
  • 执行世界可整体迁移：文件系统与子进程共享同一 execution world，把 provider 指向远程沙箱，Bash/PTY/LSP 全部随之迁移；ctx.sandbox 在 spawn 前 wrap argv。
  • Subagent 是一个"seam"：从"fresh child agent"到"另一个产品里的委托 turn"都能插；Agent Teams 提供任务板、身份、消息、中断。

来源：deepseek-ai/deepseek-harness（docs/architecture.md）· V3.1 公告 · HF 模型卡

06五家速览：Aider / Cline / Gemini CLI / Goose / Amp

6.1 Aider —— 不用 tool call 也能打

  • 结构化输出替代工具调用：edit formats —— whole（整文件，简单但贵）/ diff（SEARCH/REPLACE 块）/ diff-fenced（适配 Gemini）/ udiff（专治 GPT-4 Turbo 的 lazy coding）/ editor-diff（--architect 模式：架构师模型出方案 + 编辑器模型出 diff 的双模型分工）。每种模型配实测最适配的格式。
  • Repo map：tree-sitter 抽符号 → 文件依赖图 → 图排序（类 PageRank）→ 默认 1k token 预算输出"最重要的签名树"——"预检索上下文"路线的代表作（与 Claude Code 的 just-in-time 探索相对）。
  • git 原生：每次修改自动 commit、可 undo；--lint --test 自动跑并回喂。

edit formats · repo map

6.2 Cline —— IDE 内嵌 + 逐工具审批的"安全派"

  • 每次工具调用默认都要用户批准（auto-approve 可按工具粒度放开）——把 human-in-the-loop 做成默认值。
  • Plan / Act 双模式：Plan 完全只读，Act 才执行——认知上分离"探索"与"修改"。
  • 工具：execute_command / read_file / write_to_file（全文件重写）/ replace_in_file（SEARCH/REPLACE）/ search_files / list_files / use_mcp_tool 等。
  • Checkpoints：隐藏的 shadow git，每次工具调用后快照工作区，可 restore/compare，不污染真实历史；@mentions 引用上下文；接近上限自动 compact。

6.3 Gemini CLI —— Google 的开源通用 CLI

  • Apache-2.0，TypeScript；工具：google_web_search（grounding）/ web_fetch / read-write-replace / shell / save_memory；MCP 走 settings.json。
  • .gemini/ 目录：custom commands（轻量子代理/斜杠命令）、GEMINI.md 分层记忆、.geminiignore；checkpoint/restore、自动 compression、trusted folders + 逐命令审批（YOLO 放开）、Docker 沙箱、headless JSON 输出。

6.4 Goose（Block → Linux Foundation）—— MCP-first 通用 agent

  • Rust；所有能力都是 MCP extension（70+），provider 15+（含 Ollama）。
  • Subagents = 独立 goose 进程（lead agent 派生，各自独立上下文）；Recipes/macros：声明式 YAML 工作流——把 workflow 编排作为 loop 之上的可选层；.goosehints 等价 CLAUDE.md。

6.5 Amp —— "皇帝没穿衣服"的极简派

  • 400 行 Go + 3 个工具（read_file / list_files / edit_file）写出能用的编码 agent；edit 用 string replace 是实测发现 Claude 3.7 特别擅长；空 old_str + 不存在的文件 = 创建。
  • 工具四要素：name / description / JSON schema / execute。输出格式没有标准答案，按"模型能不能理解 + token 开销 + 生成速度"实验决定。
  • 结论：复杂度应该花在打磨而不是架构上。

How to Build an Agent

07学术与方法论参照：SWE-agent / OpenHands / Manus

7.1 SWE-agent —— ACI 概念的出处

不微调模型，只靠为 GPT-4 设计的 ACI（受限动作空间 + guardrails）就大幅提升 SWE-bench：search / lookup / 100 行窗口 open / 自带语法检查的 edit（改坏拒绝提交）/ 强制 lint / 限制并发编辑。配置驱动：YAML 定义工具与提示词，可整份换掉（dsh 插件化思想的先声）。Enact 版（2025）进一步工程化：typed events、record/replay、结构化类型工具 API。

7.2 OpenHands —— 事件溯源 + CodeAct

  • 架构：immutable EventLog（一切皆事件），Agent 是无状态循环执行器（读事件 → 查 LLM → 发 Action → 收 Observation），Conversation + Runtime（Docker 沙箱）分离——事件溯源 + 确定性重放。
  • CodeActAgent：action 空间是 Python 代码（一段代码里连续调用编辑/bash 函数）而非离散 JSON——表达力强（循环/条件/组合），代价是安全与解析复杂度。
  • Condenser 抽象：上下文压缩成为可插拔策略；SecurityAnalyzer 对动作风险分级（低风险直执 / 高风险等确认）。

架构文档 · SWE-agent 论文

7.3 Manus —— KV-cache 优先的上下文工程（方法论）

  1. KV-cache 命中率是生产 agent 最重要的单一指标（输入:输出 ≈ 100:1，缓存与非缓存 token 价差约 10 倍）→ prompt 前缀稳定、上下文 append-only、JSON 序列化确定性、显式缓存断点。
  2. 工具要 mask 不要 remove：中途增删工具会作废缓存并让历史引用失效 → 状态机 + logits mask + 统一前缀命名（browser_ / shell_）。
  3. 文件系统是终极上下文：外部记忆无限且持久；压缩必须可恢复（丢网页内容但保 URL，丢文档内容但保沙箱路径）。
  4. todo.md 复述：反复重写计划 = 把全局目标"复述"到上下文末尾，对抗 lost-in-the-middle。
  5. 保留失败：不清理错误 trace，失败证据帮模型隐式更新信念。
  6. 小心 few-shot 陷阱：上下文过于同质会让模型盲目延续模式 → 注入受控多样性。

关键维度分拆

  • 循环结构：全部收敛于"单层 while 循环 + 工具调用"，没有人用 planner-executor 分层做主循环——规划被降维成一个工具（update_plan / TodoWrite / todo.md）或一种模式（Plan mode）；复杂度被推到子代理（并行/隔离）和事件协议（App Server、dsh 事件瀑布、EventLog）。
  • 编辑策略四派：string replace（最通用，前提"必须先 Read"）/ 自定义 patch（多文件原子修改、token 高效）/ 整文件重写（简单可靠，配 IDE 审批）/ 结构化输出（跨模型兼容，含不开 function call 的开源模型）。没有银弹，按模型实测选格式。
  • 上下文三板斧（家家命中）：压缩 + 外部记忆（AGENTS.md 已成事实标准）+ 子代理隔离；外加 just-in-time 检索 vs 预检索地图两条路线。
  • 权限光谱（松→紧）：Manus/Amp 云沙箱全自动 → Codex OS 沙箱 × 审批正交 → Claude 多模式 + hooks → OpenHands 风险分级 → Cline 默认逐工具人工审批。
  • 扩展机制：MCP 已成公约数；分歧在 MCP 之上——hooks/skills 四层（Claude）、协议化（Codex 明确不用 MCP 管会话）、一切皆插件（dsh）、MCP-only（Goose）。

09从对比中提炼的十条设计规律

  1. 循环必须傻，工具必须好（ACI 第一定律）：智力投资放在工具接口、描述文案和反馈内容上，而不是控制流上。
  2. 上下文是稀缺资源，KV-cache 是命根子：append-only、稳定前缀、确定性序列化、配置变更追加而不改写、工具 mask 而非删、延迟加载。
  3. 规划降维成一个工具，探索降维成子代理：没有 planner-executor 架构，只有 update_plan/TodoWrite + Task/subagent。
  4. 验证回路决定下限：lint / test / LSP diagnostics / git diff 自动回喂——比模型能力更决定日常可用性。
  5. 权限模型是产品决策："能做什么"（sandbox）与"何时问人"（approval）应解耦成正交两轴。
  6. 一切事件化/持久化：会话即日志，带来 resume / fork / replay / 审计能力。
  7. 可恢复 > 可丢弃：checkpoint + 可恢复压缩是长任务的保险。
  8. 模型与 harness 协同设计：DeepSeek 改模板连带改训练；Aider 按模型选格式；Amp 按模型选 string replace。
  9. 结构化的失败要保留：失败轨迹是模型的免费学习信号。
  10. 最小可用内核极小，护城河在打磨：流式执行、后台任务、审批 UX、可观测性、成本控制。

10选型指南：当我们自己要做一个 Agent

第一步：先分类，再动手

用 Anthropic 的二分法开场：Workflow（路径可预先编排，要可预测）→ prompt chaining / routing / parallelization / orchestrator-workers / evaluator-optimizer，普通代码 + LLM 调用即可，不要上自主循环；Agent（开放问题、步数不可预测、需要 grounding）→ while 循环 + 工具 + 反馈，用沙箱和 evals 对冲风险。

第二步：最小可行 Agent（MVP 清单）

一个能打的编码 agent MVP = 1 个模型 + 6 个工具 + 3 个机制：

工具（6 个起步）
  read_file    # 带行号、默认截断、禁止 cat
  edit_file    # string replace，必须先 read；空 old + 新路径 = 创建
  bash         # 持久会话、超时、输出截断、后台执行
  grep / glob  # 专用搜索工具，禁止在 bash 里 grep/find
  todo / plan  # 规划工具——注意这是"一个工具"而不是一层架构

机制（3 个）
  权限闸门     # allowlist/denylist + 危险命令确认；沙箱能上就上
  验证回路     # 编辑后自动 lint / typecheck / LSP diagnostics 回喂
  上下文预算   # 接近上限触发摘要压缩；或文件外置记忆

参考量级：Amp 的 400 行 Go / Claude Agent SDK 的 ~50 行 Python 就能跑起这个循环。

第三步：逐项决策清单

决策点选项与适用条件
模型reasoning model（复杂规划，慢贵）vs 快速模型（高频小步）；单模型 vs architect+editor 双模型（Aider）；能否换 provider（OpenCode / Codex 都做了抽象）
Loop 实现裸 API while 循环（可控性最好，Amp / Anthropic 官方都推荐先这样）→ Agent SDK（现成权限/hooks/子代理/会话）→ 框架（LangGraph 状态机适合复杂编排；OpenHands SDK 事件溯源适合平台化；需要持久化/协作/复杂多 agent 时才值得）

面试答题框架（建议展开顺序）

  1. 定义：agent = LLM + 工具 + 环境反馈循环（引 Anthropic / Thorsten Ball）；与 workflow 的区别（谁决定控制流）。
  2. 本质简单性：画出标准循环伪代码；"皇帝没穿衣服"——400 行就能写出可用 agent。
  3. 真正的难点（体现深度）：ACI / 工具设计（引 SWE-agent + poka-yoke）、上下文工程（attention budget、compaction / 外部记忆 / 子代理隔离、KV-cache 友好）、验证回路、权限模型。
  4. 横向证据（体现广度）：举 2–3 个具体对比——Claude"先 Read 才能 Edit + 只读工具并行" vs Codex"apply_patch 单入口 + OS 沙箱正交审批" vs OpenCode"LSP 反馈回路" vs dsh"loop 可插拔"。
  5. 选型结论（体现判断力）：从最小循环起步、预算花在工具与上下文打磨、按模型实测编辑格式、权限与沙箱解耦、evals 驱动迭代；需要持久化/编排/协作时才引入框架。
