Agent SSH Tool 产品流程与交互设计

从配置、接入、使用到交互的完整用户旅程 —— 面向 Kimi CLI 及通用 Agent

1. 产品定位

Agent SSH Tool 是 Agent 的“远程手脚”：让 Agent 能够安全、异步、可观测地登录到远程机器并执行操作；同时保留一条“人在回路”的通道，当 Agent 遇到需要确认、输入或排查的场景时，用户可以无缝接管。

核心产品主张：

  • 对 Agent：像调用本地命令一样调用远程机器，但完全异步、可追踪
  • 对用户：既能享受自动化的效率，又能在关键时刻介入和确认
  • 对平台：统一凭证、统一审计、统一调度

2. 目标用户与角色

角色主要职责使用场景
平台管理员配置凭证、主机、权限策略初始化部署、安全管控
Agent（自动化主体）发起任务、获取结果、做决策自动部署、巡检、修复
终端用户与 Agent 对话、确认关键操作、必要时接管 Shell日常运维、问题排查
审计/安全人员查看操作日志、审计会话合规、事后复盘

4. 配置阶段

4.1 管理员配置主机

步骤 1：注册主机

管理员通过 CLI 或 Web UI 注册一台远程主机：

ssh-tool host add \
  --name prod-web-01 \
  --hostname 10.0.1.23 \
  --port 22 \
  --username deploy \
  --credential prod-deploy-key \
  --labels env=prod,role=web,team=platform

注册后系统进行连通性测试，成功后主机状态变为 available。

4.2 配置凭证

步骤 2：注册凭证

凭证独立存储，支持密码、私钥、SSH Agent 三种类型：

ssh-tool credential add \
  --name prod-deploy-key \
  --type private_key \
  --key-file ~/.ssh/id_rsa_prod \
  --allowed-hosts 10.0.1.0/24

凭证加密存储，Agent 只引用名称，永不接触明文。

4.3 权限策略

步骤 3：配置权限
  • 哪些 Agent/用户可以对哪些主机执行哪些命令
  • 危险命令拦截列表（如 rm -rf /、mkfs）
  • 是否需要用户二次确认
  • 最大执行时长、最大并发数

5. Agent 接入阶段

5.1 Agent 如何发现工具

Agent 通过标准 Tool 协议发现 SSH Tool。以 Kimi CLI 为例，Tool 描述形如：

{
  "name": "ssh_tool",
  "description": "在远程主机上执行命令、传输文件或打开交互式 Shell",
  "parameters": {
    "type": "object",
    "properties": {
      "host": { "type": "string", "description": "主机名或 host_id" },
      "command": { "type": "string", "description": "要执行的命令" },
      "mode": { "type": "string", "enum": ["foreground", "background"], "default": "foreground" },
      "timeout": { "type": "integer", "description": "超时时间（秒）" },
      "require_confirmation": { "type": "boolean" }
    },
    "required": ["host", "command"]
  }
}

5.2 Agent 连接与认证

Agent 本身不需要管理 SSH 连接。它通过调用 Tool API 发起请求，由 SSH Tool 后端完成：

  1. Agent 调用 ssh_tool，传入 host 和 command
  2. SSH Tool 后端根据 host 找到对应 credential
  3. 后端建立 SSH 连接（或复用已有 Session）
  4. 后端执行任务，异步返回 task_id

关键设计：Agent 不持有 SSH 私钥、不直接连接远程主机。所有连接由受信任的 SSH Tool 后端代理，便于统一审计和轮换凭证。

6. Agent 使用阶段

6.1 前台任务：Agent 同步等待

适用于短命令、需要立即拿到结果的场景。

User: 帮我看看 prod-web-01 的磁盘使用情况
Agent: 好的，我执行一下 df -h。
      [调用 ssh_tool，mode=foreground]
      [等待结果...]
Agent: prod-web-01 的磁盘使用情况如下：
      /dev/sda1 已用 72%，剩余 28GB。

6.2 后台任务：Agent 提交后异步跟进

适用于长时间运行、批量部署等场景。

User: 在 prod-web-01 上后台部署新版本
Agent: 已提交后台任务，task_id: t-abc123。我会持续跟踪进度。
      [Agent 订阅任务事件流]
      [每隔一段时间向用户汇报关键节点]

6.3 文件传输

Agent 通过扩展参数上传/下载文件：

{
  "host": "prod-web-01",
  "task_type": "upload",
  "local_path": "/tmp/config.json",
  "remote_path": "/etc/app/config.json"
}

7. Agent 怎么获取所有需要的消息

7.1 消息类型

Agent 需要获取的消息分为四类：

消息类型内容获取方式
状态事件Pending → Running → Succeeded / Failed / CancelledWebSocket / SSE / 轮询
输出日志stdout / stderr 片段流式订阅 或 分页查询
诊断信息错误码、根因提示、建议动作任务结束时随结果返回
交互请求“命令需要输入，请用户接管”运行时事件推送

7.2 推荐获取模式

对 Kimi CLI 这类终端 Agent，推荐 SSE（Server-Sent Events） 或 长轮询，因为：

  • 单向 server → client 推送足够
  • 比 WebSocket 更简单，易穿越代理
  • Agent 可以在一个连接里同时接收状态、日志、事件

7.3 消息协议示例

event: task_state
data: {"task_id":"t-abc123","state":"Running","timestamp":"..."}

event: log
data: {"task_id":"t-abc123","type":"stdout","data":"Installing nginx..."}

event: interaction_request
data: {
  "task_id":"t-abc123",
  "type":"awaiting_input",
  "reason":"sudo password required",
  "suggested_action":"open_interactive_shell"
}

event: task_complete
data: {
  "task_id":"t-abc123",
  "state":"Succeeded",
  "exit_code":0,
  "duration_ms":12500,
  "summary":"nginx installed successfully"
}

8. 用户交互流程

8.1 纯 Agent 自动执行

User: 在 prod-web-01 上检查 nginx 状态
Agent: 执行 systemctl status nginx
      [task 自动完成]
Agent: nginx 正在运行，已运行 3 天 12 小时。

8.2 Agent + 用户确认

当命令命中策略（危险操作、影响范围大）时，Agent 先询问用户：

User: 重启 prod-web-01 上的 nginx
Agent: 重启 nginx 会影响当前在线连接，确认执行吗？
       [展示影响范围：prod-web-01, service: nginx, connections: 42]
User: 确认
Agent: 执行重启中... [task 开始]
      [完成后]
Agent: nginx 重启成功，服务已恢复。

8.3 Agent + 交互式 Shell

当命令进入交互状态或需要人工排查时，Agent 打开交互式终端：

User: 帮我排查 prod-web-01 上 nginx 启动失败的原因
Agent: 我先查看日志... [执行 journalctl -u nginx]
      [输出显示配置语法错误]
Agent: 发现 /etc/nginx/nginx.conf 第 47 行有语法错误，需要进入交互式 Shell 手动修复吗？
User: 打开终端
Agent: [调用 AttachInteractive(t-xxx)]
      [在 Kimi CLI 中嵌入一个 xterm.js 终端面板]
      [用户直接编辑配置文件、测试、重启]
User: 修复好了
Agent: 我确认一下 nginx 状态... [继续自动化]

8.4 交互式 Shell 的产品细节

功能说明
一键开启Agent 检测到需要交互时，向用户展示“打开终端”按钮
权限继承用户接管时继承该 task 的凭证和主机权限，无需二次登录
会话录制交互过程全程录像/录屏，便于审计和复盘
安全提示顶部显示当前主机、用户、剩余空闲时间
自动关闭空闲超过 N 分钟自动断开，释放资源
交还 Agent用户退出终端后，Agent 可继续执行后续检查

9. 异常与错误处理流程

9.1 连接失败

Agent: 无法连接到 prod-web-01 (Connection timeout)
       可能原因：网络不可达、SSH 端口未开放、主机已下线
       建议：
       1. 检查主机网络状态
       2. 确认安全组/防火墙规则
       3. 使用 TestConnection 重新验证

9.2 认证失败

Agent: 认证失败，无法使用 prod-deploy-key 登录 prod-web-01
       可能原因：密钥被轮换、用户名错误、密钥权限过大
       建议：
       1. 在凭证管理页面更新密钥
       2. 确认 ~/.ssh/authorized_keys 包含当前公钥

9.3 命令执行失败

Agent: 命令执行失败 (exit code 1)
       命令：apt install -y nginx
       错误：E: Unable to locate package nginx
       建议：
       1. 运行 apt update 刷新包索引
       2. 检查源配置 /etc/apt/sources.list
       [Agent 可以自动尝试 apt update 后重试，并询问用户]

9.4 超时

Agent: 任务执行超过 300 秒，已自动取消
       可能原因：命令挂起、等待输入、网络卡顿
       建议：
       1. 以 background 模式重新执行
       2. 打开交互式 Shell 查看现场

10. 安全与权限流程

10.1 最小权限原则

  • 每台主机配置专用低权限账号（如 deploy）
  • 禁止 root 直连，必要时通过 sudo 并记录
  • 凭证按主机/环境隔离

10.2 命令审查

策略引擎在任务执行前检查：

if command matches dangerous_pattern:
    require_user_confirmation()
if command writes to protected_path:
    require_admin_approval()
if command runs as root:
    add_audit_flag()

10.3 审计日志

每次操作记录：

  • 谁（Agent / 用户）
  • 在什么时间
  • 对哪台主机
  • 执行了什么命令
  • 结果和输出摘要
  • 是否经过交互式 Shell

11. 可观测性

11.1 Agent 侧视角

Agent 能获取到的信息：

  • 任务实时状态
  • 逐行输出
  • 执行耗时
  • 退出码
  • 错误诊断
  • 是否有人工接管

11.2 用户侧视角

  • 当前有哪些任务在跑
  • 历史任务列表与结果
  • 输出回放
  • 交互式 Shell 入口

11.3 平台侧视角

  • 主机健康状态
  • 队列长度与等待时间
  • 并发会话数
  • 失败率、错误类型分布

12. 完整示例 Walkthrough

场景：用户让 Kimi CLI 在远程服务器上排查并修复问题

Step 1：用户发起请求
User: prod-web-01 的 nginx 好像停了，帮我看看
Step 2：Agent 调用 SSH Tool
Agent → ssh_tool:
  host: prod-web-01
  command: systemctl status nginx
  mode: foreground
  timeout: 30
Step 3：SSH Tool 调度并执行
Task t-001 创建 → Queued → Preparing → Connecting → Running
输出流实时返回给 Agent
Step 4：Agent 分析输出并决策
输出显示：nginx failed (exited, code=1) /etc/nginx/nginx.conf:47 unknown directive
Agent 判断：配置错误，需要人工修复
Step 5：Agent 请求用户接管
Agent: 发现 nginx 配置文件第 47 行有语法错误，需要进入交互式 Shell 修复吗？
User: 好，打开终端
Step 6：用户通过交互式 Shell 修复
[Kimi CLI 中弹出 xterm.js 终端]
User 执行：vim /etc/nginx/nginx.conf
User 执行：nginx -t
User 执行：systemctl restart nginx
Step 7：Agent 接管后续
用户退出终端
Agent 自动执行：systemctl status nginx
Agent: nginx 已恢复正常运行，配置验证通过。

13. 产品验收清单

  • ✅ 管理员可以注册主机和凭证
  • ✅ Agent 可以通过 Tool API 发起前台/后台任务
  • ✅ Agent 可以实时获取任务状态、输出、诊断信息
  • ✅ 危险操作可以触发用户确认
  • ✅ 交互式 Shell 可以一键开启和交还
  • ✅ 所有操作都有审计日志
  • ✅ 任务支持取消、超时、重试
  • ✅ 失败后 Agent 能获得可操作的诊断建议
