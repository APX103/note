01先建立整体地图

Claude Code 的 Agent Loop 可以拆成四层。入口层处理文本、图片、Slash Command 和 Hook；核心层维护消息状态并决定继续还是结束；工具层把模型生成的 tool_use 变成真实副作用和 tool_result；适配层把流式事件显示到 REPL，或转换成 SDK 消息。

入口证据：screens/REPL.tsx:2661–2803 · QueryEngine.ts:1180–1294 · query.ts:219–239
最重要的复用：Subagent 没有“子进程专属 Agent Loop”。runAgent() 只是构造一套新的消息、工具、权限上下文，然后调用与主 Agent 相同的 query()。所以理解了主循环，就理解了子 Agent 90% 的运行机制。

三个容易混淆的“轮次”

  • 用户轮次（user turn）：一次用户提交到最终答复，内部可能发生很多次 API 请求。
  • Loop iteration：queryLoop 的一次 while 迭代。工具结果产生后，turnCount + 1，再次请求模型。
  • Subagent 运行：由一次 Agent 工具调用启动，内部拥有自己的一整个用户轮次和多次 Loop iteration。

02入口：用户输入如何进入 Loop

2.1 REPL：先规范化，不是直接请求模型

REPL 的 handlePromptSubmit() 先处理粘贴文本、图片引用、退出命令和立即执行的本地命令。如果当前已有查询，新的 prompt/bash 输入会进入统一队列；否则封装成 QueuedCommand，交给 executeUserInput()。

processUserInput() 再按输入类型分流：

  • 普通文本经 processTextPrompt() 形成 user message，并附带 IDE 选择、文件、Todo、Skill 等上下文。
  • Slash Command 可以只在本地执行；当 shouldQuery=false 时，不进入模型 Loop。
  • 图片会存储、缩放并转成 Content Block；UserPromptSubmit Hook 可以阻止提交或附加上下文。
handlePromptSubmit.ts:120–170 · handlePromptSubmit.ts:396–496 · processUserInput.ts:85–269

2.2 两个入口，共用同一个核心

入口准备工作消费 query() 事件的方式
REPL.onQueryImpl构建 System Prompt、User/System Context、工具上下文与 AbortController。onQueryEvent 更新 React 消息列表、流式文本、Tool UI 和 transcript。
QueryEngine.submitMessage除上述内容外，还维护跨提交的消息数组、usage、权限拒绝和文件读取缓存。归一化为 SDK Message，写会话记录，最终生成 result；ask() 是其一次性便捷封装。

因此本文后续只追 query()：它是两条路径真正的汇合点。启动时的认证、MCP 初始化和终端渲染不属于核心 Loop，不在本文展开。

03核心 queryLoop 的九个阶段

query() 是很薄的生命周期包装，真正逻辑在 queryLoop()。状态对象包含 messages、toolUseContext、压缩跟踪、输出截断恢复次数、Stop Hook 状态和 turnCount。每轮末尾用一个新的 State 替换旧状态。

state = {
  messages, toolUseContext, turnCount: 1,
  autoCompactTracking, maxOutputTokensRecoveryCount,
  stopHookActive, transition, ...
}

while (true) {
  messagesForQuery = prepareContext(state.messages)
  assistantMessages, toolResults, toolUseBlocks = [], [], []

  for await (message of callModel(...)) {
    yield message
    collect assistantMessages and toolUseBlocks
  }

  if (toolUseBlocks.length === 0) {
    if (recoverableError) { state = recoveredState; continue }
    if (stopHookSaysContinue) { state = withHookMessage; continue }
    return completed
  }

  for await (update of executeTools(toolUseBlocks)) {
    yield update.message
    toolResults.push(normalizeForAPI(update.message))
  }

  attachments = drainQueuedCommandsAndContext(...)
  if (aborted || hookStopped || maxTurnsExceeded) return ...

  state.messages = [...messagesForQuery, ...assistantMessages,
                    ...toolResults, ...attachments]
  state.turnCount += 1
}
主状态机：query.ts:241–321、while 入口、下一轮状态提交。源码中的 query_recursive_call 只是 profiler 的历史命名，当前实现是迭代，不是递归调用自身。

准备本轮消息视图

先取最近一次 compact boundary 之后的消息，再按顺序应用工具结果预算、可选 Snip、Microcompact、Context Collapse 和 Autocompact。System Context 被追加到 System Prompt，User Context 在调用模型前注入消息。

建立本轮执行器

初始化 assistantMessages、toolResults、toolUseBlocks，并根据 tengu_streaming_tool_execution2 选择是否创建 StreamingToolExecutor。

流式请求模型

deps.callModel 在生产环境是 queryModelWithStreaming。参数包括消息、System Prompt、工具、模型、Thinking 配置、AbortSignal、Agent 定义和权限上下文等。

收集 assistant 与 tool_use

每个 assistant 消息既向外 yield，也加入本轮数组。内容中的 tool_use block 被单独收集，并令 needsFollowUp=true。

无工具调用：尝试恢复或结束

没有工具调用时，依次处理 Context Overflow、媒体过大、max output tokens、Stop Hook 和 Token Budget；都不需要继续时返回 completed。

有工具调用：执行并回收结果

流式执行器收取剩余结果；否则调用 runTools()。每个工具结果经 API 归一化后成为 user-role 的 tool_result 消息。

加入队列消息与动态附件

工具全部完成后才插入普通用户消息，避免与 tool_result 交错。此处也领取后台任务通知、文件变化、记忆与 Skill 发现附件，并刷新新连接的 MCP 工具。

检查中断、Hook 与 maxTurns

Abort、阻止继续的 Hook、超过 maxTurns 都会终止。否则本轮消息被拼接到状态中，turnCount 加一。

回到 while 顶部

新的模型请求现在能看到“原历史 + assistant 的工具请求 + 工具真实结果 + 新附件”，这就是 ReAct 闭环。

继续循环的真实条件：源码明确说 stop_reason === 'tool_use' 不可靠。它不以这个字段决定循环，而是以实际 assistant 内容中是否出现 tool_use block 为准。query.ts:551–558

04工具执行、权限与并发

4.1 每个工具都经过同一条流水线

tool_use block
   │
   ▼
findToolByName（含旧 alias 回退）
   → inputSchema.safeParse（Zod）
   → tool.validateInput?（工具自定义校验）
   → PreToolUse Hooks
   → 权限决策（规则 / 模式 / 用户 / classifier）
   → tool.call(...)
   → mapToolResultToToolResultBlockParam(...)
   → PostToolUse Hooks
   → user message { tool_result, tool_use_id, is_error? }

工具不存在、参数错误、权限拒绝和执行异常都会尽量转成与原始 tool_use_id 对应的错误结果，而不是直接让整个 Agent Loop 崩溃。这保证下一轮模型能够观察失败并修正动作。

4.2 两条调度路径

路径何时启动工具并发规则结果顺序
runTools
非流式		整次模型响应结束后。连续的 isConcurrencySafe 工具组成并行批次；不安全工具独占串行。默认最大并发 10，可由 CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY 覆盖。按工具调用批次推进。
StreamingToolExecutor
功能开关		模型仍在流式输出时，收到完整 tool block 就可启动。安全工具可并行；任何不安全工具必须独占执行。进度可立即输出；结果完成后释放，仍在执行的非并发工具会阻塞后续结果。

流式执行器还处理两个重要故障场景：Bash 错误会中止同批兄弟工具/子进程；Abort 或模型 fallback 时，为未完成的 tool_use 生成合成的错误 tool_result，避免历史里留下没有结果的“孤儿调用”。

05结束、恢复与中断

“模型不再调用工具”只是最常见的结束条件，不是唯一出口。核心 Loop 和外围 SDK 各自承担一部分限制。

出口 / 转移触发条件结果
completed没有 tool_use，Stop Hook 没有 blocking error，Token Budget 也不要求继续。正常结束当前用户轮次。
max_turns工具结果产生后，turnCount + 1 > maxTurns。产生 max_turns_reached 附件；SDK 转成 error_max_turns。
aborted_streaming
aborted_tools		用户在模型流式输出或工具执行期间中断。补齐必要的错误 tool_result，释放资源并返回。
stop_hook_blockingStop Hook 返回 blocking error。把 Hook 反馈作为 meta user message 加回历史，再请求模型，而不是结束。
hook_stopped / stop_hook_prevented工具 Hook 或 Stop Hook 明确禁止继续。按 Hook 要求退出。
reactive_compact_retryPrompt Too Long / 媒体错误且可恢复。先尝试 Collapse drain，再 Reactive Compact；用压缩后的消息重试。
max_output_tokens_recovery输出被 token 上限截断。必要时提高输出上限；否则注入“从截断处继续”的 meta 消息，最多恢复 3 次。
blocking_limit / 模型错误上下文硬限制、图片错误、不可恢复 API/运行时错误。返回错误；已经出现的 tool_use 会尽量补齐错误结果。
SDK 预算限制getTotalCost() >= maxBudgetUsd。由 QueryEngine 在消费事件时检查，输出 error_max_budget_usd，不在核心 while 内。

06Subagent 完整调用链

6.1 谁决定调用 Subagent？

是模型自己，不是外部路由器。AgentTool.prompt() 把可用的 Agent 类型、用途和工具范围写进工具描述；在可选路径中，动态列表也可通过 agent_listing_delta 附件注入，以避免工具 Schema 变化破坏 Prompt Cache。模型根据这些说明生成 name: "Agent" 的 tool_use。

基础输入为 description、prompt、subagent_type、model、run_in_background；完整 Schema 还包含 Team 名称、权限模式、isolation 和 cwd。Task 是兼容旧会话的别名，当前工具名是 Agent。

AgentTool.call 接管

它先处理 Team 路由；普通路径按 subagent_type 查找经过权限过滤的 AgentDefinition。未指定类型时，默认是 general-purpose；Fork 开关打开时是另一条规定路径。

构造子 Agent 的任务与提示词

普通路径使用所选 Agent 自己的 System Prompt，初始对话只有一条包含任务 prompt 的 user message。父对话内容不会自动塞进去。

组装工具与隔离参数

先用 worker 的权限上下文调用 assembleToolPool，再由 runAgent 根据 Agent 的 allow/deny 列表、内置/自定义身份和同步/后台属性过滤。可选 Worktree 会创建独立 Git 工作区并覆盖 cwd。

运行 runAgent

它完成子上下文初始化后调用同一个 query()。子 Agent 可以使用工具、触发压缩、遇到 maxTurns，逻辑与主 Agent 一致。

只提炼最终报告

finalizeAgentTool() 取最后一个 assistant 的文本；如果最后一个消息只有 tool_use，则向前找最近有文本的 assistant。父 Agent 默认不接收子 Agent 的全部中间工具输出。

映射为普通 tool_result

同步结果包含报告、agentId 和使用量；一次性 Explore/Plan 省略续聊提示。父 Loop 把它加入消息历史，下一次模型请求再综合成用户可见答案。

核心实现：AgentTool.tsx:239–356 · 提示词、工具与运行参数 · finalizeAgentTool · 结果映射
“AgentTool.isReadOnly() === true”不代表子 Agent 只能读。这个标记只是把权限判断委托给它内部实际调用的工具。普通 general-purpose Agent 可以拥有写文件和 Bash 工具；真正的限制来自 AgentDefinition 的工具列表、权限模式和每次内部工具的权限检查。另外，尽管工具提示词使用了“subprocesses”一词，这里的本地普通路径是直接调用 runAgent()，并没有启动独立 OS 子进程。

07runAgent 如何创建子运行时

runAgent() 是 Subagent 的“运行时组装函数”。按源码顺序，关键动作如下：

  1. 解析模型与 agentId：模型优先级由 getAgentModel 统一处理；注册追踪层级，准备独立 sidechain transcript。
  2. 构造 initialMessages：普通 Agent 只有任务消息；Fork 还会拼接过滤过未完成工具调用的父上下文。
  3. 准备上下文：读取 User/System Context；Explore/Plan 可省略 CLAUDE.md 和旧 gitStatus，以减少无效 token。
  4. 解析工具和权限：普通子 Agent 默认关闭 Thinking 以控制成本；同步 Agent 与父 Agent 共享 AbortController，后台 Agent 使用独立控制器。
  5. 执行 SubagentStart Hooks：把 additional context 加入初始消息，并注册 Agent frontmatter 中生命周期 scoped hooks。
  6. 预加载 Skills、连接专属 MCP：Agent 可以增加自己的 MCP Server；新建的内联连接在结束时清理，引用父级已有连接不会被误关。
  7. createSubagentContext：替换 messages、options、agentId、文件缓存和各类状态回调，形成新的 ToolUseContext。
  8. 写初始 sidechain 与 metadata，随后进入 for await (const message of query(...))。
  9. finally 清理：关闭专属 MCP、清理 Hooks/缓存/Todo、停止该 Agent 遗留的后台 Bash 和监控任务。

08同步、异步与并行回收

同步：父工具调用等待子 Loop

AgentTool.call 持续消费 runAgent 的 async iterator，收集消息并向 UI 转发 tool_use/tool_result 进度。完成后返回 status: "completed"，父工具层将其映射为最终报告的 tool_result。

父 Loop 此时仍停在这一个工具调用里。

异步：先返回句柄，后送通知

先注册 LocalAgentTask，再用 detached closure 启动 runAsyncAgentLifecycle。父 Agent 立即得到 status: "async_launched" 和 output_file，继续自己的工作。

最终结果通过后续 task-notification 回到模型，不是父 Agent 主动轮询得到。

8.1 同步结果的精确边界

子 Agent 完整历史：
  user(task) → assistant → tool_use → tool_result → ... → assistant(final report)
       │                         │
       │                         └─ AgentTool.onProgress：供 UI 展示
       └─ recordSidechainTranscript：完整落盘

父 Agent 历史：
  assistant(tool_use: Agent)
  user(tool_result: final report + agentId + usage)  ← 不包含所有中间工具输出

8.2 后台结果如何重新进入父 Loop

  1. runAsyncAgentLifecycle 消费子 Loop，持续更新 Task 进度。
  2. 完成后先 completeAgentTask，让等待 TaskOutput 的调用立即解除阻塞，再整理报告和 Worktree 信息。
  3. enqueueAgentNotification 生成包含 taskId、状态、result、usage、output_file 的 <task-notification>，以 mode: "task-notification" 入队；notified 标志避免重复通知。
  4. 若父 Loop 正在运行，通知在工具完成后的附件阶段被领取，进入下一次模型请求；若父 Loop 已空闲，useQueueProcessor 在队列变化时启动一个新的输入轮次。
异步启动 · 同步启动 · 后台生命周期 · 通知入队 · 空闲时处理队列

8.3 并行 Subagent 不需要另一个 Scheduler

AgentTool.isConcurrencySafe() 返回 true。因此模型在同一条 assistant 消息里发出多个 Agent tool_use 时，通用工具调度器就可以并行运行它们。同步并行意味着父工具批次等待这些调用全部产出结果；后台并行则每次调用很快返回 agentId。

同步前台 Agent 也已注册成 Task，因此可以中途转后台；开启自动后台化时，默认阈值为 120 秒。转后台后，原调用返回 async_launched，后续仍走同一通知机制。

09普通 Subagent、Fork 与 Team

路径初始上下文工具 / Prompt Cache返回方式
普通 Subagent
subagent_type		所选 Agent 的 System Prompt + 一条任务 prompt；不继承父对话。独立组装并过滤工具；普通路径关闭 Thinking。默认同步最终报告；可后台通知。
Fork Subagent
FORK_SUBAGENT 开关		继承父 System Prompt 与对话；省略 subagent_type 时触发。复用父 tools、model、Thinking 和上下文前缀，目标是命中同一 Prompt Cache。该实验路径统一后台执行，以 task-notification 回收。
Agent Team / Teammate
team_name + name		独立成员身份和团队上下文。走 spawnTeammate，不是本文的普通 runAgent 路径。teammate_spawned，之后通过 Mailbox / SendMessage 协作。
Remote
内部构建		任务被 teleport 到远程 CCR 会话。不是本地子 Loop。remote_launched + taskId/sessionUrl。

Fork 为什么要有 placeholder tool_result？

Fork 调用发生在父 assistant 已生成 tool_use、但真实工具结果尚未完成的时刻。子历史既要保留父 assistant 的完整 tool_use，又必须满足 API 的 tool_use/tool_result 配对要求。buildForkedMessages() 因此克隆父 assistant，并为每个 tool_use 填统一占位结果，最后追加子 Agent 专属 directive。

这样多个 Fork 的 API 前缀可以保持一致，只在最后的任务指令处分叉。它还会用 querySource 和 Fork 标记阻止 Fork 内再次 Fork，避免递归失控。

Worktree 的回收策略

Subagent 在临时 Worktree 中完成后：没有变化就删除 Worktree；有变化则保留，并把 worktreePath 和 worktreeBranch 放进结果。它解决代码工作区冲突，但不等于安全沙箱，也不是独立 OS 进程权限边界。

10一次完整消息轨迹

把“请调查模块 A，同时检查测试”抽象成一次同步 Agent 调用，消息流如下：

U0  用户：调查模块 A，并检查测试

P1  父 assistant：tool_use Agent({
      description: "调查模块 A",
      subagent_type: "Explore",
      prompt: "只读调查 A 的入口、依赖与测试，返回关键文件和结论"
    })
        │
        │  AgentTool 创建 C0 = [user(任务 prompt)]
        ▼
C1  子 assistant：tool_use Glob / Grep
C2  子 user：tool_result（搜索匹配）
C3  子 assistant：tool_use Read
C4  子 user：tool_result（文件内容）
C5  子 assistant：最终调查报告，不再调用工具
        │  子 queryLoop 返回 completed
        │  finalizeAgentTool 提取 C5 文本
        ▼
P2  父 user：tool_result {
      tool_use_id: P1 的 Agent 调用 ID,
      content: 调查报告
    }

P3  父 assistant：基于报告回答用户，或继续调用测试工具
P4  父 user：测试工具结果（如果 P3 有 tool_use）
P5  父 assistant：最终答复，没有 tool_use → Stop Hooks → completed

这里有两条独立的消息链：C 链是子 Agent 的完整执行轨迹，P 链是父 Agent 的决策轨迹。两条链通过 P1 的调用和 P2 的报告连接，而不是把 C1–C4 全量复制进 P 链。

11上下文与状态边界

11.1 AgentDefinition 从哪里来

内置 Agent、插件 Agent、用户/项目/策略配置中的 Markdown 或 JSON Agent 会合并为定义列表。定义可声明 tools、disallowedTools、model、effort、permissionMode、maxTurns、skills、mcpServers、background、memory 和 isolation 等。

该快照中的内置定义包含 general-purpose、状态线配置、Claude Code Guide，以及受开关控制的 Explore、Plan、verification。Explore 明确禁用 Agent 和文件编辑工具。外部构建默认从子 Agent 工具池排除 Agent，内部 ant 构建则允许嵌套委派；后台 Agent 通常还会受到更严格的工具白名单限制，不能据此假设任意递归都可用。

11.2 数据到底共享什么

资源默认普通 Subagent设计意义
父对话全文不共享；调用者必须在 prompt 中交代任务背景。控制上下文成本，避免工具噪声污染父历史。
最终文本报告共享，作为 Agent 工具的 tool_result。父 Agent 负责综合，而不是机械转发子日志。
完整子对话写入 sidechain transcript，可用于查看和恢复。审计与续聊不依赖把全文塞回父上下文。
文件系统与进程默认同进程、同 cwd、同文件系统。便于真实编码，但并行写同一文件仍有竞争风险。
工具权限继承 canUseTool 入口，但应用子 Agent 的工具集合、模式与避免弹窗规则。委派不会绕过内部工具的权限检查。
后台 Task 根状态通过 setAppStateForTasks 写 root store。即使异步子 Agent 的普通 setAppState 被隔离，任务系统仍统一可观测。
Worktree可选；有改动时保留路径与分支。用 Git 工作区解决写冲突，而不是虚构“默认沙箱”。

12设计结论与源码索引

可以提炼出的六个设计结论

  1. Agent Loop 是消息状态机，不只是 while + API。它还要保证 tool_use/tool_result 配对、消息顺序、Abort 清理和上下文可恢复。
  2. 流式输出与流式工具执行是两件事。前者让 UI 更快看到 token；后者让安全工具在模型还没说完时就开始执行。
  3. Subagent 是工具化委派。父 Agent 不需要知道子 Loop 细节，只面对一个符合工具协议的任务原语。
  4. 同步与异步是两种结果回传协议。同步返回最终 tool_result；异步先返回启动句柄，再以通知形成新的模型输入。
  5. 上下文隔离和执行隔离必须分开讨论。Fresh context、Fork cache 共享、Worktree、Remote 是不同维度，不能都叫“独立 Agent”。
  6. 并发安全是工具自己的声明。AgentTool 标记可并发，通用调度器便复用同一套并行机制，无需为 Subagent 特制一套平行调度系统。
