1. 这套系统是什么

claude-science 桌面应用(内部代号 operon)的 artifacts 不是 claude.ai 云端那套 —— bundle 中不存在 create_file / present_files / wiggle 等云端机制,也没有 /api/organizations/.../artifacts 这类端点。它是一套纯本地的 artifact 系统:

  • 本地 Fastify HTTP 服务:所有 artifact 操作走 /api/... 路由,WebSocket /api/ws 推送变更事件;
  • 本地 SQLite:元数据存 operon-cli.db(drizzle ORM);
  • 本地磁盘目录:文件字节存 <数据目录>/artifacts/...。

所以"文件在服务器上能访问"里的"服务器",就是这个内嵌的本地 API 服务。

💡
数据目录定义在 03-decoded/0038.js:533-534:db_path = <dir>/operon-cli.db,artifact_storage_path = <dir>/artifacts。Artifact Store 实例化于 03-decoded/1856.js:274。

核心概念只有一个:frame。frame 是消息/会话单元,root_frame_id 就是会话(conversation)id —— bundle 里没有 conversation_id 这一列,broadcastToConversation(root_frame_id, ...) 等用法可佐证(03-decoded/0871.js:1094)。

2. 两层存储: Workspace vs Artifact Store

理解整套系统的关键:生成文件会经过两个层级,只有进入第二层才会出现在 artifacts 面板。

Layer 1 — Workspace(会话临时区,不入库)Ephemeral

代码执行(analysis 工具 / kernel-exec)产生的文件,先写到按 frame 隔离的 workspace 目录:

<workspaceBase>/<frameId>/...        // 03-decoded/0183.js:130

系统提示里写得非常直白(03-decoded/0195.js:160):

"Workspace files are ephemeral. bash/python/r write to a task-scoped
workspace ... nothing persists until save_artifacts. ... prior work is
found in the artifact store, not by searching the filesystem —
earlier sessions' outputs are not in your workspace."

没经过提升的文件永远不会出现在 artifacts 面板里,但它确实存在于磁盘上、也能被执行环境继续访问。

Layer 2 — Artifact Store(持久层,入库)Persistent

只有调用 save_artifacts 工具(或被自动提升)的文件才落到这里:

<数据目录>/artifacts/<projectId>/<artifactId>/v<versionId前8位>_<文件名>
  • 路径构造:03-decoded/0187.js:9-46(_projectPath / _versionPath);
  • 文件字节在磁盘,元数据在 SQLite 的 artifacts / artifact_versions 表;
  • 归集单位是 project(NOT NULL 外键、级联删除),conversation 只是出处记录。
代码执行 (analysis / kernel-exec) │ ▼ 写入 ┌─────────────────────┐ save_artifacts / 自动提升 ┌──────────────────────┐ │ Workspace (临时) │ ───────────────────────────▶ │ Artifact Store (持久)│ │ <base>/<frameId>/ │ │ 磁盘 + SQLite 元数据 │ │ 不入库、面板不可见 │ ◀── 未提升则永远停留在此 │ 面板可见、版本化 │ └─────────────────────┘ └──────────────────────┘

3. 数据模型 (SQLite Schema)

Drizzle schema 在 03-decoded/0110.js:302-420。注意 每条 artifact 同时挂在 project 和 conversation 两层之下,不是二选一:

artifacts {
  id, filename, created_at,
  project_id     NOT NULL → projects.id (onDelete: cascade),  // 所有权的硬边界
  root_frame_id  NOT NULL,        // 会话归属 (= conversation id)
  frame_id,                       // 具体产生它的消息 frame
  latest_version_id,
  is_user_upload,                 // 用户上传而非 agent 生成
  is_branch_mint,                 // 从旧会话"分支"过来的副本
  is_ephemeral,                   // 临时产物,所有列表查询都排除
  consumed_at, folder_id, priority, superseded_by_artifact_id
}
// 索引: ix_artifacts_conversation_priority (project_id, root_frame_id, priority)

artifact_versions {
  artifact_id, version_number, frame_id,
  content_type, size_bytes, checksum (sha256), storage_path,
  is_intermediate,                // 依赖提取自动提升的中间产物
  producing_cell_id, cell_sources, is_checkpoint,
  parent_version_id, agent_name, language
}
  • 同 (project, frame) 下同名文件 = 同一 artifact 的新版本(findByProjectFrameAndFilename,0131.js:56-73);跨会话同名则是独立 artifact;
  • 还有血缘追踪:artifact_versions.dependency_mappings + artifact_dependencies 表(0491.js:463-483),用于跨会话追溯文件依赖;
  • reference artifact:不落盘、指向 host 授权路径、带 drift 检测(0187.js:180-242)。

4. 产物写回的三条通道

a. 显式保存 — save_artifacts 工具(主通道)主通道

暴露给模型的工具(03-decoded/0491.js:46-241),参数 files(相对 workspace 或注册 local-repo root 的路径)、language、version_of、checkpoints。handler 逐个校验路径 containment(workspace 逃逸直接拒绝),然后:

  • 文本类 → artifact_service.save_artifact(...)(支持 {{artifact:...}} 引用重写,0183.js:436-449);
  • 其余 → save_artifact_from_path(...)(0183.js:450-477);
  • 写盘统一走 _saveArtifactCommon(0187.js:47-169)。
b. 自动收集 — 执行后扫描 + auto-view隐式
  • 执行前后对 workspace 做 scanWorkspace + diffFiles 得出 filesWritten,写入 execution_log(0183.js:253/295,0335.js:2791-2819);
  • 新生成的图片走 auto-view,作为 vision block 注入消息流(0865.js:1245-1266);
  • 依赖提取:代码执行中读到的文件被 auto-promote 为 is_intermediate: true 的 artifact(0496.js:734-742,日志前缀 [dependency-extraction] auto-promote)—— 入库了但默认被面板过滤,这是"查不到"的常见来源。
c. 用户上传 — 分块上传 API手动

POST /api/artifacts/upload/init → /chunk (multipart) → /finalize(sha256 校验),chunk 暂存 staging,finalize 后 save_user_upload_streaming 入库并标 is_user_upload=true(路由 vendor/powershell-utils/0048.js,服务 1855.js:108-136)。

每次保存都会通过 WebSocket 广播 artifact_created 事件(0885.js:26-49),Agent 侧 _processCodeArtifacts 更新 session 列表、持久化 lineage、记录 cell provenance(0865.js:1474-1533)。另有 artifact_deleted / renamed / moved / priority_update 事件。

5. 查询接口与前端面板过滤条件

列表查询存在两种粒度,这是理解"查不到"的关键:

端点粒度实现
GET /api/projects/:pid/artifacts project 级,含该项目所有会话的产物 2457.js:129-143 → listForProject(0131.js:99-110)
GET /api/projects/batch/artifacts 多 project 批量 2457.js:172-184
GET /api/frames/:root_id/artifacts 单会话级,按 root_frame_id 过滤 vendor/powershell-utils/0017.js → listForConversation(0131.js:176-181)

会话面板(前端 artifacts 面板的数据源)的过滤条件是:

// 03-decoded/0131.js:176-181

  let conds = [
    eq(artifacts.projectId, projectId),

    eq(artifacts.isEphemeral, false),
  ];
  if (opts.excludeIntermediateVersions)
    conds.push(eq(artifact_versions.isIntermediate, false));  // ← 默认排除中间产物
  ...
}

路由里 exclude_intermediate 默认 true(传 ?exclude_intermediate=false 才能看到中间产物)。Agent SDK 侧同理:host.artifacts(frame_id=…) 按会话查,只传 project_id 按项目查,都不传则全局搜索(0791.js:96-108)。

6. 为什么文件"生成了却查不到"

典型症状:在 project 的某个 session 里生成了文件,文件能访问(在磁盘/执行环境里),但 artifacts 面板里没有。按可能性排序,有三种根因:

① 最常见 文件没走 save_artifacts,一直停在 workspace

代码执行写完文件如果不显式调用 save_artifacts,文件就只是 workspace 里的临时态 —— 没入库,任何 artifacts 接口都查不到,但磁盘上真实存在、可被后续执行读取。这完全吻合"找不到但又能访问"的现象。

② 次常见 被自动提升成了 intermediate,被默认过滤

依赖提取会把执行中读到的文件自动入库,但标 is_intermediate: true;会话面板默认 exclude_intermediate=true 把它们滤掉。用 ?exclude_intermediate=false 再查一次即可验证。

③ 跨会话场景 文件是上一个 session 产的,root_frame_id 对不上

新 conversation = 新 root frame id,旧 artifact 的 root_frame_id 仍指向旧会话,会话级列表自然为空。这是设计使然,不是数据丢失:

  • 旧文件仍属于 project,project 级视图(/api/projects/:pid/artifacts、Files 面板、batch 接口)都能看到;
  • 新会话的 agent 可通过 host.artifacts(search=…) 跨会话找回,再 read_file(version_id=…) 读取 —— 系统提示专门教模型这么做;
  • 要在新会话"拥有"该文件,需显式分支:copy_artifact 以 is_branch_mint: true 创建新行(0885.js:225-243),UI 对应 "Branch in new session"。

7. 排查手册

# 1. 直接看磁盘,确认文件在 workspace 还是 artifact store
ls <数据目录>/artifacts/<projectId>/

# 2. 查 SQLite,看有没有入库、标记是什么
sqlite3 <数据目录>/operon-cli.db \
  "SELECT id, filename, root_frame_id, is_ephemeral
   FROM artifacts WHERE project_id='<pid>';"

# 3. 带上 intermediate 再查一次会话接口
curl "http://localhost:<port>/api/frames/<root_id>/artifacts?exclude_intermediate=false"

# 4. 按 project 级查(跨所有会话)
curl "http://localhost:<port>/api/projects/<pid>/artifacts"

判定逻辑:

  • artifacts 表无对应行、磁盘 workspace 里能找到 → 情况 ①,走 save_artifacts 提升即可;
  • 表里有行但 is_intermediate=true → 情况 ②,面板过滤问题;
  • 表里有行但 root_frame_id 是旧会话 → 情况 ③,用 project 级视图或 branch。

8. 附: 与 claude.ai 云端的区别

维度claude.ai 云端claude-science (operon)
产物工具create_file / present_filessave_artifacts + 执行后自动扫描
存储云端(wiggle 等内部服务)本地磁盘 + 本地 SQLite
归集维度organization / conversationproject(硬边界)+ root_frame_id(出处)
API/api/organizations/...本地 Fastify /api/projects/... /api/frames/...

另外,bundle 里确实存在 Anthropic /v1/files API 客户端(0149.js,带 anthropic-beta: files-api-2025-04-14 头),但它只用于把 PDF/图片作为模型输入上传(0490.js:130-155),与产物存储完全无关。

📌
一句话总结:operon 的 artifact = 本地 project 级文件仓库;workspace 是会话临时草稿区,save_artifacts 是把草稿"发表"进仓库的唯一显式入口;面板按 (project, root_frame_id, 非 ephemeral, 非 intermediate) 过滤展示。文件"查不到"几乎都是卡在这四个过滤条件之一上,而不是丢了。
