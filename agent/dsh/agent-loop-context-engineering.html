01一次请求的三路合体

DSH 发给模型的从来不是一坨拼接的 prompt 字符串，而是结构化请求：messages 与 tools 两个平级字段，加上调用配置。三路原料各管各的：

 原料一：系统提示             原料二：消息历史            原料三：工具信封
 ─────────────────           ─────────────────          ─────────────────
 ctx.systemPrompt 服务         会话日志「对话抽屉」         会话日志「信封抽屉」
 多个插件各贡献一段：          surface 折叠派生：           request/header 快照
 · 基础人设 / 工具规则         system / user /             （调用配置 + 完整
 · 技能目录卡片                  assistant / tool              工具 schema 全集，
 · 端砚这类插件想加的             消息依次产出                只在变化时追加）
        │                          │                          │
        ▼ 渲染成 system 消息         ▼                          ▼ 取最新一份
        └────────────┬──────────────┴──────────────────────────┘
                     ▼
        一次 API 请求 = messages + tools + 调用配置
                     ▼
            经 LLM 适配器翻译方言 → HTTP 发出
核心认知：系统提示是「插件拼装」的（所以装了新插件模型会"知道"新能力）；历史是「日志派生」的（从不单独存储）；工具清单是「快照取最新」的（变化才记账）。三路在请求组装那一刻合体。

02接口实物：请求长什么样，走哪种方言

以「委派过一次远程 agent」的会话为例，第 2 轮发出请求的骨架：

{
  messages: [
    { role: "system",    content: "你是…助手。工具使用规则… ← 系统提示也是一条消息" },
    { role: "user",      content: "帮我用 MolClaw 分析这个蛋白" },
    { role: "assistant", tool_calls: [                    ← 模型点菜：assistant 消息自带
        { id: "call_1", name: "subagent_a2a",
          arguments: "{\"agent\":\"MolClaw\",\"objective\":\"…\"}" } ] },
    { role: "tool", tool_call_id: "call_1",               ← 菜上桌：每个调用一条
      content: "MolClaw 的分析结果…" },                     tool 消息，靠 id 配对
    { role: "assistant", content: "根据分析，这个蛋白…" },
    { role: "user",      content: "再搜一下相关文献" }
  ],
  tools: [ 10 个工具的三行式 schema（见第 3 节） ],
  …调用配置（模型名 / 温度 / 推理强度）
}

两套方言并存，DSH 的 DeepSeek 官方路线走 Anthropic 那套

OpenAI Chat Completions（行业普通话）Anthropic Messages（DSH deepseek 官方路线）
端点POST /chat/completionshttps://api.deepseek.com/anthropic + /v1/messages
工具字段tools:[{type:'function', function:{name, description, parameters}}]tools:[{name, description, input_schema}]，system 为顶层字段
谁在用vLLM / Ollama / 各家网关普遍仿它DSH 的 llm-deepseek 适配器（多 provider 另有 dsh-llm-pi-ai）

「兼容」永远打折：DeepSeek 有自家私货——顶层请求扩展字段（dsh-deepseek-llm-api-extensions 包当登记处）、图片走 Files API、deepseek-flash 的 systemPromptUpdate: in-history 语义。适配器 README 原话：模型收到系统提示、消息历史、工具 schema、调用配置，适配器不添加任何自撰的提示词（without adapter-authored prompt prose）。

对插件作者意味着：只写一遍 ToolSchema，方言差异全被适配器层吃掉——端砚的工具在任何 provider 上一行 if 都没写就都能用。

03Tool List 是怎么嵌进去的

从注册到模型眼前，五步只换格式不换内容——自始至终只有三样东西：name / description / parameters。

 插件侧                     框架侧                        provider 侧
 ────────────────          ─────────────────────         ─────────────────────
 ctx.tools.register          注册表 schemas()               收到 JSON 的 tools 字段
 (defineTool({…}))    ──►    白名单投影：只放行三样，    ──►   按聊天模板渲染成
   execute/render/             execute 等绝不外泄                token，塞进模型输入
   presentCall 留在本地                                                                        │
                                                          模型读清单 = 读普通文本
                                                                                              ▼
                                                    模型生成 tool_calls（结构化返回，免正则解析）

线上实物（以 subagent_a2a 为例）

"tools": [{
  "type": "function",
  "function": {
    "name": "subagent_a2a",
    "description": "Delegate one objective to a remote A2A agent…
                    Available agents:
                    - MolClaw —— 蛋白结构分析      ← describeTool 写的广告词
                    - ep-agent —— …",                   逐字抵达模型眼前
    "parameters": {
      "type": "object",
      "properties": {
        "agent":     { "type": "string", "enum": ["MolClaw", "ep-agent", …] },
        "objective": { "type": "string" }
      },
      "required": ["agent", "objective"]
    }
  }
}, … × N 个]
工具清单的三个身份：① 独立字段——与 messages 平级，不占对话历史；② 上下文的一部分——provider 渲染成 token，每次请求都全量重发、全量计费，哪怕一个工具都没被调用；③ 可缓存前缀——内容稳定时通常命中 prompt cache（账单没有看起来那么恐怖）。

token-meter 插件把上下文压力分三块单独统计：systemTokens / toolsTokens / messageTokens——工具清单独占一块，白纸黑字可查。DSH 内部类型 GenerateOptions.tools 的注释也点明：「适配器把它映射到 provider 的 tools 字段」。

04token 账本：每一轮都在为全部历史付费

轮次这次请求带什么input token =
第 1 问[系统提示, 你的第1条] + tools系统 + 工具清单 + 第1条
第 2 问[系统, 第1条, 回复1, 第2条] + tools上一行全部 累计 + 第2条
第 3 问[系统, …全部往来…, 第3条] + tools再累计……
  • 每次请求的上下文 = 系统提示 + 工具清单 + 此前全部对话 + 新消息，token 加总计费；输出 token 另算。
  • 有一类请求不等你说新话：工具结果回填后立刻追加一次请求让模型消化结果——「它自己连续干活」的体感来源。
  • 对话越长越贵的直接推论 → DSH 的 compaction 子系统（压缩：遮蔽旧事换摘要）与 token-meter 的 contextPressure / projectedTokens（下一请求的预估成本）都是为这本账服务的。

05谁在选工具：框架摆菜单，模型点菜

        ┌─────────────────── 一个 step ───────────────────┐
        │ 1. ctx.tools.resolve()  问一次 when 条件/作用域     │
        │    → 本步候选名单（可远小于注册总量）                 │
        │ 2. 组装请求：候选 schema 进 tools 字段               │
        │    request/header 落日志（信封记账）                  │
        │ 3. 发给模型 ═══► 模型生成中 = 读清单 + 挑 + 填参数  │
        │    框架代码在此刻不做任何匹配/打分              │
        │    输出二选一：纯文本 → 轮次结束                       │
        │              tool-call 批次（可并行多个）             │
        │ 4. 框架此刻才动：validateArgs 兜底 → execute          │
        │ 5. 结果回填日志 → 模型看见自己点的菜 → 下一个 step     │
        └─────────────────────────────────────────────────┘
        收敛条件：模型不再点菜（不是超时）
语义选择是模型训练出来的能力：选择好坏几乎完全取决于 description 写得好不好。端砚把 roster（每个 agent 的名字+一句话职责）织进 subagent_a2a 的描述、再把 agent 参数做成 enum——不是文档行为，是在做路由设计：把「N 个工具里挑一个」降维成「填一个下拉框」。

06万一工具有一万个：四道闸门 + 一条旁路

实测锚点：ToolUniverse 一个 SCP 服务器 1894 个工具，全量挂载 schema 下发 ≈ 450K tokens（端砚验证记录）——线性外推一万工具 ≈ 240 万 tokens，任何窗口都爆。但爆的位置是「每步请求投影」，不是「安装」：

 闸门1【安装】 1w 个插件进 profile —— 花磁盘，不花上下文
 闸门2【注册】 端砚：添加 ≠ 挂载；勾选白名单 selectedTools 才 register
 │             上限 maxToolServers=8 · maxSelectedTools=128（可配）
 闸门3【每步解析】 harness 原生：ctx.tools.resolve() 按 when 条件/作用域
 │             出本步候选名单，名单外根本不进请求
 闸门4【模型点菜】 只有候选的三样 schema 抵达模型
 ─────────────────────────────────────────────────────────────
 旁路【skills】 为海量能力而生：目录卡片（名+一句话）进上下文，
               正文 SKILL.md 按需作为一条 user 消息注入，平时零 token

顺带揭开一个朴素真相：技能正文、文件变化通知、AGENTS.md 这些「注入上下文」，在请求里都是伪装成 user 消息出现的——日志层用 source 字段区分三种来源（人话 / 注入 / 续轮），模型侧看都是用户消息。

07日志视角速览：为什么组装是纯函数

 会话日志（唯一真源 · 仅追加 · seq 连续）
 ├─ 对话抽屉：system / user / assistant / tool 消息   ──派生──► messages
 │    （surface 折叠：被"替换/遮蔽"的旧事件不再出现，
 │      但日志里原样保留，供审计与人类转录）
 └─ 信封抽屉：request/header 快照                     ──取最新──► tools + 调用配置
      （initial / resume / change / series 四种时机才追加，
       未变沿用——聊一百轮只有一两份快照）

 回放 = 从同一组事件重新派生 ⇒ 每个请求都是日志的纯函数
  • 「更正 / 压缩 / 换提示词」全部表达为一次追加（surfaceOp: append / replace），日志永不被改写；
  • 失败与重试的模型尝试走 assistant/attempt（纯日志行），不污染模型可见历史；
  • 子代理 fork 的 seed = 父日志「已完成轮次前缀」——同样的派生机制换个起点而已。

08源码地图

agent-loop（循环本体）

packages/core/agent-loop/src/index.ts（driver，838 行）· agent.ts（Agent 约定，751 行）· inbox.ts（排队与插话）。扩展插件只依赖 agent 抽象，绝不直接依赖 agent-loop——循环本身可整体替换。

session（日志）

packages/core/session/src/types.ts（事件词汇表 574 行）· index.ts（append/派生）。文档 docs/subsystems/session.zh.md。

tools（注册表）

packages/core/tools/。要点：schemas() 白名单投影、resolve() 每步候选、when 条件注册。文档 docs/subsystems/tools.zh.md。

llm（方言层）

packages/llm/llm-deepseek/（官方 Anthropic 方言端点）· dsh-llm-pi-ai（多 provider）· deepseek-llm-api-extensions（私货登记处）。文档 docs/subsystems/llm-streaming.zh.md。

token-meter（账本）

packages/llm/token-meter/：systemTokens / toolsTokens / messageTokens 三块拆账 + cacheReadTokens + contextPressure。

实测样本

dsh-plugin-inkstone：subagent_a2a 的 describeTool 广告位、selectedTools 白名单、verification.md 里的 1894 工具 ≈ 450K tokens 实测。

一图流收口：messages 管「发生过什么」（日志派生），tools 管「现在有什么菜」（信封快照），system 管「你是谁+规矩」（插件拼装）；框架摆菜单，模型点菜，agent 炒菜，日志记账——每一步请求都是这本账的纯函数快照。
