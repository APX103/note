01先建立整体认识

DSH 的 Subagent 不是另一套 Agent 执行引擎，而是一套可插拔的后台委派与生命周期管理系统。真正执行模型请求和工具调用的，仍然是普通的 Agent、AgentLoop 与 Session。

Subagent = 既有 Agent 执行能力 + 委派管理 + 可替换运行后端

父 Agent 启动子 Agent 后，不必停在工具调用里等待最终答案。子 Agent 独立运行；完成后，运行时把结果通知直接创建者。程序调用方也可以显式等待结果 Promise。

最重要的阅读抓手
先分清“谁发起委派”“谁管理生命周期”“谁提供运行方式”。其余 preset、消息、目录、恢复和清理，都是围绕这三类角色展开的。

02工具、服务与 Provider：三层分工

packages/subagent 是一个包组，而不是单个实现。它将模型入口、统一管理与运行后端拆开。

图 1 · 从模型工具到实际执行

父 Agent 的模型决定何时委派、委派什么任务
↓
工具层tool-subagent：启动；tool-subagent-control：消息、列表、中断、等待
↓ ctx.subagents
服务层：SubagentRuntime + SubagentManager能力与深度检查、容量、创建、恢复、消息、结果、取消、目录和清理
↓ 按 provider 名称路由
本地 Providerspawn / fork → prepareContinuable()
外部 ProviderACP / DSH SDK / Codex / Claude Code → start()
↓
普通 DSH Agent + AgentLoop独立子 Session，可继续对话
另一个进程或外部产品一次执行，返回 SubagentRun
CONSUMER

工具只负责入口

把模型参数翻译为 startActivation() 请求，不自己管理子 Agent 生命周期。

SERVICE

Manager 负责难事

统一处理准入、所有权、并发、消息、结算、容量和资源释放。

PROVIDER

后端负责差异

决定全新还是继承历史、同进程还是外部产品，以及如何开始执行。

03Session、Agent、Activation：不要混为一谈

持久档案

Session

保存消息、工具调用和领域事件。可以落盘、重开和继续，是子 Agent 的持久身份与历史。

在线执行者

Agent

内存中的工作状态。接收输入、调用模型、执行工具，并维护当前轮次与收件箱。

一次在线期间

Activation

一次驻留或外部执行的管理记录，包含运行句柄、结果 Promise、容量槽与清理状态。

图 2 · 一个 Session，可以有多次 Activation

同一个子 Session：reviewer ────────────────────────────────────────────────────────→ 时间 Activation #1 Activation #2 创建 从持久 Session 冷恢复 │ │ ├─ 执行任务 A ├─ 执行任务 B ├─ 空闲 ├─ 空闲 └─ 释放内存中的 Agent └─ 再次释放 │ │ └────── Session 始终保留，对话可继续 ───┘
一句话记忆
子 Agent 不在内存里，不代表它的 Session 消失。Activation 结束释放的是一次在线执行；本地子 Session 仍可被列举、恢复并接收新任务。

04一次委派，从工具调用到完成通知

以本地 spawn 为例。工具返回名称和子任务最终完成，是两个完全不同的事件。

图 3 · 委派时序

父 Agent 委派工具 Runtime / Manager 子 Agent │ │ │ │ │ 1. 调用 subagent │ │ │ ├───────────────────▶│ 2. startActivation │ │ │ ├─────────────────────▶│ │ │ │ │ 3. 检查权限/深度/容量 │ │ │ │ 4. Provider 准备数据 │ │ │ │ 5. 创建 Session + Agent │ │ │ │ 6. 初始任务进入 inbox │ │ │ │ 7. 写目录并发 start 事件│ │ │ ├──────────────────────▶│ │ 8. 返回子代理名称 │◀─────────────────────┤ │ │◀───────────────────┤ │ │ │ │ │ │ 9. 独立执行 │ 继续做别的，或先 │ │ │ 模型/工具循环 │ 结束当前轮次 │ │ │ │ │ │ 10. 空闲且无待处理输入 │ │ │ │ 11. 取结果并释放资源 │ │ 12. 收到完成通知 │ │ │ │◀──────────────────────────────────────────┤ │ │ │ │ 13. 发 end、交付 result │ ▼ ▼ ▼ ▼
  1. 启动确认不是任务结果started subagent reviewer 只说明子任务已创建，初始输入已被收件箱接受。
  2. 父 Agent 可以继续工作多个独立委派可以并行启动。只剩等待时，父 Agent 可以结束本轮，不必轮询。
  3. 完成通知可以唤醒父 Agent父级忙时通知成为后续输入；父级空闲时可由通知开始新一轮。
  4. 结果交付发生在清理之后Manager 提取输出、释放句柄和容量、发送通知、发布结束事件，再完成结果 Promise。

05spawn、fork 与外部后端

假设父 Session 已有完成轮次 A、B，当前正在执行调用委派工具的轮次 C。

图 4 · 子任务拿到的初始内容

父 Session： [已完成 A、B] [正在执行 C：调用 subagent] spawn 子 Session： [新的任务提示词] 不复制 A、B，也看不到 C fork 子 Session： [复制的 A、B] [新的任务提示词] 不复制尚未完成的 C 外部 Provider 外部运行时： [自包含任务] 一次执行，返回最终文本或安全诊断
后端父级对话历史独立垂类 preset后续消息与冷恢复适用场景
spawn不继承支持支持独立、角色明确的本地子 Agent
fork复制创建时的已完成轮次不支持，继承父组合支持审查、延续、基于既有对话的分析
ACP / SDK / Codex / Claude Code不进入父级对话由子运行时自身配置当前共享路径不支持进程隔离或外部产品能力

本地 Provider 的代码很短，是因为它们只贡献初始 seed：spawn 不提供历史，fork 找到最后一个 turn/end 并复制此前缀。创建、消息、恢复和清理仍由 Manager 统一负责。

fork 是创建时的一次性快照，不是持续同步；复制历史也不等于复制父 Agent 的全部局部权限与工具状态。

06有 Agent Team，但没有独立的 Swarm 调度系统

Subagent 能形成类似 Swarm 的执行结构：多个兄弟并行、子级继续嵌套、同树成员发消息。但它本身不负责自动拆解任务、自动选人、自动负载均衡或全局黑板。

Agent Team = Subagent 树 + 根 Session 上的共享任务板
SUBAGENT 已提供

执行与通信树

  • 创建和并行执行
  • 嵌套委派
  • send_message 与 list_agents
  • 等待、中断、恢复和生命周期管理
TEAM 额外提供

共享任务协调

  • 任务 owner 与认领、完成、释放
  • Lead 重新分配
  • blockedBy 任务依赖 DAG
  • writeScopes 文件重叠提示
Team 不会自动驱动流水线
任务依赖完成后，后继任务只会变为 ready，不会自动启动或唤醒 owner。需要成员行动时仍要显式 send_message。Team 默认关闭；共享目录不等于独立 worktree，write scope 也不是文件锁。

Team 的成员身份、消息和生命周期仍由 Subagent 拥有，对应实现位于独立的 packages/team，不是另一套 Agent 运行时。

07一个具体的调用树：创建向下，结果向直接父级回流

假设 Lead 同时委派调研和实现，调研 Agent 又委派事实核查：

图 5 · 创建关系与模型可见名称

lead（深度 0） │ ├─ researcher（深度 1） │ └─ fact-checker（深度 2） │ └─ implementer（深度 1） 模型可见名称： lead researcher researcher/fact-checker implementer

执行与结果顺序

  1. Lead 同时启动 researcher 和 implementer两次委派可重叠执行，启动工具本身支持并发。
  2. researcher 启动 fact-checker前提是它拥有委派工具，并且深度上限允许第三层 Agent。
  3. fact-checker 完成通知直接创建者 researcher，不会自动越级通知 Lead。
  4. researcher 汇总后完成它的最终回答通知 Lead；implementer 完成时也独立通知 Lead。
  5. Lead 汇总收齐完成用户请求所需的结果，再生成最终答案。
创建方向：lead ──▶ researcher ──▶ fact-checker
通知方向：lead ◀── researcher ◀── fact-checker

名称描述的是创建关系。同一棵树的本地可继续成员仍可用 send_message 联系其他成员，消息路由不会改变这棵树。

08“链式调用”其实有三种

嵌套创建

A 创建 B，B 创建 C

本地后端支持。子级需要看到委派工具，并且 maxDepth 必须足够。

继续同一个 Agent

多次给 B 新任务

本地子 Agent 完成后，可通过 send_message 冷恢复原 Session，保留历史。

固定流水线

A 输出自动成为 B 输入

没有内置自动 pipeline 运算符，需要模型、工作流或 Team 任务与显式消息共同编排。

嵌套深度怎么计算

maxDepth: 0   不允许委派
maxDepth: 1   lead → child
maxDepth: 2   lead → child → grandchild
maxDepth: 3   再允许向下一层

默认 maxDepth = 1，所以默认只允许直接子代理。深度写入子 Session 元数据，冷恢复不会把它重新算成顶层。整棵树还共享 Activation 容量，默认最多 8 个在线或正在创建的后代，根不占名额。

如果采用程序工作流，可以等待一个 Activation 的 result，再显式启动下一个；如果使用 Team，可用 blockedBy 表达依赖，但仍需显式执行。

09为什么结束后还能找到并唤醒子 Agent

系统同时维护“持久成员目录”和“进程内驻留表”，它们回答不同问题。

持久目录

父 Session 的 catalog

subagent/catalog 事件记录直接子级身份、模式、标签和名称。它回答“这个父级创建过谁”。

在线状态

Manager.resident

进程内 Activation 表回答“谁现在驻留在内存中”，包括本地 Agent 和外部执行。

图 6 · 后续消息的投递路径

send_message({ agent: "reviewer", message: "再检查一个问题" }) │ ▼ 名称解析 + 同树权限检查 │ ┌──────────┴──────────┐ ▼ ▼ 子 Agent 在线 子 Agent 不在线 │ │ 消息进入 inbox 从持久 Session 恢复目标 │ │ 下一步或下一轮处理 再投递消息

list_agents 从根的 catalog 递归读取，不必唤醒所有 Agent。因此已释放的本地子 Agent 仍可显示为 inactive。外部执行是叶子，没有本地子 Session 可继续遍历。

send_message 返回的 messageId 只是收件确认，不是对方回复；只恢复目标，不会连带恢复所有创建祖先。

10源码阅读顺序：沿一条主线跳读

不要从一千多行的 manager.ts 第一行顺序读到最后一行。先建立主路径，再补异常、冷恢复和清理分支。

  1. 先看最简单的 Provider
    packages/subagent/subagent-spawn-in-process/src/index.ts
    packages/subagent/subagent-fork-in-process/src/index.ts
  2. 看公共请求、结果与 Provider 接口
    packages/subagent/subagent/src/types.ts
  3. 看模型工具如何启动 Activation
    packages/subagent/tool-subagent/src/index.ts 的 execute()
  4. 沿 Manager 的主方法跳读
    startLocal() → startExternal() → materializeTracked() → watchLocalSettlement() → finishDisposal() → deliverToMember()
  5. 最后看通信、目录与测试
    continuation-messages.ts、catalog.ts、tool-subagent-control，以及 continuation、并发和 settlement 测试。

读完只需先记住四句话

  1. 工具只负责发起，Manager 统一管生命周期。
  2. Provider 决定后端差异，本地 AgentLoop 仍是真正执行者。
  3. Session 让本地子 Agent 跨多次 Activation 继续对话。
  4. 调用树表达创建关系；Team 在同棵树上增加共享任务板。
