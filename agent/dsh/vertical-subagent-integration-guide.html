01统一委派接口，不要强行统一成 ACP

本地 DSH、进程外 DSH、ACP Agent、Codex、Claude Code 和远程 A2A Agent，都可以挂在 ctx.subagents 后面；但它们不需要、也不应该都经过 ACP。

ACP

客户端如何驱动 Agent

Agent Client Protocol 主要描述会话、提示词、取消、权限和语义更新，适合编辑器或自动化客户端连接 Agent。

官方协议仓库

A2A

独立 Agent 系统如何协作

Agent2Agent Protocol 面向能力发现、任务、消息、状态与 Artifact，适合跨服务、跨组织的 Agent 互操作。

官方协议规范

统一任务与结果 · 统一生命周期 · 按后端保留传输和能力差异
不要追求虚假的一致性
跨后端的最低公分母通常是“自包含任务输入 + 最终文本输出 + 停止原因”，不是原始思维链、私有 reasoning、内部工具事件或 Cordis 对象。

02先定义“垂类 Agent 包”，不要先写 Provider

以合同审查 Agent 为例，先确定与传输无关的领域资产。它们应当可版本化、可评测，并能被不同运行适配器复用。

图 1 · 与传输无关的垂类资产

合同审查 Agent │ ├─ 输入：合同内容或文档引用、法域、审查重点、调用方上下文 │ ├─ 输出：总体结论、风险项、原文证据、修改建议、无法确认事项 │ ├─ 领域能力：文档读取、条款检索、法规检索、证据校验 │ ├─ 行为约束：不编造依据、结论带证据、权限不足明确报告 │ └─ 评测：漏报/误报、无证据拒答、取消超时、schema 校验
任务契约

输入与输出

明确必填字段、文档引用方式、输出结构、证据要求和 Artifact 归属。

能力契约

工具与权限

定义领域操作、只读或写入范围、输出上限、取消和失败语义。

质量契约

固定评测集

用同一批任务衡量各后端，不以“最终回答看起来合理”代替验证。

如果共享工具需要跨 DSH、Codex 和 Claude Code 使用，可以把领域操作实现为 MCP 服务。MCP 共享的是工具入口，不会自动统一各产品的权限、模型行为或内部推理。

通用 tool-subagent 已经是一个 Consumer。如果通用 prompt 参数足够，可直接复用；如果模型需要填写 documentId、jurisdiction、reviewType 等领域字段，就新增自己的 Consumer 工具。

传输选择尽量属于部署，而不是模型
同一垂类能力最好用稳定的领域工具名。当前 tool-subagent 一个实例绑定一个 Provider；需要动态路由时，应由自定义 Consumer 或部署配置决定，而不是让模型理解 ACP、SDK、A2A 的实现差别。

04本地 DSH：优先使用 spawn + 独立 Agent Preset

这是成本最低、能力最完整的方案，不需要 ACP。适合共享 Host 服务、后续消息、冷恢复、结构化输出和 DSH 原生工具管线。

  1. 实现垂类提示词插件提供角色、必要约束和按需加载的领域说明；关键权限与破坏性操作约束应靠近相关工具。
  2. 实现垂类工具插件使用明确的输入/输出 schema，返回有界结果、证据或引用，避免把整个检索语料塞进模型。
  3. 声明独立 preset把提示词、工具、技能和控制工具组合为稳定 ID；若服务 Provider 与 Consumer 属于 preset 局部组合，注意共享同一个隔离 realm。
  4. 用 spawn 暴露委派子 Agent 从全新对话开始，任务必须自包含；明确指定垂类 preset。

配置骨架如下，假设基础 profile 已提供 preset registry 和 Subagent 服务：

- id: preset-contract-reviewer
  name: '@deepseek-ai/dsh-agent-preset'
  config:
    id: contract-reviewer
    plugins:
      - name: '@your-org/dsh-contract-prompt'
      - name: '@your-org/dsh-contract-tools'

- name: '@deepseek-ai/dsh-subagent-spawn-in-process'

- name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: spawn
    toolName: contract_review
    agentPreset: contract-reviewer
    maxDepth: 1

这里 maxDepth: 1 允许根创建合同审查子 Agent，但不允许它继续向下委派。

什么时候改用 fork
只有当子任务必须看到父级已完成的对话时才选 fork。fork 不支持独立选择 preset，而是继承父级组合，因此“角色明确、能力独立的垂类 Agent”通常优先 spawn。

05领域工具、垂类 Consumer 与固定内部流程

需要类型化领域参数时，写自己的 Consumer

例如让模型看到以下输入，而不是一段自由文本：

{
  "documentId": "contract-123",
  "jurisdiction": "CN",
  "reviewType": "vendor-risk"
}

Consumer 负责验证引用、构造自包含提示词，再调用 startActivation()。面向模型的后台委派通常使用 delivery: 'parent'；工作流需要直接等待结果时使用 delivery: 'caller'。

“思考流程”应该放在哪里

需求推荐所有者原因
角色、风格、判断原则preset 提示词属于模型需要遵守的领域上下文
条款检索、证据定位等操作领域工具或 MCP输入输出可验证，可被多个运行时复用
必须严格执行的步骤顺序工作流或普通代码不能依赖模型自觉遵守提示词
跨产品最终结果校验父工作流或 Provider不同产品的内部推理不可统一
不要传输原始思维链
统一结果应包含结论、证据、Artifact 引用、状态和安全诊断。需要审计时保存结构化的领域行动与证据，而不是依赖某产品的私有 reasoning 数据。

06外部也是 DSH：SDK 与 ACP 的选择

优先 DSH SDK

需要完整 DSH 对等运行时、独立 profile/patch、模型路由和持久化，但希望进程隔离。

OR

选择 ACP

只希望依赖标准客户端协议，未来可能换成其他 ACP Agent，并接受一次性文本结果。

DSH SDK：完整 Harness 子进程

父 DSH
  │ stdio JSON-RPC
  ▼
子 DSH --profile sdk --patch contract-reviewer.yml
  ├─ 自己的 profile 与 preset
  ├─ 自己的工具与 Session
  └─ 自己的模型路由

垂类组合通过子进程的 profile + patches 安装，不是通过父请求的 agentPreset 传进去。当前 SDK Provider 支持路由选项覆盖，但不支持父级强制 preset、outputSchema 或深度限制；工具侧通常设置 maxDepth: 'provider-managed'。

如果所有外部 Agent 都是 DSH，通常优先 SDK，而不是为了形式上的“统一协议”改走 ACP。

ACP：标准自动化协议

父 DSH
  │ initialize / newSession / prompt
  ▼
dsh --profile acp --patch contract-reviewer.yml

当前 Subagent ACP Provider 每次运行启动新进程，不继承父对话，不支持父级传入 preset、agentOptions、outputSchema 或深度上限，也不接受后续消息。父级只获得最终或部分 assistant 文本和安全诊断。

DSH ACP Server 自身具备会话恢复等能力，不等于当前 Subagent ACP Provider 已把这些能力暴露为可继续 Activation。

07Codex 与 Claude Code：使用原生适配器

DSH 当前实现并非通过 ACP 接入这两种产品：

Codex       DSH Provider → 官方 app-server → 临时 thread → 一个 turn
Claude Code DSH Provider → 官方 Agent SDK → 新 query → 一个结果
CODEX

原生配置是权威

Provider 固定可选模型、环境与权限模式；每次新进程、临时线程和一个轮次。领域能力通过自包含任务、原生配置或 MCP 提供。

CLAUDE CODE

原生设置是权威

Provider 固定可选模型、环境与权限模式；每次独立 SDK query。原生项目/用户设置、MCP 和权限行为仍由 Claude Code 管理。

两者当前共享路径都不支持续接、恢复、父级 outputSchema 或 Harness 深度强制。取消不会回滚已经发生的文件修改或外部副作用。

需要跨产品严格一致时
把共享领域操作放进 MCP，把最终结果验证放在父工作流或自定义 Provider，把严格步骤顺序交给父工作流。不要假设不同产品会有相同的内部执行轨迹。

08真正的远程 A2A：新增独立 Provider

当前 subagent-acp 面向本地子进程和本地 cwd，不能只换一个命令就变成远程 A2A。建议新增 subagent-a2a，第一版只做一次性任务。

图 3 · A2A Provider 主路径

A2AProvider.start(request) │ ├─ 读取 Agent Card，校验能力与认证配置 ├─ ContentBlock[] → A2A Message Parts ├─ 创建远程 Task ├─ 订阅或轮询状态和 Artifact ├─ 映射为 SubagentResult └─ 返回 { id, result, dispose }

第一版能力声明应保守：不支持父级 agentOptions、agentPreset、outputSchema 或深度限制，除非实现真正执行了对应保证。

const capabilities = {
  agentOptions: false,
  agentPreset: false,
  outputSchema: false,
  depthLimit: false,
}

必须单独设计的四个问题

WORKSPACE

远程工作区

远程 Agent 无法直接使用本机路径。选择共享文件系统、上传文档、对象存储引用或远程 workspace ID，不要直接发送本地 cwd 字符串。

RESULT

Task 与 Artifact

定义最终 Artifact 的选择、排序、部分输出、停止原因映射，以及远程终态未知时如何报告。

CANCELLATION

取消确认

dispose() 幂等，发送取消后有限等待；不能把“取消请求已发送”误报成“远程已停止”。

SECURITY

认证与诊断

显式配置凭据，不复制父环境；Artifact 校验大小、类型和完整性；诊断不泄露文档、密钥和原始协议载荷。

Provider 返回的 SubagentRun.result 应把子任务级失败映射为带 stopReason 的结果；启动失败先清理未发布资源。dispose() 需要等待可确认的清理终态。后续消息不要假装支持：当前外部 Activation 路径会按一次性执行处理。

09能力矩阵与公共契约

下表描述当前共享实现的主要边界，不是协议永远无法扩展。自定义 Provider 只能声明它真正执行的能力。

运行方式垂类组合由谁拥有后续对话父请求 outputSchema主要代价/限制
本地 spawn父部署选择独立 preset支持支持共享进程，隔离较弱
本地 fork继承父组合支持支持复制已完成历史，无独立 preset
DSH SDK子 profile + patches当前不支持不支持每次完整 DSH 启动；支持路由覆盖
ACP子 ACP Agent 自己当前不支持不支持新进程与握手；最终文本
Codex / Claude Code各产品原生配置不支持不支持一次性执行；原生设置和认证
自定义 A2A远程 Agent 自己首版建议不支持验证后才声明需自行设计工作区、Task、Artifact 和认证

公共层应该稳定的内容

  • 领域任务输入及其验证规则；
  • 结论、证据、Artifact 引用和停止原因；
  • Activation 的启动、结果、取消和清理语义；
  • 能力检查失败时明确拒绝，不能静默忽略。

如果跨后端必须有机器可读结果，可在自定义 Provider 内验证后声明 outputSchema，或在父工作流中做领域级验证；不要把“提示模型输出 JSON”当成已经执行了 schema 保证。

10验证、安全与可观测性

每个 Provider 都应通过的契约场景

  • 正常完成，返回正确最终输出和停止原因；
  • 启动前取消、启动后取消，以及重复 dispose；
  • 启动失败时已创建的部分资源被清理；
  • 发布后模型、传输或进程失败映射为结果，不丢失已有部分输出；
  • 清理失败与执行结果分开报告，不冒充已经成功停稳；
  • 请求了不支持的能力时，在执行前明确拒绝；
  • 诊断不包含任务内容、凭据、环境值、原始协议载荷和无界日志；
  • 多个兄弟运行同时取消、完成和清理时互不影响。

日志归属

本地子 Agent 的详细历史在自己的 Session；外部子任务的详细轨迹在子进程或远程系统。父级保留 Activation 身份、catalog、生命周期事件和终态结果，不必复制整个子 transcript。

可以用内部遥测关联 DSH runId 与远程 Task ID，但不要把内部关联 ID 当成授权依据。文件与外部系统副作用不会因取消自动回滚，写操作必须单独设计权限和补偿。

11推荐落地顺序

  1. 先把本地 DSH 垂类 Agent 做好独立 preset、只读领域工具、稳定输入输出和固定评测集；严格流程放代码。
  2. 把同一组合迁移到进程外 DSH使用 SDK Provider 和子 profile patch，验证隔离 home、取消、回收、日志归属与启动成本。
  3. 按真实需求增加协议适配器标准本地进程协议选 ACP；需要原生行为选 Codex/Claude Code；跨服务协作再实现 A2A。
  4. 最后增加有证据的丰富能力结构化输出、远程继续会话、进程池和远程工作区都应独立设计，不作为第一版的隐含承诺。

最终建议：一套垂类定义，两个实现层，多个适配器

  1. 垂类定义与评测保持传输无关。
  2. Consumer 统一领域任务，Provider 统一执行生命周期。
  3. 本地 DSH 用 preset，进程外 DSH 用 profile/patch。
  4. ACP、Codex、Claude Code 和 A2A 保留各自真实能力边界。
  5. 共享领域工具可以考虑 MCP；严格流程由工作流拥有。
