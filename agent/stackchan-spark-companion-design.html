📌 摘要

一句话定义：买回来的 M5Stack Stack-chan 桌面机器人只是"身体"，大脑住在一台 DGX Spark 上。它同时扮演两个角色：① 整个 Agent 生态的肉身化身——任何 agent（ZCode、Hermes、cron、任意 MCP 客户端）都能调用它的嘴、脸、舵机、摄像头；② 无唤醒词的桌面伴侣——听得懂"你是不是在跟我说话"，有记忆、有情绪、会主动、不用语音指令管理 session。

三条设计哲学（所有取舍由此推导）

  1. 身体归机器人，大脑归 Spark，中间一条 WiFi。机器人是瘦客户端：麦克风/扬声器/舵机/灯/脸/触摸的执行器，零智能，永远插电。
  2. 机器人的一切能力收敛为一扇门。所有 agent 地位平等，通过同一个入口控制它，谁也不许绕过仲裁者直碰硬件。
  3. 像不像活的 > 聪不聪明。80% 的打磨给 idle 状态和主动性；延迟靠 backchannel（"我看一眼哈~"）和梯度响应（拿不准就只是抬头看一眼）化解，不靠堆参数。

核心结论：大脑（Hermes Agent）、身体（stackchan-mcp）、嘴耳（Pipecat）、全部模型服务都是现成的。真正要写的只有三块胶水，合计约 500 行：Pipecat 自定义 Transport、Pipecat↔Hermes 桥、Ear 受话检测编排环。

融合原则（三条铁律）

  1. MCP 工具和 Pipecat 的 function call 都是同一个 BodyGateway 的薄封装——不要让 Pipecat 去调 MCP 协议（多绕一层），对话内工具就是进程内直调。
  2. say 一律走 Pipecat 的 TTS 管线（克隆声线、流式、打断逻辑都在那），任何工具不许直连设备音频端点——否则会出现两个不同声音的机器人。
  3. listen 直接读 Pipecat 管线的实时转写——麦克风只有一条路，stackchan-mcp 的后台轮询 voice bridge 整个不需要了。

为什么是一个服务：Pipecat 是库不是平台，本来就嵌在进程里跑 asyncio；共享状态（音频忙闲、当前表情、presence、最近转写）是仲裁的全部依据，拆两个服务就得造 IPC。拆分的那条缝已经留好——未来要把 BodyGateway 升级成独立 HTTP 服务时，胶水层不变。

Session 问题的最终答案

session 是交互的边界，记忆是独立于 session 的持久层。对话按物理边界切 session（Ear 判定受话 → 回合开始；N 分钟无受话 / 人离开 → 回合结束），session 本身短命、用完即弃——连续性由 Hermes 的跨 session 记忆承担。既不需要"永恒 session + 自动 compact"（compact 本质是丢信息），也不需要"每句话一个新 session"，更不需要任何语音 session 指令——边界是推断出来的，不是命令出来的。

已知风险：Hermes 没有文档化的 OpenAI 兼容服务端端点，程序化调用最可行的入口是 CLI 非交互模式或 Bot 通道（构建时读深度文档确认）。所以桥【②】必须做成适配层——Hermes 接口形态就算变，也只改这一块。

🔀 四条关键数据流（标注谁干的）

1. "帮我看下家里乱不乱"

你说话 → Ear 判定受话【新增③】→ 转头 → 桥送 Hermes【新增②】
      → Hermes 调 MCP stackchan_see 拍照【现成】
      → 视觉判断（provider 用 VL 模型）→ 回复 → TTS 出声【现成】
→ 全程 3–6s，开头有 backchannel（"我看看哈~"）不冷场

2. ZCode 任务完成播报（"Agent 的一个端"本体）

ZCode Stop hook → MCP say("测试全过了") + face(happy)【纯配置】
→ 机器人转头 + 变脸 + 用克隆声线播报

3. 主动性（晚间关怀 / 内心独白）

Hermes 内置 cron 触发 skill → 把最近发生的事给它看，问它"有什么想说的吗"
→ 大多数时候选择沉默（克制才可爱）→ 想说时调 MCP say/face/move【纯配置 + 写 prompt】
→ 它打瞌睡动画时段 = Hermes 整理记忆的时段：它在睡，内存在长

4. 打游戏不被打扰（无唤醒词受话检测）

对队友喊话 / 骂游戏 / 自言自语
→ Ear 持续转写【新增③ + 现成流式 ASR】→ 判定非受话 → 忽略（转写不落盘）
→ 偶尔一句拿不准 → 只抬头看一眼 + "嗯?"表情，不出声
→ "小塔，帮我看看…" → 秒应，进入对话

常驻合计 <30GB（128GB 统一内存余量充足），深脑随叫随到。路由：闲聊走快脑，重推理升级深脑，多步任务走 Hermes（其本身也挂在 vLLM 上）。

语音延迟预算（目标 ≤1s 出声）：VAD 判停 50ms → ASR partial 200ms → 首 token 300–500ms → TTS 首句 300ms。关键在分句流式：LLM 每吐一个完整句子就交给 TTS 开口，边生成边说，同时舵机做说话动画。Hermes 若整段返回，则按句切块喂 TTS，第一句先出声。

🎭 交互设计：状态机、Ear 与人格

五态状态机（脸和灯永远是状态的镜子）

idle（眨眼/东张西望/打瞌睡） → attentive（Ear 命中，转头注视）
  → listening → thinking（眼神上飘） → speaking（嘴动 + 头摆）
  → （N 分钟无受话 / 人离开）→ 回 idle

Ear：无唤醒词受话检测（永远在线的轻量层）

层组件作用
L0silero VAD有人声吗（毫秒级）
L1sherpa-onnx 流式 zipformer持续转写，不分对谁说
L2Qwen3-0.6B 受话判断"这句话是对我说的吗？"——特征：文本（称呼/祈使/疑问指向）+ 对话状态（最近交换/间隔多久）+ 视觉朝向 + 声学（是否长独白）
L3摄像头人脸朝向说话时是否正脸对着机器人——人类判断受话人一大半靠视线（Jibo 的 addressee detection 同思路），纯文本方案做不到

梯度响应（"像人"的关键）：误触发（打游戏中途它突然接话）比漏听严重一个量级——漏听再说一遍就行，乱插话会让你想拔电。所以：高信心才开口；低信心忽略（不落盘）；中间带只做零成本社交动作——抬头看一眼、歪头、"嗯?"表情，但不出声。这等于无声地问"你叫我？"，你继续打游戏它就自己低头，你补一句它就进入对话。人类自己就是这么处理社交模糊的。

算力账：VAD + 流式 ASR + 0.6B judge + 每秒几帧人脸检测 ≈ 5–10% 资源、几瓦——"理论上耗不了多少算力"的直觉成立。勿扰开关：触摸面板划一下 = 只应呼名模式（这是注意力策略，不是 session 指令）。

情绪、触摸与主动性

  • 情绪：valence/arousal 状态 → 影响 TTS 情感参数（IndexTTS2）、动作幅度、表情选择。被摸头开心，被忽略蔫。
  • 触摸：三区 = 摸头/戳脸（喂情绪值）；长按 = 闭眼（物理断摄像头+麦克风采集）；划动 = 勿扰。
  • 主动性（双进程）：反射层（规则，毫秒级：人出现抬头、没人打瞌睡）+ 深思层（Hermes cron 每 ~30 分钟内心独白，大多数时候选择沉默）。

声线克隆（四步，一周内能听到）

  1. 准备 1–5 分钟干净参考音频：无 BGM、无混响、单人、情绪一致——参考质量决定一切，zero-shot 会连语速和情绪一起继承；
  2. 先用 CosyVoice2 zero-shot（3–10s 参考即可）把实时环跑通；
  3. 确定"这就是它的声音"后，GPT-SoVITS 用 1 分钟样本微调出专属稳定声线（V3 仅 ~407M 参数，中文少样本克隆公认最强）；想按情绪说话再换 IndexTTS2；
  4. 包成 OpenAI 兼容 /v1/audio/speech，Pipecat TTS 指过去。

只克隆有权使用的声音——自己玩的桌面玩具和对外发布是两回事。

🔒 网络与隐私

  • 供电：USB-C 常插电，电池当 UPS。不做有线数据——CoreS3 无以太网，串口带宽容不下双向流式音频，而 LAN 内 WiFi 延迟 <2ms 与有线无感差别。
  • 组网：Spark 走 10GbE 有线接回交换机；双方路由器 DHCP 静态保留 + mDNS（stackchan.local），开机自动重连。
  • 边界：全部流量不出内网（本方案天然如此）；MCP 加 bearer token；语音模型全部本地，零云依赖零 API 费。
  • 隐私：非受话转写不落盘（24h 转写整个房间技术上成立，产品上要收敛）；"闭眼"手势物理断摄像头+麦克风采集；摄像头 presence 一律 opt-in。

⚖️ 关键取舍备忘（为什么不是别的）

决策理由
不用官方固件做主线目标是 agent 控外设，stackchan-mcp 固件为此而生（自带设备 HTTP API + 全套工具）；官方固件开源随时刷回
不用 OpenClaw工程质量问题（设计烂、卡），非品类问题——同类 Hermes 更快，且是大脑本体
Hermes 是大脑，不是备胎记忆/cron/skills/MCP 客户端全部现成且跨 session；胶水桥只做传输不做逻辑
不做永恒 session + compactcompact 是丢信息；记忆靠 Hermes 写入时蒸馏 + 读取时跨 session 召回；session 边界交给传感器推断
不做固定唤醒词语义受话 + 视觉朝向 + 梯度响应，成本一样低（~5–10% 资源）但体验是"人"
say 不直连设备全局唯一声线与打断策略的保证
不做有线数据链路CoreS3 无以太网、串口带宽不够；LAN WiFi <2ms 无感差别；"有线"只用于供电和刷机
