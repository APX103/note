# Agent Harness 技术 Leader 成长计划

> 目标：在 18～24 个月内，从软件架构师转型为具备「Agent Harness 架构设计 + 工程落地 + 团队领导」能力的技术 Leader。
> 创建日期：2026-10-10
> 更新日期：2026-10-10
> 状态：执行中
> 背景：软件架构师，工程面广但深度一般，无带人经验

---

## 背景诊断与起点

你不是从 0 开始学代码，而是**从架构师向 AI Agent 领域的技术 Leader 转型**。这意味着：

- **优势**：系统设计、模块划分、工程 trade-off、跨领域理解能力强。
- **短板**：
  - Agent / LLM 领域的深度专项知识（这是一个新范式）
  - 单一技术方向的长期深耕（岗位需要能打穿一个子方向）
  - 团队管理经验（从 IC 到 People Manager 的跨越）
  - 大模型应用的成本、评测、产品化思维

因此本计划会做三件事：
1. **用架构师的视角快速补 Agent 领域知识**，不做 CRUD 式学习。
2. **逼自己在一个子方向打深**，而不是继续广而不精。
3. **系统学习管理，并尽早获得带人实践。**

- 若已有 3 分以上 Agent 经验：阶段 1 可压缩到 3 个月。

## 阶段 1：建立 Agent 领域深度（0～6 个月）

**目标**：不是学会调用 API，而是建立 Agent 系统的**架构判断力**——能独立设计 Harness、Loop、Graph、Memory、Eval 的架构，并知道优劣取舍。

### 核心策略

- 不追求「写过多少代码」，追求「能画出架构图并讲清 trade-off」。
- 用 6 周时间快速跑通一个 Reference Implementation，后面全部时间花在**深度子方向**。
- 每学一个模块，输出一篇「架构决策记录」（ADR 风格）。

### Week 1-2：构建 Agent 系统的整体心智模型

- [ ] 精读 3 篇核心论文：
  - ReAct: Synergizing Reasoning and Acting in Language Models
  - Reflexion: Self-Reflective Agents
  - 一篇 2025/2026 年的 Agentic AI Survey
- [ ] 画出一张图：Agent 系统的核心组件与数据流（Loop、Planner、Tool、Memory、Eval、Observability）
- [ ] 列出每个组件的 3 个主流设计方案和各自 trade-off
- [ ] 写第一篇 ADR：《Agent Loop 设计选型》

### Week 3-4：手写一个最小可用 Harness

- [ ] 创建 GitHub 仓库 `agent-harness-lab`
- [ ] 实现一个最小 Agent Harness：
  - 同步/异步 ReAct Loop
  - 2～3 个本地工具 + 1 个 MCP 工具
  - 简单短期记忆
  - trace 记录
- [ ] 重点不是功能多，而是**模块边界清晰、接口设计合理、可扩展**
- [ ] 写 ADR：《Harness 模块划分与接口设计》

### Week 5-6：吃透 MCP 与工具生态

- [ ] 精读 [MCP Specification](https://modelcontextprotocol.io/specification/)
- [ ] 实现一个可插拔的 Tool Registry
- [ ] 实现一个简化 MCP server/client
- [ ] 思考并写下：MCP 与 Function Calling、Plugin System、微服务的边界分别在哪里？
- [ ] 写 ADR：《工具系统的协议选型与权限模型》

### Week 7-10：选一个子方向打深（关键）

从以下 4 个方向选 1 个，作为你未来 18 个月的技术标签：

**A. 记忆系统（Memory）**
- 适合：对数据建模、检索、隐私敏感
- 打深内容：
  - 长/短期记忆架构（episodic + semantic + procedural）
  - 上下文压缩、摘要、召回策略
  - 向量检索 + 知识图谱混合方案
  - 多租户隔离、记忆更新与遗忘、跨会话一致性
  - 参考：MemGPT、Zep、LangMem

**B. 工具调用与执行（Tool Use / Action）**
- 适合：对协议、执行引擎、安全边界敏感
- 打深内容：
  - MCP 协议演进与生态
  - 工具选择、并行调用、结果验证
  - 沙箱执行、权限模型、审计日志
  - 人机协作确认机制（HITL）

**C. 评测与数据飞轮（Eval / Data Flywheel）**
- 适合：对指标、数据流水线、迭代效率敏感
- 打深内容：
  - Agent benchmark 设计（成功率、步骤效率、成本、鲁棒性）
  - 自动评判（规则 judge、模型 judge、人工 judge 结合）
  - 失败 case 挖掘与回流
  - A/B 测试与 regression 体系

**D. 成本与模型路由（Cost / Routing）**
- 适合：对系统效率、商业化、资源优化敏感
- 打深内容：
  - 多模型路由策略（简单/复杂任务分流）
  - Token 预算、缓存策略、降级熔断
  - 延迟优化、批处理、推理加速
  - 成本看板与单位经济学

### 核心管理技能清单

#### 1. 1-on-1（每周一次）

- [ ] 不是汇报工作，而是谈人、谈发展、谈障碍
- [ ] 让对方先说，问开放式问题
- [ ] 记录 action items，下周跟进
- [ ] 重点问题：「你最近卡在哪？」「你想学什么？」「我对你的帮助够吗？」

#### 2. 授权与Delegation

- [ ] 用「70% 原则」：把你能做到 70% 好的事情交给别人做
- [ ] 授权时明确：目标、边界、验收标准、支持资源
- [ ] 授权后不要 micromanage，但要设检查点
- [ ] 授权失败时，先反思自己是否讲清楚了

#### 3. 反馈与绩效

- [ ] 反馈要及时，不要攒到年终
- [ ] 用 SBI 模型：Situation（情境）- Behavior（行为）- Impact（影响）
- [ ] 对事不对人，但也不要回避对人的影响
- [ ] 设定清晰的预期，定期校准

#### 4. 招聘

- [ ] 招聘是 Leader 最重要的工作之一
- [ ] 明确岗位画像：must-have vs nice-to-have
- [ ] 设计结构化面试题，避免靠感觉
- [ ] 招「潜力 + 价值观匹配」，不只是「现在会什么」

#### 5. 技术决策

- [ ] 用 ADR（Architecture Decision Record）记录重大决策
- [ ] 决策前收集输入，决策后清晰沟通
- [ ] 区分 reversible decision 和 irreversible decision
- [ ] 允许团队试错，但要快速学习和止损

#### 6. 会议与沟通

- [ ] 减少会议，但保留必要的同步
- [ ] 周会结构：上周进展、本周重点、阻塞风险、需要决策
- [ ] 重要决策会前发文档，会上只讨论和拍板
- [ ] 会后发纪要，明确 owner 和 deadline

#### 7. 冲突处理

- [ ] 先处理情绪，再处理事情
- [ ] 把冲突公开化、对事化
- [ ] 不要当和事佬，要有明确立场
- [ ] 必要时引入第三方

#### 8. 向上管理

- [ ] 理解老板的目标和压力
- [ ] 汇报时先说结论，再说关键论据
- [ ] 主动同步风险，不要等出事再说
- [ ] 争取资源时，用数据和业务价值说话

## 备注

- 本计划不是面试准备，而是真实能力成长路径。
- 作为架构师，你的学习效率应该更高：重点不是写多少代码，而是建立判断力和决策力。
- 管理能力无法只通过读书获得，必须尽早争取带人机会，哪怕从 1 个人开始。
- 单一子方向的深度是突破点，不要在多个方向平均用力。
- 每季度做一次「是否需要换平台」的评估：当前环境是否还能给你足够的成长空间。
