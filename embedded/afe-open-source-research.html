开源 AFE 调研：嵌入式音频前端能自己攒吗

魔杖项目配套调研 · 2026-09-22 · 结论：能，而且传统算法档全部 BSD 宽松许可

§1 背景与问题

魔杖音频链路当前是裸前端：PDM → mel → 自研 wakenet CNN。乐鑫 esp-sr 的 AFE（AEC+NS+VAD）免费但闭源（预编译 .a）。本文回答：有没有真开源的 AFE 组件能替代/前置，量级是否适合 ESP32-S3。先说一个关键认知：esp-sr 里的"WebRTC 模式"本身就是静态编译进闭源壳里的开源 WebRTC 算法——所以传统算法档的"开源 vs 闭源"之争其实是壳之争，算法本体（BSD）谁都拿得到。

§3 关键事实

  • speexdsp 是为嵌入式而生的老牌 C 库（Valin 出品，当年跑 Blackfin/ARM9），BSD 许可，ESP32-SpeexDSP 移植 2025 年进了 Adafruit 视野和 Arduino 库管理器——这是"零移植成本"的最短路径。
  • RNNoise 无现成 ESP32 移植，但 Teensy 社区（M4/M7）证明量化后 MCU 实时可行；ESP32-S3 双核 LX7+向量指令属同一档，工程量在自写 int8 GRU 内核。
  • 微软 NSNet2（esp-sr 的"NET"降噪档）闭源打包，开源自搞要走 ONNX→TFLM，量级比 RNNoise 大，不值当。
  • AEC 全部不需要：魔杖无音频回放，不存在回声路径（speex AEC / WebRTC AEC3 备查）。
  • 存在性证明：microWakeWord（开源，ESPHome 生态）在 ESP32-S3 上常跑 streaming mel + TFLM——"开源前端+开源模型"整条路在这颗芯片上是走得通的。

§4 拍板：魔杖分阶段

阶段 0（现在）：不加任何 AFE。安静玩具场景 + 触发平滑已够，先跑通主链路。
阶段 1（要省算力/防误触时）：VAD 预门挡在 wakenet 前。来源二选一：继续用 esp-sr AFE 的 WebRTC VAD（已接好，闭源壳里的开源算法），或纯开源路线装 ESP32-SpeexDSP 只用其 VAD。
阶段 2（嘈杂场景误唤醒变多时）：第一刀是训练侧加噪声增强重训（混入音乐/电视/键盘声，合成流水线现成）——这是照抄乐鑫自家设计（见 §6，唤醒链路不挂 NS，抗噪来自训练数据）。仍不够再考虑 speexdsp NS；RNNoise 是 v2 挑战题。
顺手账：esp-nn（真开源 SIMD 内核）可给自研 wakenet 整窗前向提速，对冲 3.12M MACs 的标量整窗成本——比换任何 AFE 都直接。

§6 WakeNet9 官方流水线拆解（我们架构的锚点）

官方 ESP32-S3 唤醒链路（benchmark 文档原表）：

唤醒(SR)链路：  麦克风 → AEC(SR_LOW_COST) → VAD(vadnet1_medium) → WakeNet9(wn9_hilexin)
通话(VC)链路：  麦克风 → AEC(VOIP) → NS(nsnet2) → VAD(vadnet1_medium) → 输出干净音频

两个关键读数：

  • 唤醒链路里没有 NS——WakeNet9 在 SNR=4dB 噪声下 96% 的唤醒率不是靠前端降噪洗出来的，是训练时喂了带噪语料。降噪器会连带损伤语音，唤醒要的是"在噪声里认词"。
  • AEC 是为智能音箱"边播边听"准备的（用回放信号做参考减回声）；VAD（vadnet1 神经版，或 WebRTC GMM 档）用于静音期跳过前向 + 压误触发。

对齐结论：我们的"裸链路 + VAD 预门 +（将来）加噪重训"恰好就是乐鑫架构去掉 AEC 的精简版，是同构不是凑合。
