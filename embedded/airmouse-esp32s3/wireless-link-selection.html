0 · 结论速览

BLE 单板是性价比与工程风险的最优解，星闪 + dongle 是性能档的可选升级，USB-C 有线是低成本的双保险。 具体：纯 BLE 方案做出来的体验对齐"罗技 MX 的蓝牙档"（~90-133Hz 报文率、10-20ms 时延）—— 对这个量级的体感，人因科学和市售产品的选择都证明"绝大多数人绝大多数场景无感"； 而星闪（SLE）+ 自家 dongle 能把两个 BLE 补不上的洞（报文率天花板、时延）一次补掉， 达到私有 2.4G 游戏外设的量级（1kHz / 2-6ms），代价是必须带 dongle、生态新、以及一个待查证的 单芯片算力问题。系统算力两边都不是瓶颈——两核占用均 <15%，真正的工程活在 SPI、任务分核与抖动隔离。

1 · 需求与约束：从 AirMouse 说起

现役 AirMouse 是双板 ESP-NOW（ICM-20948 + 6 轴 Madgwick + 速率积分指针）。 演进路线已经确定换"7 态 EKF（逆向研究成果的 C 移植）+ 姿态差分光标引擎"， 融合率目标 200Hz（"太高也没用"），HID 回报率可以设高、拍间用增量均摊。在此之上，链路层的约束按优先级：

  1. 不能烫——ESP-NOW 因射频无正经休眠调度被否决（收发至少一侧常开，整机几十 mA 级）； 这是本篇一切讨论的起点；
  2. 够用就好——商单定位是视频演示级，不是电竞外设；
  3. 算力要放得下 EKF——ESP32-S3 双核 @240MHz，FreeRTOS（ESP-IDF 自带，开销可忽略）；
  4. 复用已验证硬件——手里有跑通过 SLE 鼠标固件的 EB21duino（BS21 dongle）和 HH-M03（BS21E）。

3 · BLE：硬数学、真实世界与感知科学

3.1 连接间隔的天花板

BLE 是主机调度的：外设（鼠标）只能在每个连接事件（Connection Event, CE）里发包， 连接间隔（CI）协议下限 7.5ms。于是：

配置理论报文率现实性
CI=7.5ms，每事件 1 包133 Hz基本盘——但需设备主动协商（Windows 默认给 15-30ms，要用连接参数更新请求压到 7.5ms）
CI=7.5ms，每事件 2-4 包267-533 Hz看主机脸色：Windows 通常愿意在一个事件里多收几包小通知，但无保证
2M PHY（BLE 5）不提报文率只缩空口时间，让多包更容易塞进一个事件；主机支持才有效

结论：133 Hz 保底、~250 Hz 现实上限，1kHz 在标准 BLE 上正式关闭——这就是游戏鼠标厂商 全用私有 2.4G 协议的原因。但注意：算法侧完全不受影响——EKF 照样内部跑 200Hz~1kHz （其 5ms 门控原生支持"高频预测 + 低频校正"），光标增量逐拍攒着，每个连接事件发一次； 亚像素累积器天然就是干这个的。

扎心的对照：你手上"感觉没问题"的蓝牙鼠标，大多数连 133Hz 都没跑满，很多就在 90Hz 附近。

3.3 为什么 90Hz / 15ms 感觉没问题

  1. 指针是积分量不是阶跃量：光标位置持续累积，90Hz 增量流 + 系统指针平滑，视觉完全连续—— 人眼对运动平滑的感知阈值恰在 60-100Hz 区间；
  2. 延迟感知门槛（JND）≈ 20ms：拖拽/指向场景下人对延迟的刚可觉差在 20ms 量级， BT 鼠标的 10-20ms 正好压在线上——"绝大多数人绝大多数场景"无感；
  3. 游戏端也在降采样：游戏按自己的帧率/tick 采输入（60-360fps）， 超出它采样率的回报本来就浪费。

差距只在快速甩枪跟枪显形：8ms 增量粒度 + 额外 ~10ms 时延，在高速移动中表现为轨迹略"散"。 竞技玩家为这最后 5% 买 1kHz dongle——但前 95% 的体验，BT 档已经覆盖。

3.4 功耗与热：0.5~3mA 的秘密

3.5 BLE 形态的系统预算（ESP32-S3 双核 + FreeRTOS）

任务核占用估算备注
BLE 控制器+主机（NimBLE，133Hz 通知）核 0~5-10%别用 Bluedroid（重一倍，多耗 ~50KB RAM）
传感器 SPI + 杂务核 0~2%I²C@400kHz 读 14 字节要 0.4ms——总线比算法贵一个数量级，上高频先换 SPI（~15µs）
EKF float 200Hz（最差拍 ~60µs / 5ms 预算）核 1<1%基准：C 版 Apple Silicon 0.22µs/拍折算；double 直跑也只 4-8%
光标引擎 + 亚像素累积核 1<0.5%纯标量
合计两核各 <15%余量全给未来功能
双核买的不是算力，是"干净" 单核其实也跑得动 200Hz。把算法钉核 1、射频栈钉核 0 的价值是隔离抖动：WiFi/USB/BLE 的中断和栈任务是微秒~百微秒级突发，分核后不干扰融合节拍。两个便宜强化：EKF 热代码放 IRAM （~10KB，避开 flash 缓存抖动）、实时数据别碰 PSRAM。

4 · 星闪（NearLink / SLE）：用它买到什么

4.1 速率：12 Mbps 与三个数量级的过剩

BS21 类芯片走 SLE（SparkLink Low Energy）模式，物理层峰值约 12 Mbps—— 华为宣传的"比蓝牙快 6 倍"即对比 BLE 5 的 2M PHY（12/2=6）。应用层实际吞吐几个 Mbps。 而空中鼠标在 1kHz 报文率下只需要 ~20 KB/s ≈ 0.16 Mbps——速率富余三个数量级， 根本不是约束。真正对鼠标有意义的是轮询间隔（报文率天花板）与时延。

4.2 真正的商品：1kHz + 2~6ms

时延链（SLE + 自家 dongle）耗时
传感器 → EKF 拍（200Hz / 1kHz 喂入）0-5ms / 0-1ms
交给 BS21E（SPI 直通 / UART）≈0 / ~1ms
SLE 空口（20B 报文 @1M PHY ≈ 240µs；2M/4M 再减半）0.1-0.3ms
dongle → USB HID（1kHz 轮询）1-4ms
合计~2-6ms

间隔亚毫秒级可配、自家 dongle 自己说了算 → 报文率可到 1kHz；空口占用在 1kHz@1M PHY 也只 ~24%。这正是私有 2.4G 游戏外设的位置——用星闪达到了同样的档位，且协议有标准可依。

4.3 功耗的诚实账

SLE 单位比特能耗更低，但报文率与功耗是同一条曲线：推 1kHz，射频唤醒次数就是 BLE@133Hz 的 7 倍。合理估计：250-500Hz 报文率下与 BLE@133Hz 相当或略好；1kHz 会贵一些， 但仍是正经调度（远好于 ESP-NOW 的常开）。"不烫"目标保得住，"极限续航"要让位给性能档定位。

4.5 现实门槛

  1. 必须自带 dongle——PC 没有星闪接收端，回到双件套（BLE 的零 dongle 优势反转）；
  2. SLE 2.0 ↔ 1.0 互通未闭环——BS21E（设备侧）与 BS21（dongle 侧）的版本配对问题， 是 HiDiTing 项目留下的未决事项；
  3. SDK 成熟度——社区小、工具链坑已有前科（Kconfig 的 SUPPORT_SLE_PERIPHERAL choice 空转等，见 EB21duino 攻略）； 好在 dongle 已被实测验证能当 USB HID 用（出厂 SLE_MOUSE 固件），硬件路径是三条方案里验证度最高的；
  4. 功耗与报文率同涨（4.3 节），性能档定位下可接受。

6 · AirMouse 落地路线

  1. 商单基线：BLE 单板——ESP32-S3（核1 跑 EKF+光标引擎，核0 跑 NimBLE+传感器 SPI）， HOGP 标准 HID，配对即用。体验对标 MX 蓝牙档，对该定位绰绰有余；协商 7.5ms CI 是上板第一件事， 实测 Windows 每事件实际收几包（决定真实报文率 133 还是 250+）；
  2. 与算法层的衔接是免费的：EKF 内部 200Hz~1kHz 照跑（5ms 门控原生支持）， 光标增量逐拍进亚像素累积器，每个连接事件合并成整数 Δ 发出——链路换了，算法层一行不改；
  3. 性能档：星闪 + dongle——复用已验证的 EB21duino（BS21）做接收端、鼠标侧加 BS21E （方案 A 双芯片起步；方案 B 单芯片等 BS21E 应用核算力查证后再议）；
  4. 双保险：留一根 USB-C——充电 + 有线模式二合一，TinyUSB 与 BLE 报告逻辑共享 （都是"产出 ΔX/ΔY"），成本一个连接器，兜住"要 1kHz / 最低延迟"的场景。商用鼠标常见的双模结构；
  5. 远期愿景：双模（BLE 兜兼容 + 星闪给高性能档）——同一套固件骨架，链路层抽象成 "发送 Δ"接口即可。

7 · 开放问题

  1. Windows/Android 实际给 BLE 外设的每事件收包数（决定 BLE 档真实上限）；
  2. BS21E 应用核的 MCU 架构/主频/FPU 规格——单芯片方案的成立前提（翻 datasheet）；
  3. SLE 2.0 ↔ 1.0 互通闭环（HiDiTing 遗留）；
  4. 星闪功耗曲线实测（250/500/1000Hz 三档温升与电流）；
  5. BLE 1kHz 的野路子（堆多包/事件）值不值得做，还是直接等星闪档。
