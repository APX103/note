把 Cactus（Needle / Whistle）塞进 STM32H743？——引擎移植调研

2026-10-22 · 调研对象：cactus-compute/needle（本地已克隆 work/needle，v3.2.8）· Cactus-Compute/needle3+whistle（HuggingFace）· 官方博客 Porting Needle / cact-format / supported-devices · 社区 needle-rs

一句话结论：你的直觉「它肯定有引擎」完全正确——引擎真实存在，<1MB、C ABI、13 个平台、连静态库带头文件都发了；而且官方把「自己写移植」变成了有格式文档、有验收测试的一等公民路径（社区已有人纯靠 .cact 文件用 Rust 写出了新运行时）。
但 H743 仍然不是它的家：官方 13 个平台全是有 OS 的（连 MIPS 相机 SoC 都有，就是没有裸机 Cortex-M）；自写移植到 H743 的性能天花板实测账算出来是「一次工具调用 5~30 秒」——炫技可以，当机器人大脑不行。真正的一步好棋藏在官方列表里：linux-armv7 文件夹意味着任何小 Linux 板（包括带麦克风阵列的 Luckfox Lyra，¥100 级）零移植直接跑。

1 · 引擎的真相：闭源二进制 + 开放容器

引擎本体：每个平台文件夹发一个 <1MB 的引擎（CLI runner + 静态库 + 头文件），Python 包经 cffi 走 C ABI 调它（本地引擎可用 NEEDLE3_LIB_PATH 指定）。引擎不带权重，启动时加载 needle3.cact/whistle.cact。Whistle 和 Needle 共用同一个引擎、同一个容器、同一套量化——"one runtime"。

13 个官方平台：macos-arm64 · linux-x86_64 / arm64 / armv7 / riscv64 / mipsel · windows ×2 · android ×3 · ios ×2 · watchos · tvos · wasm · wasm-component。没有裸机 Cortex-M。官网宣传语里的 "microcontrollers" 实际指的是 Ingenic 相机 SoC 这类跑 Linux 的便宜芯片（他们专门发了 mipsel 包）——他们心中的"MCU 级"比我们的 H743 高一档。

.cact 容器格式完全公开（官方博客给了 ~20 行 Python 解析器，本地包里 needle/model/export.py 的 read_export 就是权威参考）：

  • 196 字节头 = 49 个 int32 字段：格式标签（Needle3 = 0x05E12A84）+ 全部架构几何（vocab 8192、宽 768、20 层、上下文 8192、kv_bits…）——一个引擎吃整个层深阶梯，靠的就是头里自带几何；
  • 112 字节码本（Lloyd-Max 2/3/4-bit）+ 每张量 44 字节目录 + 权重 + 内嵌 SentencePiece BPE tokenizer；
  • 量化是自研 Cactus Quants（CQ-W2A8）：每 128 个权重一组做归一化 Walsh-Hadamard 旋转 → 存 fp16 组范数 + Lloyd-Max 坐标，2.125 bit/权重；kernel 不解量化——对 int8 激活做同样的 Hadamard 旋转，旋转相消，"答案精确到量化本身"。这就是移植要写的那个核心 kernel。

层深阶梯（同一份权重可切档，needle build --layers N）：20L=121M 参数/29MB · 16L=98M · 8L=52M · 4L=29M · 2L=25M≈8MB 文件。Whistle 解码器同样阶梯（--audio-depth N，默认 8）。

2 · 官方的「移植合同」——这条路是被设计出来的

《Porting Needle 3》博客直接给了第三方运行时的验收标准（社区第一个移植在发布几天内就出现，纯 Rust、只对着 .cact 文件 + Python 参考实现写的，就是 Geekgineer/needle-rs，还编出了 ~600KB 的 WASM）：

  • 对标对象：fp32 + 模拟量化的参考输出（不是 bf16 checkpoint），余弦相似度要求 > 0.999；
  • 三道验收：tokenizer 输出逐字节一致 / 所有测试 prompt 的 top-token 一致 / 生成 JSON 与 needle_complete 沙盒一致；
  • 加载时必须断言张量数（20 层 = 581 条）与 dtype 图样，遇到 Needle2 标签报错而不是猜；
  • 分级移植：先贪心解码（"贪心就已是正确模型"），语法约束解码和置信度头第二步再补；
  • 打包机制天生支持 DIY 引擎：needle build --platform <你的文件夹> 会把你的引擎+头文件+权重打成发行目录——自写引擎是官方工作流的一等公民。

另有官方 Rust SDK（bindgen/CMake 包 C API）。"从哪儿写"的答案：① needle-rs（Rust，最接近裸机可编目标）；② needle/model/ 里的 JAX 参考实现（architecture.py / export.py / tokenizer.py / quantize.py 全在本地）；③ 官方静态库的头文件反推 C ABI。

3 · H743 上的数字账（为什么"能跑"≠"能用"）

项目数字来源/算法
官方性能锚点（Pi 5）解码 4000 tok/s @2L → 400 @20L；预填 10000→1000 tok/s官方 supported-devices
Whistle 锚点（M4 Pro）解码 1182~2557 tok/s（8L→2L），10s 音频官方博客
H743 相对 Pi5 的算力≈ 1/100 ~ 1/200（M7@550MHz 无 int8 点积指令，~0.4-1 GOPS vs Pi5 数十 GOPS）推算
H743 SDRAM 带宽16-bit FMC 实际 ~100-150 MB/s推算
2L 档每 token 权重流量≈8MB → ≥80ms/token 的总线地板（引擎设计为 mmap 原地读，正合 SDRAM 直挂）推算
一次工具调用（~300 token 提示 + 30 token 输出）乐观 5s，现实 10~30s（预填算力 1.8 GMAC ≈ 2-5s @0.4-1 GOPS + 解码 30×80ms 起）推算，需实测校准

结论：H743 自写移植 = 3~6 周工程（CQ2 Hadamard kernel + Monarch MLP/GQA+因果卷积/engram gather/超连接等自研算子 + BPE 分词器），换来的是按一次灯等 5~30 秒。作为"我把 AI 塞进了裸机"的技术验证极酷，作为家庭机器人的离线大脑不成立。

ONNX 路线死因确认：官方没有任何 ONNX 导出（本地仓库 grep 零命中）；safetensors 是 bf16 训练 checkpoint，架构是 JAX 自定义算子，要走 ONNX 得先重写成 PyTorch 再导出，之后 Cube.AI 还要过动态 KV-cache 这关——比自写运行时还绕。

4 · 拍板：三条路

路 1（推荐）：零移植官方小板当大脑。
官方 linux-armv7/arm64 文件夹覆盖所有小 Linux 板。最有意思的是 Luckfox Lyra（RV1106 单核 A7@1.2GHz，armv7，板载麦克风阵列 + 音频 codec + speaker，¥100 级）——一块板就是机器人脑袋；跑不动就用 Radxa Zero 3W / Pi Zero 2W（¥150 级）。Pi5 数据外推：单 A7 估 Needle 2L 解码 ~100 tok/s、一次调用 1~2s （可用线）；Whistle 估 1~3s 出短语 （边缘线，须实测）。API 自带 ttft_ms / decode_tps / peak_ram_mb 字段，上板十分钟就能量出真数字。H743 留在它最强的位置：常供电唤醒词（自研 wakenet）+ 音频前端 + 外设控制，GPIO 唤醒大脑板。在线态照旧：Whistle 本地转写 → 云 LLM + MCP。
路 2（炫技线，可选）：H743 自写 CQ2 运行时。
起点 needle-rs（Rust → no_std Cortex-M 是真路径）或照 JAX 参考手写 C。范围锁死 Needle 2L/4L 档 + 贪心解码，验收用官方三道测试。产出是"裸机 STM32 上跑 foundation model"的硬核 demo（+一篇能吹的笔记），不是产品功能。预估 3~6 周业余时间。做之前先把 §3 的账拍在桌上：5~30s/次。
路 3（放弃）：ONNX / Cube.AI / 编译官方静态库到裸机。官方静态库是 Linux 目标（libc/syscalls），ONNX 导出不存在， safetensors→ONNX 需重写全套自研算子且丢掉 CQ2 的 2.125bit 压缩红利（int8 后权重×4）。三条都绕远。
