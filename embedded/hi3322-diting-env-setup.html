二、方案选型结论：为什么用 Docker（amd64 转译）

官方三种环境：一站式 CLI（fbb）、HiSpark Studio for VS Code、WSL+Docker。Mac 原生编译被 SDK 构建系统本身堵死，与工具链无关：

  • 工具链 CMake（build/toolchains/clang_riscv_linx_26_03_1.cmake）把编译器路径硬编码为 riscv-x86-linux / riscv-x86-win 两个目录，无 aarch64/darwin 分支；
  • 打包 fwpkg 必经的签名工具 sign_tool / sec_tool / lzma_tool 只有 linux-x86_64 ELF 和 Windows PE；
  • 官方下载站 tools.json 里的 darwin-arm64 毕昇编译器是 ws63 产品线的，3322 用不上。

最终方案：Apple Silicon 上跑 amd64 容器（Rosetta 转译）编译，烧录用 Mac 宿主机的 fbb/hs-flash（有官方 darwin 版）。实测转译性能可接受。

4.4 完整卸载流程（工程结束后用）

本套环境没有污染任何系统位置：无驱动、无守护进程、不改 shell 配置、不动 brew 和系统 Python。所有文件都在几个自包含目录里，按顺序执行以下命令即彻底移除（约回收 6GB+）：

# 1) fbb CLI（uv 隔离环境，一条命令清两处）
uv tool uninstall hs-fbb-cli

# 2) fbb 构建环境（hs-flash / ccache / venv）
rm -rf ~/.hs-fbb

# 3) Docker（容器是唯一"活着"的东西）
docker rm -f hs3322
docker rmi hs3322-build:22.04 ubuntu-amd64:22.04 docker.m.daocloud.io/library/ubuntu:22.04
docker builder prune                      # 可选，会影响其他项目缓存

# 4) SDK 内的大头（保留代码只删产物；或整个仓库删掉重 clone 即原样）
rm -rf ~/work/hs-fbb/src/output ~/work/hs-fbb/src/tools/bin/compiler
cd ~/work/hs-fbb && git clean -nd        # 先预览，确认后 git clean -fd

# 5) 脚本目录 + /tmp 临时文件
rm -rf ~/work/hispark-3322-env
rm -f /tmp/hsflash_live.log /tmp/flash_dryrun*.log /tmp/hsflash_dry.log /tmp/fpid \
      /tmp/fbb_* /tmp/hispark_tools.json /tmp/bootstrap.sh /tmp/install_bisheng.py
⚠️ 两个边角：~/.cache/uv（13GB）绝大部分是其他项目的，精确清理用 uv cache clean hs-fbb-cli pyserial，别全清；~/work/note 里的本文档属于笔记仓库，自行决定去留。

五、板卡接口备忘

接口用途备注
3322_USB（主USB，Type-C）供电 5V/2A + Hi3322 USB DFU 烧录正常开机时不枚举任何 USB 设备（Mac 无反应是正常的）；需 UART2 发 AT+USBDFUTRIGGER 或短接 RX2-GND 才进 DFU（枚举为 3361:3322）
CAT1_USB（Hi2131）Cat1 副芯片固件升级 / 模组调试插上会枚举名为 "LiteOS" 的 RNDIS 网卡——那是基带的，别用
UART2（T2 排针）烧录 + 日志 + AT 命令，750000 波特率需外接 USB-TTL；1.8V 电平域；RX/TX 交叉、共地
UART3（T3 排针）DebugKits 维测（921600）1.8V，禁接 3.3V 串口
SWD硬件调试（GDB/OpenOCD，断点上限 3）需 J-Link 类调试器
串口板必须选支持 1.8V 电平输出 的 USB 转 TTL（普通 CH340/CP2102 默认 3.3V/5V 不能直连）。
