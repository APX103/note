00 / CV610 ON MAC先选对路线：传应用，还是刷固件

日常改界面、试算法，用「Docker 编译应用 + Mac 串口传文件」就够了。这条路线已经让 Music 触屏和 NPU 人脸检测在这块板上运行。先沿着第 01–07 步走；需要换内核、驱动或整套系统时，再看第 10 步。

Mac编辑与下载保存 C 源码和构建脚本
amd64 Linux 容器官方 GCC 编译输出 ARMv7 / musl ELF
Mac 原生串口传输与校验gzip → Base64 → SHA-256
CV610 Linux启动与观察日志、触摸、摄像头
你要做的事产物 / 工具本次证据
换一个应用或 DemoELF 程序、必要的 .so / 模型；Python 串口助手实板通过 Music 与 NPU 均运行过
更换整套系统U-Boot、内核、rootfs、分区 XML；官方 burn.sh + TFTP未实测 本教程单列官方流程
无法进入 U-Boot 的恢复Windows ToolPlatform / BurnTool + 对应镜像未实测 需 Windows 恢复环境

本文的「部署」会写什么？上传到 /root 会写根文件系统所在的 Flash；上传到这块板的 /run 则写内存，断电消失。两者都不等于整分区烧录。本次实测 /tmp 也在根分区上，不能把它当 RAM 盘。

本教程依据 2026-09-09 的成功实验整理，2026-09-10 补做了最小 C/C++ 编译复核。教程中的命令已整理为可复制的步骤；今日没有重新执行上板部署、修改开机脚本或刷写固件。先前的 会话复盘 保留需求、方案取舍和排障经过。

01 / CV610 ON MAC准备工具与接线

所在位置准备什么用途
MacDocker Desktop；Terminal；Python 3；Git；curl / tar / unzip容器负责编译，Mac 负责串口。已有工具就直接使用。
容器官方 wukun 镜像内的 GCC / G++、CMake、Meson、Ninja不用在 macOS 原生重建厂商交叉编译器。
板端能启动的 Linux、root shell、base64 / gzip / sha256sum串口助手通过已有 shell 写文件；不依赖 SSH、网络或 pyserial。
硬件CV610 主板、Debug 数据线、5 V / 2 A 电源先验证串口；Music 再接 JD9853 240×320 + Hynitron 触摸屏。
  1. 主板 J17 接 5 V / 2 A 电源。主板 J1318 是 CH343P USB 转 Debug UART，接 Mac 的数据线。不要把扩展板自身的 Debug 口当作 CV610 主板的控制台。
  2. 这次曾在只接 Debug 时观察到板子启动；这不构成摄像头、Wi-Fi、喇叭同时工作的供电保证。教程统一按官方 J17 供电规格操作。
  3. 摄像头选 OS04D10，单摄使用主板背面 J4 / Sensor0。插拔屏幕、扩展板、摄像头排线前，断开电源和可能供电的 Debug USB。
  4. Speaker 接 J47；主板已有麦克风。Music UI 和人脸检测都不靠喇叭运行。

接线依据：Sunniwell 板级指南。本机串口已经可用，不需要为了教程重复安装驱动；新 Mac 确实缺驱动时再参考 WCH 官方 macOS 驱动。

Mac 终端 · 先确认工具
docker info
python3 --version
git --version
成功标志：Docker 能显示 Server 信息，Python 显示 3.x。只出现 Docker Client 或提示无法连接 daemon 时，先启动 Docker Desktop。

02 / CV610 ON MAC拉镜像，先验证容器再下载大工程

Apple Silicon 是 ARM64，官方编译器运行在 x86 Linux，目标程序是 ARM32 Linux。这三者不同。--platform linux/amd64 指的是运行编译器的容器，不是让板子运行 x86 程序。

Mac 终端 · 新终端里先设置镜像变量
export CV610_IMAGE='swr.cn-north-4.myhuaweicloud.com/hi_spark/wukun@sha256:2fa448d269cbe5865b1840714b0e769e03c4018671198e17316c88332901952c'

# 已经缓存时，这一步只检查已有镜像
docker pull --platform linux/amd64 "$CV610_IMAGE"

# 只启动一个命令，不获取完整 SDK / 工程
docker run --rm --platform linux/amd64 --network none \
  --entrypoint /bin/sh "$CV610_IMAGE" -c 'uname -m'
成功标志：输出 x86_64 且退出码为 0。这一步失败就停下来排查 Docker；不要一边怀疑容器不兼容，一边继续下载整个工程。

易读的标签是 wukun:docker-v1.2.0-rc2。这里固定已经实测的镜像摘要，避免同名标签以后指向不同内容。首次拉取仍需要下载约 1.14 GiB 的压缩镜像层；本机已缓存。

Mac 终端 · 看编译器版本

  --entrypoint /bin/sh "$CV610_IMAGE" -c '
  /opt/toolchains/gcc-10.3-arm-musl-x86-linux-26.06.1/arm-v01c02-linux-musleabi-gcc/bin/arm-v01c02-linux-musleabi-gcc --version
'
本次为 GCC 10.3.0，厂商工具链版本 CS71.26.06.1，musl 1.2.3。镜像里的 arm-v01c02-linux-musleabi-gcc 是要使用的编译器。

HiSpark 的 镜像文档面向 Linux 宿主机；这里的 ARM Mac 应用构建结论来自实测。Docker 支持跨架构运行，但仿真编译可能慢于原生 x86，见 Docker 官方说明。

04 / CV610 ON MAC先编一个最小 ARM 程序

先用包里的原始检查脚本，确认 C 编译、C++ 标准库链接和目标格式都正确。脚本在容器内创建两个小源码，执行官方编译器，不需要板子在线。

Mac 终端 · 输出保留在挂载目录
cd "$CV610_WORK"
docker run --rm --platform linux/amd64 --network none \
  --mount "type=bind,src=$CV610_WORK/.docker-validation,dst=/work" \
  --entrypoint /bin/bash "$CV610_IMAGE" /work/sdk-probe.sh

file .docker-validation/probe/probe-armv7
shasum -a 256 .docker-validation/probe/probe-armv7
成功标志：脚本最后输出 SDK_COMPILER_PROBE_PASS；file 显示 ELF 32-bit … ARM … EABI5；程序加载器为 /lib/ld-musl-arm.so.1。2026-09-10 再次编译通过。

--mount 把 Mac 目录映射到容器 /work。即使容器由 --rm 删除，生成的 probe 目录仍在 Mac 上。不能直接在 macOS 执行这个 ELF；第 06 步将它送到板端。

编译到底执行了什么？看最关键的 C 命令
容器内部 · sdk-probe.sh 已自动执行，无需再抄一次
export PATH=/opt/toolchains/gcc-10.3-arm-musl-x86-linux-26.06.1/arm-v01c02-linux-musleabi-gcc/bin:$PATH
arm-v01c02-linux-musleabi-gcc \
  -march=armv7-a -mfpu=neon-vfpv4 -mfloat-abi=softfp \
  probe.c -o probe-armv7

此处 probe.c 检查 32 位 ARM 目标并打印 CV610 ARMv7 compiler probe。-mfloat-abi=softfp 与这套厂商库匹配；不要换成随手找到的 aarch64 或 gnueabihf 工具链。

应用包不是固件包。最小 C 程序可以只传一个可执行文件；界面程序还取决于链接方式；NPU 程序另外需要匹配的动态库与模型。第 07–08 步分别说明。

05 / CV610 ON MAC从 Mac 打开板子的串口

串口由 macOS 直接打开。本机已确认过的节点是 /dev/cu.usbmodem5C842916071，换电脑或换 USB 口后重新查，不要假设它永远不变。

Mac 终端 · 枚举设备
python3 - <<'PY'
import glob
for path in sorted(glob.glob('/dev/cu.usb*')):
    print(path)
PY

# 将值改成上面实际出现的 CV610 主板 Debug 串口
export CV610_PORT='/dev/cu.usbmodem5C842916071'
screen "$CV610_PORT" 115200

回车后应看到 Linux 的登录提示或 shell。若停在 login:，用当前固件的账号登录；不要在网页里保存密码。hisilicon # 一类提示可能是 U-Boot，还没有进入 Linux，不能执行本文的传文件助手。

板端 Linux shell · 在 screen 窗口中输入
uname -a
cat /proc/mtd
df -h / /run /tmp
command -v base64 gzip sha256sum
ls -l /lib/ld-musl-arm.so.1
本机为 ARMv7 Linux 5.10.221+；三项传输命令和 musl 加载器应存在。约 49 MiB 是当前 Linux 可见内存，不是整块物理 DDR 容量。

退出 screen：按 Ctrl+A，松开，再按反斜杠 \，按提示确认。只按 Ctrl+A、D 是脱离会话，可能仍占着串口。上传前退出所有串口终端；可用 lsof "$CV610_PORT" 查看占用进程，再正常关闭对应程序。

Docker Desktop 的 USB 设备接入需另行处理，不能把 Linux 的 --device /dev/ttyUSB0 直接替换成 Mac 节点就认定可用。本路径不依赖容器 USB 透传，见 Docker USB/IP 文档。

06 / CV610 ON MAC通过串口上传，校验后执行

先确认已退出 screen，且板端留在已登录的 Linux shell。下面的 Python 使用源码包里的 Board，与先前 NPU 部署复用同一套传输方法。

Mac 终端 · 先只执行一条检查命令
cd "$CV610_WORK"
python3 .docker-validation/serial.py 'uname -a'
应看到板端内核信息及 CV610_DONE_… 完成标记。若超时、无 shell 或串口被占用，先修复连接，不继续上传。
Mac 终端 · 上传最小 C 程序到 RAM 并执行
python3 - <<'PY'
import sys
sys.path.insert(0, '.docker-validation')
from serial import Board
with Board() as b:
    print(b.run('df -k /run; mount | grep " /run "'))
    b.push('.docker-validation/probe/probe-armv7', '/run/probe-armv7')
    out = b.run('chmod 755 /run/probe-armv7 && /run/probe-armv7; echo APP_RC=$?')
    print(out)
    assert 'CV610 ARMv7 compiler probe' in out and 'APP_RC=0' in out
PY
运行后的预期输出：CV610 ARMv7 compiler probe、APP_RC=0。这是供读者执行的最小上板检查；本次整理只复核了它的编译，上板成功的历史证据来自后面的 Music 和 NPU。

传输工具做了哪些事

  1. Mac 把文件 gzip 压缩、转 Base64，分块写入 115200 串口；板端用已有命令解码。
  2. 先写目标文件的 .new，比较原始文件与板端文件的 SHA-256。
  3. 只有校验一致才重命名到目标路径；同哈希文件重传时直接跳过。程序权限和启动由后面的命令负责。

Board.run() 的完成标记只说明 shell 命令执行结束，不表示命令成功；因此示例显式读取 APP_RC、检查应用输出。它也不会自动登录，更不是串口刷机协议。

115200、8N1 的原始上限约 11.5 kB/s，Base64 与等待还会降低速度。小程序、约 1 MiB 的 UI 可以用；几十 MiB 的 Agent 或 rootfs 不适合照搬这条传输方法。以后有网络时再用板端实际可用的 SCP / HTTP / TFTP，先确认服务和命令存在。

7.2 传到板上并切换界面

先通过串口确认 /dev/dri/card0、/dev/input/event0 存在，原系统已加载屏幕和触摸驱动。脚本停止本会话已知的三个界面进程，保留媒体 SDK 服务；新固件应先核对实际应用名。一个 DRM 屏幕只让一个界面应用占用。

Mac 终端 · 上板试运行，会临时替换当前屏幕界面
cd "$CV610_WORK"
python3 - <<'PY'
import sys
sys.path.insert(0, '.docker-validation')
from serial import Board
with Board() as b:
    print(b.run('ls -l /dev/dri/card0 /dev/input/event0; df -k /run'))
    b.push('.docker-validation/music-build/app/cv610_music', '/run/cv610_music')
    print(b.run('chmod 755 /run/cv610_music'))
    print(b.run('killall -TERM samples_panel cv610_music cv610_face 2>/dev/null || true'))
    b.read(1)
    print(b.run('setsid /run/cv610_music </dev/null >/run/cv610-music.log 2>&1 &'))
    b.read(3)
    out = b.run('cat /run/cv610-music.log; ps | grep "[c]v610_music"')
    print(out)
    assert '[display] 240x320' in out and '[music] ready' in out
PY
成功标志：日志显示 [display] 240x320、[music] ready；点屏幕后出现 [touch] pressed …。左右滑专辑封面切歌，上滑进入控制页，再上滑进入曲目列表。

原实验将程序放在 /tmp/cv610_music；教程改用已确认是 tmpfs 的 /run 做临时试运行，避免把测试文件写进紧张的根分区。这次整理没有重新上板执行这个路径调整。

08 / CV610 ON MAC已有 NPU 工程怎么重编、更新

这块原固件的两个摄像头兼容点

旧版 sys_config.ko 不识别 os04d10 名称。已核对该版本里的 sensor_xxx 对应 24 MHz，所以原开机驱动参数改为 -sensor0 sensor_xxx；应用仍选择真正的 OS04D10。这只适用于本次核对过的旧固件，不能作为任意 SDK 的通用传感器配置。

GXA543 I²C 复用器上电默认关闭；J4 需要 i2cset -y 0 0x70 0x01，已写在 start.sh。选通后摄像头在 0x3c 应答。J6 / 双摄不能直接沿用这一单通道配置。

「Power off before wiring」是应用中的断电接线提示，不是烧写工具报错。原问题最终定位到时钟与 I²C 选通；修复后有真实预览和持续推理。

这个例子对应 WS73 + JD9853 / Hynitron + OS04D10 的综合 Demo。该案例 app.defconfig 已有 CONFIG_BUILD_INSTALL=y。以构建成功日志实际输出为准，当前板仓 README 指向 _build/install/image/factory_demo/。

10.2 U-Boot 正常：官方 burn.sh，串口控制 + TFTP 传镜像

使用有真实串口和可达网络的 Linux / WSL2 环境。准备稳定电源、主板 Debug 串口、主板网口到同网段网络；本教程按有线链路准备 TFTP，不把 Linux 下的 Wi-Fi 驱动当作 U-Boot 已支持的网络能力。配置 tools/burn/config.ini 中的实际串口设备。

Linux / WSL2 官方烧录环境 · 非 Mac 原生终端
# 在完整主仓根目录，路径按本次构建日志核对
bash tools/burn/check_config.sh _build/install/image/factory_demo

# 预检成功、供电/串口/网络与镜像均确认后，才开始实际烧录
bash tools/burn/burn.sh
  1. 输入板子能访问的 TFTP 主机 IP。
  2. 输入同网段的板端 IP；这是烧录时给 U-Boot 配的地址，不要求原 Linux 已联网。
  3. 输入包含分区 XML 与全部镜像的目录。
  4. 脚本通过串口进入 U-Boot，配置网络，再逐分区下载和写入。写入期间保持供电，等完成并重启。
官方预检成功标志是退出码 0；烧录成功标志包含 AutoBurn 完成。随后用串口检查 uname -a 和目标 Demo。不要仅凭进度条走完判断应用功能通过。

官方 Linux Docker 启动示例需要串口设备映射和 TFTP 网络配置。Mac Docker USB、UDP 可达性是另外的验证工作，本会话没有执行。按当前偏好，真要走这步时用 x86 Linux 或 Windows + WSL2，不继续自建工具链绕路。

10.3 U-Boot 不可用：Windows ToolPlatform / BurnTool

  1. 准备 Windows PC 和匹配的串口驱动，将完整镜像目录拷到 Windows。
  2. 解压 SDK 附带的 tools/ToolPlatform/ToolPlatform-CAM-5.7.14-win32-x86_64.zip，运行 ToolPlatform.exe。
  3. 选择 Hi3516CV610、正确 COM 口、115200，加载该构建配套的 NAND 分区 XML。
  4. 按工具提示进入烧写状态并断电 / 上电，写入完成前不要断电；完成后查看串口启动日志。

BurnTool 通过芯片 ROM Boot 通信，不依赖已有 U-Boot；普通 Python shell 文件上传助手做不到这一点。没有验证过 Wine、Windows ARM 虚拟机或其他 Mac 替代运行方式。

本节依据固定版本的 官方构建文档、烧录指南、ToolPlatform 操作指南，以及 WS73 案例 README。原始脚本参数已核对；整机执行尚未验证。

11 / CV610 ON MAC遇到问题，先看这一项

现象先查什么处理方向
Docker 只显示 Client / daemon 未连接Docker Desktop 是否启动先让 docker info 成功，再拉镜像或构建。
exec format error容器平台与 ELF 架构容器用 linux/amd64；板端产物必须是 ARM32，不能是 Mach-O / x86_64 / AArch64。
编译成功，但末尾退出 127最后失败的是哪个命令可能只是容器缺 file；本次 Go 构建就遇到过。用 Mac 的 file 检查，不能直接判为编译失败。
Mac 上没有 cu.usb* 节点数据线、主板 Debug 口、设备枚举、供电先排除充电线和接错扩展板串口，再按需要看 WCH 驱动。
串口乱码 / 上传超时115200、独占串口、Linux 已登录退出 screen 会话；不能向登录界面或 U-Boot 提示符发送 shell 文件传输。
文件存在却报 not foundELF 指定的加载器与所需 .so检查 /lib/ld-musl-arm.so.1、ABI、readelf 的 NEEDED；不要直接覆盖系统 libc。
SHA-256 不一致串口丢字节、被其他进程占用、存储空间不启动 .new 文件；恢复连接并重传。
No space left on devicedf -h / /run 与 cat /proc/mtd/run 用内存；本机 /tmp 用根分区。不要把 256 MiB Flash 总容量当作 rootfs 余量。
屏幕黑 / DRM 失败现有界面进程、card0、屏幕驱动先停原 UI，只保留一个显示进程；别把媒体服务顺手全杀。
Music 没声音它是 UI Demo没有接音频解码；不是 Speaker 坏了。
Live 没画面OS04D10 接 J4、24 MHz 时钟、I²C mux仅对当前旧固件按第 08 步兼容记录排查；先断电再调整排线。
WS73 搜不到 5 GHz 热点热点频段当前方案需 2.4 GHz；可改用合适热点或网线。本次 ZeroClaw 试聊因此暂停，未证明聊天可用。
烧录脚本打不开串口 / TFTP 超时Linux 设备映射与板端能到达的服务器地址与编译是两回事；按官方 x86 Linux / WSL2 路线准备，不把 Mac 容器地址直接当 LAN 地址。

硬件环境发生变化时重新确认设备节点、屏幕分辨率、Flash 类型与分区、摄像头型号。固定版本和已有日志能帮助排查，不能代替实际检查。
