01 / OUTCOME这次真正完成了什么

这台 ARM Mac 已经可以作为当前应用开发的主力电脑。官方 x86 Linux 容器里的编译器可运行，编出的 ARMv7 程序已通过 Mac 原生串口部署到 CV610，触摸屏和真实摄像头上的 NPU 检测都已验证。没有为此自行重建交叉工具链。

02 / SESSION需求如何一步步收敛

  1. 先研究，不试运行

    最初目标是跑通官方 Demo，并探索“小智式”的创意作品。先查硬件、上层工程、SDK、Mac 支持和烧录路线，遵守当时不安装、不编译的要求。

  2. 明确要自己的端侧 Agent

    用户补充：上下文、唤醒和工具循环留在板端；ASR、LLM/VLM、TTS 可以在云端。Py 小智是参考，不希望依赖小智后端承载主 Agent。

  3. 授权 Docker 后验证编译

    先前展开下载过早，被用户提醒应先验 Docker。随后完成 amd64 容器最小检查、厂商 C/C++ 构建及 PicoClaw ARMv7 构建，确认无需先换 x86 电脑。

  4. 接 Debug，读取真实板况

    进入 Linux 控制台，确认 ARMv7/musl、小内存和根分区剩余空间；先验证已有面板，再按“换一个”的要求编译 LVGL Music。

  5. 新触摸 Demo 获得用户确认

    Music 完成封面、播放控制、曲目列表交互；用户确认成功。这一步打通了完整的应用编译与部署链路。

  6. Agent 从“自写”收敛到“复制并裁剪”

    按用户“越小越好”的要求修订方案，比较 PicoClaw 与 NullClaw，研究 Py 小智表情与播放状态；没有越过方案阶段直接实施。

  7. 免费语音实验做过，也撤掉了

    Mac Python + Whisper + 系统 TTS 曾跑通；准备 uv 环境供用户自行控制后，按用户要求彻底删除模型下载路线。

  8. 把芯片的视觉算力用起来

    重新列出 Demo，解释 NPU、IVE、ISP 分工。用户选择人脸 Demo；先用图片验证 NPU，再等待接入摄像头。

  9. 修复时钟与 I²C 通道，完成实时检测

    确认背面 Sensor0 接线，定位旧模块时钟别名和 GXA543 默认断开问题。修复后摄像头初始化成功，显示真实画面，重启验证通过。

03 / BOARD板子是什么，1 TOPS 用在哪里

板卡是 Sunniwell CV610 生态开发板，本次实板对应 Hi3516CV610-20S。芯片、主板、扩展板和屏幕是不同层级：不能仅凭“CV610”就假定无线模块、屏控制器、Flash 布局全部相同。硬件规格与接口以板级指南和芯片资料为依据。

资源已知规格 / 本次板况开发上的意义
CPUCortex-A7 MP2，950 MHz执行 Linux、UI、网络与业务逻辑；不是 Mac 的 ARM64 环境。
NPU1 TOPS适合兼容模型的目标检测等推理；峰值算力不等于固定帧率。
DDR128 MB；当前启动划分 Linux 56 MB / MMZ 72 MBLinux 实际 MemTotal 约 49 MB；媒体保留内存不能当作应用空闲内存。
系统与根分区Linux 5.10.221+ / ARMv7；当前根分区约 36.3 MB初读空闲约 5.8 MB，部署视觉 Demo 后约 2.6 MB。板卡标称 Flash 容量不等于根分区可用空间。
屏幕与触摸JD9853 240 × 320，Hynitron 触摸本次使用 DRM /dev/dri/card0 与 evdev /dev/input/event0。
摄像头OS04D10，当前仅使用背面 J4 / Sensor0J6 是 Sensor1；双摄需要额外的通道切换处理。
音频板载双麦克风 U1415 / U1416；Speaker 接口 J47只收到一只外接喇叭正常。视觉 Demo 不调用音频。
01 · 图像质量ISP / AI ISP曝光、白平衡、降噪等；是否启用某一算法取决于配置。
02 · 视觉运算IVE图像处理、运动检测、跟踪等基础计算。
03 · 模型推理NPU加载兼容模型，检测人脸、人体、车辆等目标。
04 · 媒体与交互编码单元 + CPUH.264/H.265/JPEG 与应用组织；本次 UI 由 CPU 驱动。

音乐和表情界面主要使用 CPU、显示与触摸。摄像头 + NPU Demo 才开始利用这颗芯片更有特点的视觉能力。1 TOPS 不能推出可以在 128 MB 板子上运行通用 LLM/VLM；本次方案仍把大模型推理放在外部。

接口与供电结论

  • J17：正常测试使用 5 V / 2 A 供电；J1318 Debug：USB 数据线接 Mac，板载 CH343P，115200 波特率。
  • J1319：USB 通信口，也有供电能力，不能与 Debug 口混为一谈。SW401 为主板电源开关。
  • J4：主板背面 Sensor0，30 pin / 0.5 mm FPC，下接触座。金属触点朝向以连接器实际触点为准，不能只看蓝色补强片。
  • 插拔摄像头排线之前完全断电，包括拔掉 Debug USB。若两颗模组都印有 OS04D10，单摄演示任选一颗接 J4 即可。

关于“只接 Debug 能不能启动”：会话早期按原理图给过“Debug 只供串口芯片”的判断，随后实机确实读到了已启动的 Linux。用户没有确认当时是否存在其他供电，因此没有完成“仅 Debug 供电”的独立验证。最终保留独立供电接法，不把当时的控制台连通归因于 Debug 能稳定带动整板。

官方主工程通过多仓清单组织。只克隆板卡应用仓，不能当作完整固件工程；本次没有完成上层整机工程的全量构建。后期通过 tag_V2.0.0_Beta 的 SDK 部分克隆和按需获取，补齐小应用需要的头文件、sample、模型与库。

三个平台需要分开看

宿主电脑ARM64 macOS编辑、文件管理、Docker Desktop、原生串口。
厂商工具运行环境x86_64 Linux显式 linux/amd64 容器，执行 SDK GCC/G++。
编译产物ARMv7 LinuxELF32 / EABI5 / musl，使用厂商目标库。
部署执行CV610 实板串口上传与校验后运行，开发板本身不跑 Docker。

“Mac 和板子都是 ARM”并不意味着二进制互通。官方交叉编译器交付为 x86 Linux 程序；macOS 是 Darwin，板子是 32 位 ARM Linux，还需要对齐 musl、浮点 ABI、加载器和 SDK 库版本。

本次阅读的官方环境文档有 Ubuntu、Windows/WSL2 和 Docker 路线，没有找到 CV610 原生 macOS 全流程的官方验证指南。自行重建 GCC/binutils 或评估 Clang + sysroot 在技术上有路线，但不能解决所有镜像工具、二进制库和 Windows 恢复工具的兼容性。用户明确要求 Docker 不行就转 x86，本次没有执行自建工具链路线。

检查结果如何解释

06 / AGENT RESEARCH想做的 Agent，以及为什么还没做

需求最终明确为：复制一个成熟开源底座，尽量裁剪；板端掌握上下文和工具循环，只向外部调用模型。首版先普通多轮聊天，随后增加免费听说、说话表情、唤醒和按需视觉。不要另建框架、管理后台、多 Agent、插件市场或长期记忆系统。

CV610 本地

会话与短历史、工具执行、摄像头抓拍、录音播放、UI 状态；本地唤醒是目标，首个闭环可以先触摸触发。

云端或外部服务

LLM / VLM 推理，按需要配置 ASR 和 TTS。本地管理上下文不代表上下文不上传；普通图文模型也不天然包含语音能力。

两条视觉路线均成立

A. 主模型是 VLM
板端 Agent → 摄像头抓拍 → JPEG + 问题 → 主 VLM → 回答

B. 主模型只接受文字
板端 Agent → 文本 LLM → inspect_scene(question)
                           ↓
                     本次抓拍 + 独立视觉 API
                           ↓
                  文字描述 / 时间戳 / 错误结果
                           ↓
                     文本 LLM 继续回答

Py 小智的 take_photo(question) / VLCamera 已有路线 B 的实现：拍 JPEG，编码为图片输入，调用独立视觉 API，返回描述。摄像头工具可以经 MCP 暴露，但给文本模型返回图片路径不会赋予视觉能力；MCP 返回 ImageContent 也需要明确进入模型请求。首版按需拍一张即可，不需要持续上传视频。源码依据

方案边界：用户要求“先方案，再设计，最后实现”。本次没有交付完整 Agent，也没有承诺 NullClaw 必然可装。最新方向是复制并裁剪；若继续，第一步应是真实文字聊天和资源测量。

07 / REVERTED EXPERIMENT免费语音方案：验证过，但已撤销

08 / RUNNING DEMO现在运行的 NPU Demo 是怎样做的

采用最小复用方式：SDK 的 AiDetect 推理接口 + 本仓 samples/gui/common 摄像头 / 媒体适配 + 已编好的 LVGL / DRM 库。新增的小应用负责按钮、取帧、检测、预览转换和画框，没有自行训练模型。

01 · 采集OS04D10 / J4VI 与 ISP 建立摄像头通路。
02 · 输出VPSS640 × 360、NV21、目标 10 fps。
03 · 检测AiDetect → NPU模型输入 768 × 448；返回类别、位置与置信度。
04 · 展示LVGL / DRM240 × 135 预览，绿色人脸框、青色人体框。
项目本次实际配置
模型det_hvf_hor.bin，1,382,752 字节，约 1.38 MB / 1.32 MiB。
来源HiSpark / Hi3516CV610，tag_V2.0.0_Beta，固定提交见版本表。
接口ss_mpi_aidetect_create_chn、ss_mpi_aidetect_process，应用复用 sample_common_aidetect_* 包装。
模型信息输入 768 × 448；3 类：FACE / HUMAN / VEHICLE。当前 UI 只显示前两类。
预览处理CPU 最近邻缩放与 NV21 → RGB565；预览区域 240 × 135，屏幕总分辨率 240 × 320。
按钮Live 返回摄像头实时画面；Test image 对本地图片做一次真实 NPU 推理。
可执行文件cv610_face 322,964 字节；这个体积不包含模型、动态库或系统依赖。
运行测量单次检测调用观察到约 42–47 ms；VPSS 输出为 10 fps。两者不是同一统计口径。

它是不是 YOLO？

不能根据当前资料确认。实际加载的是海思 AiDetect 的预编译“人脸人形车形”模型；本次查到的官方接口与模型说明没有标注其网络架构或 YOLO 版本。SDK 另外明确提供 yolov5.om、yolov8.om 示例，但不是此次部署的模型。不能凭输出形状或效果猜成某个 YOLO 版本。官方模型文档

人脸检测与身份识别也不同。现在做的是找出脸的位置；“认出这是某个人”还需要特征提取、注册与比对。本次没有身份库。

验证如何逐级推进

  1. 无摄像头先验证 NPU：官方 sample 对测试图推理成功，正脸置信度约 0.90；硬件中断计数增加，错误计数为零。
  2. 接入 UI：触摸 Test image 后显示 Faces 1 / People 1；读取 LCD 截屏验证结果。测试输入来自 OpenCV 的 Lena 样例，转换为 640 × 360 NV21，不是实时摄像头。
  3. 接入真实摄像头：修复下节两个配置点，读取传感器初始化、VPSS 和 NPU 状态，并检查真实 LCD 画面。
  4. 验证重启：保留摄像头连接重启，确认通道选通、进程、视频帧和 NPU 计数恢复；用户最终确认“可以了”。

旧 UI 把测试图标成 OFFICIAL TEST IMAGE，容易误解为海思随模型提供的测试图；准确来源是 OpenCV 样例。本页按真实来源记录，不把测试图片的识别结果当作现场摄像头结果。

实板当时媒体 MMZ 使用约 44 MB / 72 MB，剩余约 28 MB；Linux 可用内存观察到约 29 MB。这是短时运行快照，没有做长时间稳定性或精度基准。

09 / ROOT CAUSES摄像头接好了，为什么仍然没画面

用户看到的英文实际是 Power off before wiring，意思是“接线前断电”，属于提示文字，并不是 Flash 写入失败。它放在等待画面上很容易被当作错误，后来已从两个等待状态中移除。真实故障要看串口日志和图像计数。

问题一：旧 sys_config 模块不认识 OS04D10 名称

板上原固件的 sys_config.ko 不接受 os04d10 这个传感器名称，直接传入会得到错误时钟配置。对照实际模块与 SDK sys_cfg.c，它内置的 sensor_xxx 对应 24 MHz（配置值 0x4001）。

# 现有启动脚本中，给旧 sys_config 模块选择正确时钟
./load3516cv610_20s_debug -i -sensor0 sensor_xxx

# 应用仍然使用真正的 OS04D10 驱动
SENSOR0_TYPE=OS04D10_MIPI_4M_30FPS_10BIT

这只是当前旧固件的时钟兼容别名，并没有把摄像头换成“未知型号”。没有为此重编内核，也没有通过随意写寄存器规避问题。

问题二：GXA543 上电没有选通 Sensor0 的 I²C

接摄像头后日志出现 I2C_WRITE error / os04d10_reg_init failed，MIPI 没数据，VPSS 收帧为零。用户确认是背面 Sensor0，接口选对了。真正原因是 I²C 多路器 GXA543 在 0x70，控制值上电为 0x00，两路都未接通。

检查修复前选通 J4 后
i2cget -y 0 0x700x000x01
探测 OS04D10 地址 0x3c无应答3c 应答
摄像头初始化寄存器写失败24Mclk ... Init OK!
视频 / NPU无帧VPSS 10 fps，NPU 持续执行
# 单摄像头接 J4 / Sensor0 的已验证选通命令
i2cset -y 0 0x70 0x01

# 已固化到 /root/face-demo/start.sh，失败就停止启动
i2cset -y 0 0x70 0x01 || exit 1

依据是本仓已有的 samples/sensor/dual/patch/0004-dual-sensor-gxa543-i2c-mux.patch。本次最小应用遗漏了这一步；修复后再次重启确认生效。这是软件初始化遗漏，不是用户接错。双摄需要复用原补丁的逐次通道切换方式，不能把单路设置推广为双摄全部已支持。补丁来源

最后一次重启验证摘要

I2C mux: 0x01
cv610_face: running
os04d10 24Mclk 4M30fps(MIPI) 2LANE_720Mbps 10bit linear Init OK!
[camera] start=00000000
VPSS: 640 × 360 / YVU-SP420 / frame_rate 10
NPU stream recv_cnt: 281

提取自 .docker-validation/npu-face/camera-fix-verification.log。4M30fps 是传感器工作模式；当前应用从 VPSS 取出的低分辨率视频配置为 10 fps，不应混写为屏幕每秒显示 30 帧。

串口脚本也修了两类可靠性问题

串口写入需要处理部分写成功，不能假定一次 write 传完。命令完成判定也不能匹配固定的 echo 字符串：终端开启回显时可能先匹配到发出的命令。本次改成每条命令随机完成标记，由 printf 产生，并兼容 CRLF；后台命令与标记之间用换行，避免形成 &; 语法错误。保留 check_serial.py 作边界检查。

12 / WHAT REMAINS后续只做真正需要的下一步

当前停在一个已验证的视觉基线，后续可按兴趣选择，不自动展开新工程：

继续玩 NPU

基于人脸位置让眼睛跟随，检测到人再显示表情；或者明确切换到 SDK 的 YOLO 示例。若要识别身份，再单独增加特征提取与比对。

回到最小 Agent

先复制并裁剪一个底座，完成真实多轮文字聊天，测 Flash / RSS / 峰值；通过后再接免费语音和表情，最后考虑视觉工具。

这次值得保留的方法

  • 先做最小探针。验证容器执行和厂商 hello world，再拉大仓、编整机。
  • 复用现成接口。硬件适配、媒体和 UI 已有实现，新增代码只连接必要部分。
  • 让“成功”对应证据。编译、上板、触摸、离线推理、真实摄像头和重启，各有独立验证。
  • 保留失败的真正原因。网络下载中断、缺少 file 工具、I²C 通道断开，与平台不支持是不同问题。
  • 跟随用户的成本边界。不想下载语音模型就撤销，不把“开源免费”偷换成没有安装和维护成本。

未完成的项目包括：全量固件构建与烧录、身份识别、双摄、真实 LLM/VLM 对话、板端语音、长期稳定性、音频与视觉并行运行。这些都没有在本页计为已完成。
