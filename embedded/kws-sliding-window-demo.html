怎么读这幅图：时间从右往左流动，最右侧竖线是「现在」。 上面两条泳道（波形、分帧）与最下面的概率曲线共享同一条时间轴——对照着看「词走到哪了 / p 涨到哪了」； 中间的 FIFO 泳道是右侧 1 秒的放大镜，它就是模型每次推理真正吃到的那份「100 帧快照」。 三个必看瞬间：t≈2.2s 概率连续 3 拍过线 → 绿星触发；t≈5.1s 噪声尖峰只红 2 拍 → 被连续 k 拍规则滤掉； 任何时候暂停后按「步进」，可以看到 FIFO 每次只滑动一格（10ms）。

对应泳道的四步拆解

① 分帧（波形 → 特征）
16 kHz 采样，每 10ms（160 样点）产出一帧，帧窗 25ms（400 样点，相邻帧重叠 60%）。 每帧算 40 维 log-mel 特征（动画里用能量高低示意颜色）。帧率 = 100 帧/秒。
② 特征 FIFO（环形缓冲）
只保留最近 100 帧 = 1 秒。新帧从右进、最老一帧被覆盖，永不回头读旧数据。 这 1 秒就是模型的「感受野」——约一个唤醒词的长度。
③ 滑窗推理（每 4 帧 = 40ms 一次）
每次推理吃「整份 FIFO 快照」输出一个 p ∈ [0,1]。 词长 0.7s ≫ 步长 40ms，整词完整落在窗内约有 (1000−700)/40+1 ≈ 8 拍机会，漏不掉。
④ 判决（概率流 → 一次事件）
四件套：阈值 0.8 + 连续 3 拍确认（噪声尖峰只红 1–2 拍，被滤）+ 上升沿只触发一次 + 触发后 1.5s 冷却；退出用低阈值 0.5 做迟滞防抖。

再往深一层

有状态流式模型（WakeNet 路线）
动画演示的是「无状态」方式：每 40ms 把 100 帧全量卷一遍，正确但费 CPU。 生产模型（WakeNet / microWakeWord）全部用因果卷积/循环结构，推理之间传递 state 张量、 缓存中间激活，每次只算新到的 1 帧的增量——成本摊薄 ~100 倍，这是 ESP32-S3 上它只占小半个核的原因。 代价是要处理 state 老化：长期静音或触发后需复位。
触发延迟怎么来的
你把词说完（t=2.1s）→ 词尾滑到窗口右端、p 冲高 → 再等 3 拍确认（3×40ms）→ t≈2.2s 触发，距词尾约 100~200ms。所有商用唤醒都是这个量级。触发那一刻词尾就在 FIFO 最新几帧， 所以可立刻切 ASR，并把 FIFO 里最后几百 ms 的 pre-roll 一起交出去，紧跟的话一个音节不丢。
ESP32 上的任务结构
I2S DMA → 环形缓冲 → 音频任务每 32ms（512 样点）取一块（ESP-SR AFE 即此粒度）→ 提特征/推理/判决 → 回调。实时预算：处理一块的耗时必须 < 32ms，否则丢块（留计数器监控 overrun）。 特征 FIFO 与 state 放内部 RAM，权重留 flash 用 mmap。
关于本页的「假模型」
页内波形与概率都是合成的教学模型（p 按「词尾贴近窗口右端的程度」生成）， 真实 WakeNet 的概率曲线形状与此类似：词尾附近冲高、词滑出后回落。 判决逻辑（阈值/连续拍/冷却/迟滞）与真实系统一致。
