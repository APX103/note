1. 背景与目标

用 M5StickS3（ESP32-S3，板载红外收发）做一个空调开关遥控器，目标是一个按键完成"学习 + 发送"：

  • K1 短按：发送空调开关码（on/off）。
  • K1 长按：进入学习模式，用空调遥控器（或手机万能遥控 App）对着设备学习红外波形。
  • K2 长按：关机。

硬件：IR TX = GPIO46（板载），IR RX = GPIO42（板载）。软件栈：Arduino CLI + M5Unified + ESP32IRPulseKit（库）。

项目目录里有四个 sketch：ir_recorder（录制）、ir_player（回放）、ir_dump_official（官方 RMT 示例）、ir_toggle_remote（单键二合一，本次主战场）。

2. 现象描述

现象初判实际根因
录制"成功"（显示 SAVED），但发送后空调无反应 发射功率 / 协议问题 文件格式错位（Bug 1）+ 单帧协议连发两次（Bug 2）
同一个按键每次按，捕获的 tick 数字都不一样 噪声 / 滤波问题 部分正常（抖动），部分是库 RX 截断（Bug 3）
手机万能遥控 App 的码，解码不出任何空调品牌 手机码不标准 码其实对（App 能控空调），是接收链路损坏 + AGC 恢复期削头
学习过程中"还没按就结束"（误触发） 随机噪声 RX 通道溢出/噪声触发（Bug 3 的衍生）
修完所有代码后，近距离测试才终于控制空调 — 板载 IR 发射功率小，必须 ≤50cm 正对接收窗

整场调试的教训：症状看似都在"软件"，但最后的临门一脚是"物理距离"。四个真 bug 是软件，最终达成目标是靠"库生成标准帧 + 近距离"。

3. 排查时间线（逐步还原）

第一轮：读代码 → 发现文件格式错位
现象：录制正常、发送"OK"、空调没反应。通读 toggle_remote.ino 时发现一个隐蔽的字节序/类型问题： 
// 保存（saveToggle）：
f.write((const uint8_t *)&raw.len, sizeof(raw.len));  // raw.len 是 size_t → 4 字节

// 读取（loadToggle）：
uint16_t len = 0;
f.read((uint8_t *)&len, sizeof(len));                 // 只读 2 字节
保存写 4 字节长度，读取只读 2 字节，tick 数据整体偏移 2 字节。用 Python 按 C 语义模拟往返： 
loaded[0:4]: [0, 300, 300, 300]   ← 开头多一个 0 长度 mark
loaded[-2:]: [165, 52]            ← 结尾 trailer/gap 丢失
Bug 1 修复：长度显式存 uint16_t，并给读取端加"文件精确大小校验"，旧固件留下的坏文件直接拒绝。
第二轮：查库源码 → 发现 Haier 是单帧协议
库源码 src/ac/Haier.h 明确写着：HAIER_AC 每次按键只发一帧（kHaierAcDefaultRepeat == kNoRepeat）。而固件里： 
bool sent1 = tx.send(view);
delay(40);
bool sent2 = tx.send(view);   // 又发一遍！
空调把两帧当成两次独立按键：开 → 关，互相抵消。Bug 2 修复：只发一次。
第三轮：用户实测捕获 → 用数据说话
用户用手机万能遥控 App（App 能正常控制空调）连续学习，捕获 len=169/175/221/233… 每次结构都不同。把每帧丢进 Python 做直方图分析：
  • 169/175：几乎全是 50% 占空比方波（mark≈space≈540µs）——无任何数据位空间，纯坏信号。
  • 221：头是 Haier 双头（3150/3160/3000/4510µs 对得上），但数据位 mark 被削到 280-330µs，且夹杂 40-190µs 毛刺。
  • 233：数据位已标准（mark 460-570µs、0 位 630µs、1 位 1660µs），但没有头部（半帧）——解码器找不到同步头，位流无法对齐。
结论 手机码本身是对的，但 StickS3 接收到的波形质量很差。这指向接收链路本身的问题，而非遥控器。
关键转折：TX→RX loopback 自测，隔离问题
为了分清"接收配置问题"还是"遥控器信号问题"，写了一个 loopback 测试固件：用板载 TX 发一帧库编码的标准 Haier（精确 520µs mark），再用 RX 接收。对比两条接收路径： 
原生 ESP-IDF RMT RX（128 符号, 1us, 官方示例配置）：
  头 2984/3011, 2984/4303 · mark 511-540µs · space 673/1644µs  → 完美！

库 IRReceiver（默认 64 符号, 无 DMA）：
  头 302/303/302/435 · mark 被削到 240-460µs + 毛刺        → 损坏！
同样一个信号，原生驱动收得完美，库收得一团糟。Bug 3 确认：库 RX 通道配置有缺陷。
第四轮：修库 → 128 符号 + DMA
ESP32-S3 的 soc_caps.h：每通道 RMT 仅 SOC_RMT_MEM_WORDS_PER_CHANNEL = 48 符号。AC 帧普遍 75-125+ 符号，库却把 RX 通道写死 mem_block_symbols = 64 且 with_dma = false——长帧靠 ISR 手工搬运，必然丢数据、削 mark、产生毛刺。

补丁（.arduino_sketchbook/libraries/ESP32IRPulseKit/src/hal/RmtHal.cpp）：

cfg.mem_block_symbols = 128;   // 原 64
cfg.flags.with_dma = true;    // 原 false
打补丁后 loopback：Haier 解码从 0 次 → 12 轮中 2 次成功，且头部全部干净。
第五轮：Haier 容差 40% → 55%
即使 RX 修好，仍有部分帧失败。分析发现：接收头（TSOP 类）在长头部后 AGC 恢复期会把第一个数据 mark 从 520µs 削到 280-330µs，而 Haier 解码容差 40% 的下限是 312µs——刚好卡在边界，偶尔过关偶尔失败。

补丁（src/ac/Haier.h）：tol_pct 40 → 55。位判定靠 space 长度 + 0xA5 前缀 + 校验和把关，放宽 mark 窗口不会误判。

第六轮：看原理图 → 硬件特性实锤
用户强烈要求看硬件。下载官方原理图 K150_Stick_S3_PRJ_V0.6（M5Stack 文档站），从"BTB 小板 IR_TX/RX SPK"页确认：
  • RX：Vishay VSOP38338——38kHz 解调接收头，内置 AGC + 带通，active-low 输出，10K 上拉。
  • TX：Everlight IR928-6C/F1——940nm 红外管，22Ω 限流 + 三极管驱动，GPIO46。
硬件特性解释了所有"解码玄学"：AGC 建立期吞头、信号过强饱和、940nm 需要正对。
第七轮：学习链路反复失败 → 换思路
手机只能"连按"（每次发一帧），且多次捕获质量不稳。固件升级为"多次按学习"：累积最佳捕获 + 头部感知评分（含完整 3000/3000/3000/4300 头的帧 +500 分）+ 毛刺过滤（<150µs 并入邻居）。但用户数据里"数据区标准、头部缺失"的半帧问题始终绕不过去。

决策 既然空调已经确认认识 Haier 协议，而库有可靠的编码器——放弃"学习"这条路，直接用库生成教科书级 Haier 帧发送，彻底绕开脆弱的学习链路。

第八轮：最终——距离！
生成帧固件烧上后，用户近距离（≤50cm 正对空调接收窗）按 K1：空调动了！

此前"发不出去"的最后一块拼图：板载 IR 管功率很小（IR928 单管 + 22Ω 限流），隔 1 米以上信号根本到不了空调。所有代码问题都修完后，剩下的纯粹是物理问题。

4. 关键实验与数据

4.1 loopback 自测固件（定位 RX 问题的最有力工具）

核心思想：用自己的发射端发出已知标准波形，再用接收端收回来。这样"遥控器"这个变量被完全消除，剩下的只有板载链路和软件栈。对比原生 RMT 驱动与库驱动，问题归属一目了然。

5. 红外原理与 StickS3 硬件

5.1 红外通信怎么工作

遥控器把 38kHz 载波按 mark/space 时长调制后发射；接收头（TSOP 类）内部完成带通滤波 + AGC + 整形，输出解调后的方波，由 RMT 计时。信息只编码在时长里，载波本身不携带信息。

  • 接收头输出的是"解调后的 mark/space 波形"（不是原始 38kHz 信号）。
  • 接收头有 AGC：自动适应信号强度，但收敛需要时间（约 0.4-1.8ms），会吞掉 burst 开头的 mark。
  • 每次按同一键，由于距离/角度/环境光差异，AGC 收敛点不同 → mark/space 时长有 ±几十 µs 的抖动——这是正常现象，靠协议容差和校验和来容忍。

5.2 StickS3 板载红外（原理图实锤）

项目器件关键特性
IR RXVishay VSOP3833838kHz 解调头、内置 AGC、active-low、GPIO42、10K 上拉
IR TXEverlight IR928-6C/F1940nm 红外管、22Ω 限流、三极管驱动、GPIO46、高电平点亮
板载 IR 发射功率很小。 实测 ≤30-50cm 正对空调接收窗才可靠。隔 1 米以上通常毫无反应——这常常被误判成"代码问题"，其实是物理限制。使用姿势必须先确认。

5.3 手机红外 vs 实体遥控器

StickS3（VSOP38338）小米手机红外后果
发射功率单管毫安级专用驱动，强得多手机贴脸会让接收头 AGC 饱和，波形损坏
载波38kHz 最灵敏（±2-3kHz）30-56kHz 可编程非 38kHz 边沿变钝
按键行为—很多 App 只能"点按"发一帧学习时要多次按，靠累积选优

接收建议：手机/遥控器距 StickS3 30-100cm 最稳（太近饱和、太远弱）。

7. 方法论：以后这类事情应该怎么做

这次的教训沉淀成一套可复用的排查流程，先按顺序做，别跳步：

1 先读硬件，再读代码

第一件事是查官方文档 + 原理图 + 官方示例，确认引脚、器件型号、电路特性、官方推荐配置。本次如果一开始就知道"板载发射功率小、接收头是 TSOP 带 AGC"，能少走一半弯路。

2 用数据说话：原始数据打出来，离线分析

串口把捕获的原始 tick 数组打印出来（做成 C 数组格式方便复制），拿 Python 离线做直方图、头部扫描、位流提取。别对着屏幕"猜"，让数据告诉你 mark/space 是标准、削短还是方波。

3 写受控实验隔离变量：loopback 自测

用自己的 TX 发已知标准波形、用 RX 收回来（loopback），把"遥控器/手机"这个外部变量彻底排除。再对比原生驱动 vs 第三方库，问题归属（硬件 / 库 / 自己的代码）立刻水落石出。

4 区分"正常现象"和"bug"

抖动、AGC 吞头、量化误差、帧合并边界不同——都是正常的物理/协议现象，靠容差和重编码容忍。而"mark 被系统性削 40% + 毛刺"、"文件读出来的 tick 与写进去的不一致"是 bug。判据：正常现象应围绕标准值±小范围浮动且结构完整；bug 是结构性损坏。

5 检查文件格式与字节序

嵌入式持久化最容易栽的坑：sizeof(size_t) 在 32 位 ESP32 上是 4 字节，而协议约定 2 字节；写读不一致会导致整体错位。用脚本做一次写→读往返校验，一次就暴露。

6 库有坑时，用原生驱动交叉验证

第三方库的默认配置不一定适配你的板子（RMT 内存、DMA、容差）。怀疑库时不要猜，直接用 ESP-IDF 原生 API 写个最小示例对比，官方示例的配置通常就是正确基线。

7 物理因素永远最后排（也是最先容易漏的）

距离、角度、遮挡、功率。板载 IR 功率小是常态。测试时先把设备怼到接收窗前，确认链路通，再谈优化距离。

8 遇到瓶颈果断换思路

"学习 + 回放"依赖一整条脆弱链路；当协议已知且库有可靠编码器时，直接生成标准帧往往更稳。别死磕一条路。

9 改第三方库要打补丁记录

库改动写在项目内的 .arduino_sketchbook/libraries（用户级库目录），并把改动记进 README/笔记，避免更新库时被覆盖后无从查起。

8. 当前状态与使用说明

8.1 最终固件行为（toggle_remote）

按键行为
K1 短按库生成教科书级 Haier 帧（完整双头 + 正确校验和），连发 3 次；按一次"开"、再按"关"交替（默认 制冷 24°C / 风速自动）
K1 长按学习模式（备选路径：多次按累积最佳帧 + 头部感知 + 毛刺过滤）
K2 长按M5.Power.powerOff() 关机
实测通过：设备举到空调正前方 30-50cm、正对接收窗，按 K1 空调有反应。

8.2 使用注意

  • 发射：≤30-50cm 正对空调接收窗（面板右下角暗红色小窗）。
  • 接收（学习）：手机/遥控器距设备 30-100cm。
  • 串口设备名：arduino-cli board list 查看（可能是 usbmodem1101 / usbmodem101，设备重枚举会变）。
