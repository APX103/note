MICROPIXEL / GRAVITY-BALLS 3D DEMO

MCU 上的一箱弹珠：
gravity-balls 三维小球 Demo 拆解

MicroPixel（github.com/78/micropixel）是跑在乐鑫 MCU 上的 WebAssembly 应用运行时：应用用 C++23 SDK 编写、编译成 AOT 产物，由固件里的 WAMR 执行。它仓库里的 gravity-balls（重力彩球）是一个教科书级的 3D demo——8~64 颗预光照小球关在固定于设备的透明盒子里，加速度计直接提供惯性力，倾斜/甩动/旋转设备，球就像真实弹珠箱一样运动。本文拆解它的完整实现：不用姿态融合的传感器物理、INDEX8 预烘焙球体图集 + 调色板行复用的"零 GPU"渲染、脏矩形节流、显示记录（draw records）架构，以及背后的 Host/Guest 分工。

00 / TL;DR结论速览

gravity-balls 用约 1000 行 C++ 在没有 GPU、没有 FPU 吞吐可依赖的 MCU 上做出了可信的三维弹珠箱，全部秘密在三处工程取舍：

  • 物理上不做姿态融合——加速度计读数取相反数就是盒子坐标系里"重力 + 墙壁推力"的合力（比力），静止时指向地、甩动时自动含墙壁推球的反作用力；有陀螺仪再加旋转参考系三个惯性力（离心、欧拉、科里奥利）。设备坐标系 = 盒子坐标系，一步到位，省掉姿态估计整套状态机。
  • 渲染上不画三角形——启动时把球面光照烘焙成 11 种直径的 INDEX8 灰度图集（含覆盖率抗锯齿边缘），24 行调色板把强度映射成"8 种球色 + 8 种光晕 + 8 种光斑"，一颗球 = 一条 Sprite 绘制记录；线框盒 = 22 条 2px FlatQuad，深度雾靠调色板行变体。逐像素填充由 Host 的整数内核执行（P4 还能走 DMA2D 批量搬运）。
  • 负载上靠内容节流——纯黑背景 + 每个 buffer 记录上一帧画过的脏矩形，下一帧只清这些矩形（超过 60% 屏幕才整屏清）；720px 面板按一半分辨率渲染再由 Host 2× 放大；物理固定 240 Hz 但每帧最多 8 步、多余时间丢弃不追赶。
维度做法为什么
3D 感知加速度计取反当重力 + 陀螺仪惯性力盒子固定在设备上，无需世界系姿态（不需要融合）
球体渲染预烘焙 INDEX8 图集（11 直径）+ 调色板行选色避免运行时逐像素光照；换色 = 换调色板行，零成本
遮挡排序画家算法：按视深从远到近画不透明球无深度缓冲，凸球 + 不透明 sprite 足够正确
光晕/光斑加法混合 Sprite，全部先于球体绘制光晕只照亮背景，被后画的不透明球自然遮挡
清除开销三缓冲各自记脏矩形，黑 FillRect 回擦AMOLED 黑色省电且免整屏带宽
物理节奏240 Hz 固定步长 + 累加器 + 每帧 ≤8 步 + 丢弃慢帧不滚雪球，行为确定性可回归测试

一句话：这是"把 3D 问题降维成 2D sprite + 一条物理捷径"的典范——平台侧只提供整数光栅内核和调色板，应用侧用聪明的预处理（烘焙图集）和聪明的物理（比力直接当重力）把三维体验塞进了 WASM 应用的预算里。

01 / PLATFORM平台背景：MicroPixel 是什么

MicroPixel 是 Espressif 微控制器上的 WebAssembly 应用运行时：应用（Guest）用受限 C++23 SDK 编写，经 WASI SDK 编译为 AOT v6 Bundle；固件（Host）基于 ESP-IDF 6.1 + 固定 commit 的 WAMR fork，负责硬件管理、应用隔离（商店/App Store、BundleFS）和系统 UI。应用开发不需要 ESP-IDF，一条 micropixel --transport usb run 完成构建-安装-启动-跟日志。

芯片开发板与本 demo 的关系
ESP32-P4Metalio-Claw4（720×720）buffer 按 360×360 渲染、Host 2× 放生的代表场景
ESP32-S31ESP-Mosaico（480×480 圆屏）README 的主参照板：触摸逻辑坐标 720×720 → buffer 480×480
ESP32-S3ESP32-S3-BOX-3 / 立创 SZPI / M5Stack CoreS3S3 三板型支持

图形的两种应用模型（demo 选了第二种）

  • Scene（保留模式）：Guest 提交对象树与属性变化，Host 验证后只重绘受影响区域——适合页面/精灵类 UI。
  • DirectSurface / HostSurface（立即模式显示记录）：Host 持有多缓冲，Guest 每帧提交一批 RasterResources 绘制记录（FillRect / FlatQuad / Sprite / AdditiveSprite / Text），算法和场景判断留在 Guest，逐像素循环在 Host 执行。运行时内核把连续不透明块攒批交给设备契约 Graphics::CopyOpaqueBlocks（P4 用 DMA2D 实现），失败由 CPU 内核重画。

设计文档的原则一句话："billboard 变成 RasterResources 记录，每像素填充由 Host 的 INDEX8 + 光照调色板整数内核完成；不提供通用浮点网格与逐像素深度缓冲——MCU 没有值得依赖的浮点吞吐。"gravity-balls 就是这条路线的旗舰示范：Guest 里没有任何逐像素循环。

顺带一提：Guest 运行时里还有一个更小的兄弟 guest/runtime/sphere_view.cpp——系统 UI 自己的 3D 球视图，因为 Guest 不链接 libm，连 sin/cos 都是手写的多项式逼近（最大误差 ~1e-3 rad）。同一套"球 = 纹理索引表 + 投影到整像素"的思路在平台内复用了两次。

02 / WHATDemo 是什么

gravity-balls v0.1.1（app id micropixel.gravity-balls）是一个独立 Guest 应用，清单 app.json 声明：单线程（threading: none）、支持 square/portrait/landscape 三种布局、最小 320×320，传感器与触摸全是可选能力（sensor.acceleration / sensor.gyroscope / input.touch）——没有 IMU 也能跑，重力退化为固定指向远墙。

  • 画面：纯黑背景上一个线框透明盒子（远墙矩形 + 四条深度棱 + 深度标尺 + 远墙网格，共 22 条线），24 颗（默认）不同大小、8 种颜色的预光照小球在里面滚撞；每颗球带加法光晕和投在远墙上的光斑。面向 AMOLED 的黑色设计。
  • 交互：倾斜/甩动/旋转设备 = 盒内惯性力变化；点画面 = 全部球获得确定性弹起速度（观察前后遮挡）；点顶部 1/8 = 重置；右上 MENU = 设置面板（球数 8/16/24/32/48/64、盒深 6/9/12/15、重力 ×0.5~×2），面板开着模拟不停。
  • 传感器失效策略：500ms 没有新加速度样本，重力缓慢回到指向远墙的 9.8 m/s²——demo 永不因缺传感器而死。

代码规模：渲染 + 应用主体 main.cpp 890 行，物理 physics.hpp 138 行，回归测试 physics_test.cpp 56 行。运行画面不依赖任何图片素材（大厅封面 JPEG 只用于商店）。

资源模型：纹理槽 + 调色板槽

启动时 Guest 做三件上传：① UploadTexture(0, 图集宽×高, kColumnMajor, atlas_)——一张 INDEX8 图集（球 11 档直径 + 64×64 径向渐变 blob）；② UploadLitPalette(0, 24 行, palette_)——24 行 × 256 项 RGB565；③ 之后绘制记录里只需要引用"槽号 + 调色板行号"，换颜色、换亮度、换深度雾全在调色板行上做，图集纹丝不动。

坐标系与多分辨率

  • 世界系：原点在盒中心，y 向上，z 朝屏幕里；相机在原点看 +z，针孔模型 scale = focal / (z + extent.z + 10)，盒子开口（玻璃面）在深度 10 处正好铺满 buffer 短边（focal = min(w,h)/2 × 10/4.4）。
  • 三套像素坐标系：逻辑显示坐标（触摸、safe area，Mosaico 为 720×720）→ buffer 像素（surface_.ToBuffer() 换算，480 或 360）→ 面板物理像素。大于 480 的面板以 2 倍降采样创建 surface（Claw4 720→360 buffer），Host 放大，降低近球的填充率与带宽。
  • 自适应：图集直径按 buffer 短边缩放（最多 1.5×，避免放大出锯齿）；盒子的宽高比跟随 buffer；标题放在 RendererInfo::safe_area() 内（圆屏角部 inset）；MENU 按钮贴 buffer 角；字体度量从逻辑像素换算（Raster 文字不随 buffer 缩小）。

04 / RENDERING渲染管线详解

4.1 烘焙：一颗球的所有样子

BuildAtlas() 启动时为 11 档直径（480 buffer 下 14~52px）逐 texel 计算：像素圆外的覆盖率先行钳位（coverage = clamp(radius+0.5-dist, 0, 1)，黑底上等价于 alpha 抗锯齿）；圆内重建法线 n=(dx,dy,nz)，做 Lambert 漫反射 + Blinn-Phong 高光（^32），光向左上略偏前（light=(-0.45,-0.60,0.66)，half-vector 归一化），强度 0.14 + 0.70·diffuse + 0.32·specular，乘覆盖率后量化到 1..252（0 = 圆外，253/254 留给线框）。再烘焙一个 64×64 的 (1-r)² 径向 blob 给光晕和光斑共用。运行时不再有任何光照计算。

4.2 调色板：24 行就是全部配色自由度

行号用途生成规则
0..78 种球色强度 ≤0.78 线性缩放到本色；顶部 22% 只向白混合 55%（防止球堆变白块）；253 号 = 远墙网格色、254 号 = 盒棱色，且随行号变暗 → 深度雾
8..15光晕色30% 本色 × 强度，供 ADDITIVE 叠加
16..23光斑色28% 本色 × 强度

线框的深度衰减因此是免费的：画棱时按端点深度选"第几行球色"的 254 号条目，越远越暗。

4.3 每帧绘制顺序（painter's algorithm 的关键排序）

  1. SetPalette 绑定调色板槽；
  2. 清除：该 buffer 首次使用 → 整屏黑 FillRect；否则回擦上一帧记录的脏矩形（球矩形 ∪ 光晕矩形，与光斑相交时合并），脏矩形总面积 > 60% 屏幕则退化成一次整屏清；
  3. 线框盒：22 条世界空间线段投影后，各向法向偏移 ±1px 构成 2px 宽四边形，FlatQuad 四顶点带深度亮度（顶点"色"其实是调色板行内的亮度索引 0..7）；无 polygon_supported() 能力则整段跳过；
  4. 全部光斑（AdditiveSprite，行 16..23）：球在远墙上的投影，越高越大越淡（0.9 + 1.5·离墙高度），贴墙时被球完全盖住而省略；
  5. 全部光晕（AdditiveSprite，行 8..15）：1.6 倍球径的 blob；
  6. 全部球体（不透明 Sprite，行 0..7）：按视深从远到近插入排序后绘制；投影半径就近选择 11 档直径中最接近的一档；
  7. HUD：标题 Text + MENU 按钮 FillRect/Text；面板打开时再约 30 条记录。

为什么光晕必须全部先画：加法混合的光晕如果画在球后会叠加到别的球的高光上，球堆会糊成白块；先画光（只照亮黑背景），再画不透明球，遮挡关系由后画的球自然建立——这是整个渲染正确性的支点。

4.4 帧成本账本

默认 24 球一帧约：1 SetPalette + 若干清除 FillRect（脏矩形数 ≤ 球数×2+4）+ 22 FlatQuad + 24 光斑 + 24 光晕 + 24 Sprite + 4 条 HUD ≈ 100 余条记录；每条记录的逐像素代价都在 Host 的整数内核里（INDEX8 查调色板写 RGB565；加法按通道饱和加）。遥测按帧累计 records / clear_px / sprite_px，把"清除像素数远小于整屏 230400"当作验收指标。

05 / PHYSICS物理引擎详解（138 行）

5.1 核心洞察：加速度计读数取反 = 盒内合力

盒子固定在设备上，盒子坐标系就是设备坐标系。加速度计输出的是比力（specific force），其相反数恰好是盒内质点感受到的"重力 + 墙壁推力"：静止时指下方，甩动时自动包含墙壁推球的惯性反作用力。不需要姿态融合、不需要世界坐标系——这是整个 demo 最值钱的一步简化。轴映射沿用 Tilt 约定（屏幕右为 -X、下为 +Y），重力 = (-ax, -ay, kDepthAxisSign·az)，z 符号常量留了一个翻转开关应对装机方向。

有陀螺仪时再加旋转参考系三个惯性力，让"转设备"本身产生可感效果：

acceleration = gravity
             - ω × (ω × r)      // 离心：球被甩向外圈
             - dω/dt × r        // 欧拉：角加速时推向反方向
             - 2 ω × v          // 科里奥利：运动中的球被侧推

5.2 数值与单位

参数值说明

单位比例16 单位/米8.8 单位的盒子 ≈ 55cm 弹珠箱；不缩放的话 4 单位落差要 0.9s，"像在水里漂"

求解迭代每步 2 轮（球对 + 墙）64 球全对检测 O(n²) 也就 2016 对，MCU 够用

5.3 传感器调理

  • 采样：以 5ms 请求间隔打开加速度计/陀螺仪（钳到传感器 min/max），每帧读一次最新样本（timestamp 去重，实际样本率不超过帧率）；
  • 加速度：NaN 防御 → 限幅 40 m/s² → ×16×重力倍数 → 单样本低通 α=0.6（一拍延迟，保甩动锐利）；
  • 陀螺仪：ω 直接用；角加速度由相邻样本差分再 α=0.5 平滑（dt 窗口 0.1ms~200ms 才采信）；
  • 失效：500ms 无新样本 → 加速度通道重力缓慢回默认（α=0.1），陀螺仪项清零。

5.4 回归测试（宿主机跑，不进 Bundle）

physics_test.cpp 五组断言：① 正碰后动量守恒（和 <1e-6）且动能不增；② 完全重合球心仍有限且被分开（法向退化到 (1,0,0)）；③ 64 球 150 秒正弦变化重力 + 周期 Kick 压力测试，全程有限且不出盒；④ 20 秒静止收敛到远墙上（位置误差 <0.01、动能 <0.01）；⑤ 旋转系方向性：纯 ωz 自旋把静止球向外甩（离心 vx>0），角加速度把它推向旋转反方向（欧拉 vy<0）。确定性物理 + 纯函数世界 = 可以无硬件验收，这与我们 Renode 调研里"嵌入式测试难进 CI"的痛点正好是一套可行答案。

06 / FRAME LOOP帧循环与时序

for (;;) {
    DrainEvents();                       // Stop/Resume/Touch
    while (!surface_.AcquireFree(index)) // 等空闲 buffer（面板受限时增大）
        HandleEvent(app_.WaitEvent());   // 等事件时顺便处理，不忙等
    Sample(now);                         // 读 IMU → 调理 forces_
    Advance(now);                        // 累加器 → ≤8 步 world_.Step()
    BuildFrame();                        // 投影/选档/光斑/远到近插入排序
    surface_.Update(index, [&](list){ Draw(list, index); }); // 编码+Host内核
    surface_.Present(index);             // 提交，Host 可能直接扫描输出
}   // 每阶段耗时进遥测桶：wait/physics/geometry/update/present
  • 三缓冲流水：Guest 在 AcquireFree 拿到的 buffer 上画，Present 后 Host 合成/扫描输出，Guest 立刻去拿下一块——等待时间被计成 wait_us，是"面板受限"的信号。
  • 暂停/恢复：应用时钟冻结；Resume 时三个 buffer 内容未知（buffer_ready_=false → 下帧整屏清一次）、累加器清零、力清零，时间没有为球流逝，杜绝恢复瞬间的巨步长穿透。
  • 遥测：每 120 帧输出两行日志——性能行（fps×100、五个耗时桶均值、记录数、清除/精灵像素数）与仿真行（球数、深度、步数、丢弃步、慢帧、平均深度/速度、IMU/陀螺实际样本率）。没有画面时靠 z_avg / speed_avg 判断球是否落到远墙、是否在动——远程验收友好的设计。
  • 平台约束：Guest 单线程、1 秒 watchdog（进 Host ABI 时重置）、Stop 后 500ms 内必须退出、无 libc/libm（连整数 abs 都是手写内联）。

08 / TAKEAWAYS值得抄的思路

  • 比力即重力：任何"设备固定容器 + 里面东西"的交互（弹珠、液体、粒子、平衡球），都不要做姿态融合——加速度计取反对到设备系就完事。我们的 AMOLED 液体 demo、magic-wand 手势之前都在用 IMU，这条捷径直接适用。
  • 烘焙图集 + 调色板行：把"形状×光照×颜色"分解成 灰度索引图 × 行调色板，换色换雾零运行时成本；覆盖率写进亮度即得黑底抗锯齿。任何 SPI 屏 + RGB565 的项目都能搬（我们 StickS3 的 AMOLED 完全同构）。
  • 加法光晕先画、不透明体后画：无深度缓冲时建立遮挡秩序的最廉价手段，且避免光晕叠加成白块。
  • 脏矩形 + 纯黑背景：三缓冲各自记账，只回擦上一帧碰过的矩形；这是 AMOLED 省电 + 降带宽的通用姿势（与我们 esp32-s3-amoled 笔记里的局部刷新思路互相印证）。
  • 固定步长 + 丢弃：240Hz 确定性物理每帧 ≤8 步、溢出丢弃——比"追时间"的变步长在嵌入式上稳得多，还让 150 秒压力测试成为可能。
  • 逻辑搬到 Guest、像素留给 Host：即使不做 WASM，这个分层也值得抄——应用层产出显示记录（矩形/精灵/文本），渲染内核集中一处优化（DMA2D/整数化），多板适配只在内核层发生。
  • 遥测即验收：fps×100、分桶耗时、清除像素数、平均深度/速度——把"效果对不对"变成没有屏幕也能断言的数字。

边界与注意：① 画家算法只对"凸 + 不透明 sprite"正确，球互相裁切或半透明物体的场景不能直接推广；② O(n²) 碰撞在 64 球封顶是刻意为之，上百物体要上空间划分；③ 陀螺仪欧拉/科里奥利项的方向 README 自述"需真机确认"，抄的时候先跑它给的测试断言；④ 图集最大 1.5× 缩放上限是烘焙抗锯齿的边界，更大的 buffer 应重烘焙而不是硬放大。
