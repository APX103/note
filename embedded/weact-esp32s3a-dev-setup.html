01 / 结论先行

  • 板子与资料：WeAct ESP32-S3-A = 乐鑫原装 ESP32-S3-WROOM-1 模组的 P2P 开发板（对标官方 DevKitC-1），硬件资料全在 WeActStudio.ESP32S3-AorB 仓库，A 版用 WROOM-1 模组、B 版用裸片 ESP32-S3-R8。
  • 本板关键引脚：USER 键（SW3）= GPIO45（按下为 HIGH，接 3V3 + 板载 10k 下拉）；RGB 灯（WS2812B）= GPIO48；BOOT = IO0。比官方 DevKitC-1 多一颗独立 USER 键。
  • 烧录铁律：本板（本机）必须走丝印 USB 的原生 USB-C 口（ESP32-S3 内置 USB Serial/JTAG，VID 303a:1001），丝印 COM 的 CH343 串口链路存在单向大块数据损坏，无法完成烧录（详见第 06 节）。
  • 本机工具链零新增：arduino-cli 1.5.1 + esp32:esp32 3.3.10 直接可用，FQBN 加参数即可，不用装任何板包。

03 / 原理图引脚考古

原理图 ESP32S3-A/Hardware/ESP32_S3_A_Sch.pdf 是单页 Altium 导出 PDF。纯文本提取（pypdf）能拿到全部网络标号但丢失空间关系，需要两步走：

pip3 install --user pypdf pypdfium2   # 文本提取 + 定位渲染

# 第一步：全文提取，确认模组型号与按键/LED 的存在
# KEY@BOOT / KEY@RESET / KEY@USER —— 三颗按键！
# LED3 (WS2812B)：VDD1 DOUT2 VSS3 DIN4

# 第二步：pypdfium2 搜索标签坐标，按坐标裁剪渲染 PNG 局部图
searcher = tp.search('KEY@USER')  # 拿到字符框 -> crop -> save

裁剪出的局部图交给视觉模型读取网络连接，再用 Zephyr 板级定义交叉验证，结论一致：

元件引脚备注
USER 键（SW3）GPIO45按键接 3V3、R12 10k 下拉到 GND → 空闲 LOW、按下 HIGH（主动高，串口实测确认）
RGB 灯（LED3，WS2812B）GPIO48DIN 经 0R 电阻接入
BOOT 键（SW2）GPIO0常规 strapping 用法
RESET 键（SW1）EN/CHIP_PU—
USB 转串口CH343P走 COM 口 USB-C，接 UART0（GPIO43/44）
原生 USBGPIO19/20另一个 USB-C 口，S3 内置 USB Serial/JTAG
两个实战细节：① GPIO45 是 strapping 引脚（VDD_SPI 电压选择），WeAct 用 10k 下拉保证上电采样为 0（3.3V flash 供电），作普通输入用没问题；② 原理图上按键极性两次视觉识别有分歧，最终用「固件开机采样空闲电平」的自适应写法一劳永逸（见第 05 节），上板实测空闲电平 = 0、按下 = HIGH。

判型信息与仓库 Tool/WeAct-ESP32S3N16R8-mpy-V1.2.bin 的命名互为印证。--no-stub 是因为 stub 上传在本板 COM 口必挂（见第 06 节），ROM 直读虽然慢但稳。据此定 FQBN：

esp32:esp32:esp32s3:FlashSize=16M,PSRAM=opi,CDCOnBoot=cdc
参数取值原因
FlashSize16M16MB 板载 Flash
PSRAMopiR8 = 8MB Octal PSRAM，选错运行时堆分配失败
CDCOnBootcdcSerial 走原生 USB CDC，日志直接在 USB 口看（默认 Disabled 时日志走 UART0/COM 口）

05 / 按键点灯 Demo

行为：每按一次 USER 键，RGB 依次 红 → 绿 → 蓝 → 白 → 灭 循环；串口打印事件与极性判断。WS2812 用 Arduino 核心内置的 neopixelWrite()（RMT 驱动），零外部依赖：

#define KEY_PIN 45   // SW3 USER，空闲 LOW / 按下 HIGH
#define RGB_PIN 48   // LED3 WS2812B

static const uint8_t kColors[][3] = {
    {0,0,0},{32,0,0},{0,32,0},{0,0,32},{32,32,32}};  // 灭红绿蓝白
static const char *kColorNames[] = {"灭 OFF","红 RED","绿 GREEN","蓝 BLUE","白 WHITE"};
static int colorIdx = 0, idleLevel = -1;
static bool pressed = false;
static uint32_t lastChangeMs = 0;

void setup() {
  Serial.begin(115200);
  delay(300);
  neopixelWrite(RGB_PIN, 0, 0, 0);
  pinMode(KEY_PIN, INPUT);          // 板载 10k 下拉决定空闲电平
  delay(200);
  idleLevel = digitalRead(KEY_PIN); // 自适应极性：按下 = 电平翻转
  Serial.printf("KEY 空闲电平 = %d，即按下时为 %s\r\n",
                idleLevel, idleLevel ? "LOW" : "HIGH");
}

void loop() {
  bool now = digitalRead(KEY_PIN) != idleLevel;
  if (now != pressed && millis() - lastChangeMs > 30) {  // 30ms 消抖
    lastChangeMs = millis();  pressed = now;
    if (pressed) {
      colorIdx = (colorIdx + 1) % 5;
      neopixelWrite(RGB_PIN, kColors[colorIdx][0],
                    kColors[colorIdx][1], kColors[colorIdx][2]);
      Serial.printf("KEY 按下 -> RGB: %s\r\n", kColorNames[colorIdx]);
    }
  }
  delay(5);
}

编译一次通过：319,504 字节（24% APP 区），全局变量 22.6 KB（6% RAM）。上板串口实测输出 KEY 空闲电平 = 0，即按下时为 HIGH，与原理图分析一致。

06 / 攻防战：CH343 口烧录八连败

这是本次最有价值的部分，完整记录排障树。症状：线插 COM 口（CH343P，macOS 识别 VID 1a86:55d3，走 Apple 通用 CDC 驱动，设备名 cu.usbmodem*），esptool 连接、同步、读芯片信息、擦除全部正常，唯独 stub 上传必失败：

#尝试结果
1esptool 4.7 / 115200，默认复位写 RAM 超时（0107）
2arduino-cli（esptool 5.3）/ 921600stub 校验错误（checksum）
3同上 / 115200校验错误
4pip esptool 4.7 / 460800、230400超时
5venv 装 esptool 3.3（另一代 stub 二进制）/ 115200、921600超时
6先 no-stub 进 bootloader，再 --before no_reset 链式 stub 写（排除 DTR/RTS 自动复位干扰）超时
7检查 macOS tty 层：termios.tcgetattr 实测 iflag/oflag/lflag 全 0（纯 raw，无 IXON/OPOST 污染）排除
8monkey-patch pyserial，把每次写入拆成 64 字节小块（排除单次大写入被驱动截断）超时（5653 字节全部发完，等不到 ROM 应答）
—--no-stub write_flash 直写擦除成功后报 0105: Requested resource not found —— ESP32-S3 ROM 不提供写 flash 命令，此路天生不通

定性证据链

  • 芯片→电脑方向完全正常：flash 擦空后芯片 boot 循环刷屏 invalid header: 0xffffffff，2 秒稳定收到 22 KB，无一错字。
  • 小命令双向正常：sync、chip_id、flash_id、erase 这类几十字节的小包全部秒回。
  • 只有「电脑→芯片」的持续大块数据必坏：esptool 5.3 明确报 checksum error（收到数据的 MD5 与发出不符，字节级损坏实锤）。

结论：CH343 发送 → ESP32-S3 RX0 这段链路（板级信号完整性/器件，或 Apple CDC 驱动深层 bug）在持续传输时损坏数据。波特率、esptool 版本、复位时序、tty 层、写入分块全部排除后，软件侧无牌可打，判定为硬件级问题。

方法论沉淀：串口烧录排障按「方向 × 包大小」二维分诊——读 OK + 小命令 OK + 大块挂 = 发送链路问题，别在协议层空转，直接换物理通道。另外两个知识点：① S3 的 ROM 不支持 no-stub 写 flash（读取可以），stub 是硬需求；② no-stub 尝试的擦除是真实生效的——本次 bootloader 就是这么被擦掉的（板子没砖，ROM 下载模式永远在；原厂 MicroPython 备份就在仓库 Tool 目录，可随时刷回）。

07 / 终局：原生 USB 口一把过

线换到板另一个 USB-C（丝印 USB），Mac 立刻识别出新设备 /dev/cu.usbmodem21201，描述 "USB JTAG/serial debug unit"，VID 303a:1001（Espressif）——这是 S3 芯片内置的 USB Serial/JTAG，硬件级复位进下载模式，不依赖任何外部电路：

BOOTAPP=~/Library/Arduino15/packages/esp32/hardware/esp32/3.3.10/tools/partitions/boot_app0.bin

esptool.py --chip esp32s3 --port /dev/cu.usbmodem21201 \
  --before usb_reset --after hard_reset write_flash \
  0x0     build/*.bootloader.bin \
  0x8000  build/*.partitions.bin \
  0xe000  "$BOOTAPP" \
  0x10000 build/*.ino.bin

# Wrote 319504 bytes in 2.4 seconds — Hash of data verified ✓

复位后固件自启，串口横幅、极性判断、按键事件全部按预期输出。原生 USB 通道从此为这块板子的唯一烧录/调试通道；COM 口只剩「理论上的日志口」用途（本机连日志都建议别指望它）。

若哪天要用 arduino-cli 一条龙：arduino-cli upload -p /dev/cu.usbmodem21201 -b <FQBN> 同样走原生 USB，esptool 会自动识别 USJ 设备。
