01 / 需求与最终效果

设备上电后直接进入黑底白色液体画面。液体根据板子的倾斜和晃动流向不同方向；小倾角缓慢流动，大倾角加速更明显，回正后保留一段惯性再逐渐停下。

最初希望约半屏发白。实机体验后，需求调整为：约 1/3 屏幕的液体、更多更小的粒子、内部无空洞、更柔和的冲击与更明显的阻尼。

AMOLED 像素自行发光，没有独立背光。这里的“白色水珠”最终表现为连续白色区域，而不是把整个背景点亮。

物理粒子和屏幕像素不是一一对应：900 个粒子负责动力学，92×112 的密度图负责表面重建，再以 4 倍像素扩展显示到 368×448 屏幕。

04 / USB、BOOT 与完整备份

最初扫描时还没有板子串口；用户插入后出现了 /dev/cu.usbmodem31301，无需按 BOOT。通过实机查询确认是 ESP32-S3、16 MB Flash 和 8 MB PSRAM。

ls /dev/cu.*
ioreg -p IOUSB -w 0

cd /Volumes/ssd/main_link/work/ESP32-S3-Touch-AMOLED-1.8
PY="$PWD/.local-tools/espressif/python_env/idf5.5_py3.11_env/bin/python"
PORT=/dev/cu.usbmodem31301
"$PY" -m esptool --chip esp32s3 -p "$PORT" flash_id

BOOT 是进入下载模式的备用方法，不是“进入了错误模式”。正常先尝试自动连接与复位；自动握手失败时，再按住 BOOT 配合 RESET 进入下载模式。更换 USB 插口后应重新确认端口名，数据线需要支持数据传输。

在首次写入前读取原机 16 MB Flash

"$PY" -m esptool --chip esp32s3 -p "$PORT" -b 921600 \
  read_flash 0 0x1000000 \
  .local-tools/original-flash-20260910.bin

shasum -a 256 .local-tools/original-flash-20260910.bin
wc -c .local-tools/original-flash-20260910.bin

本次实际读出 16,777,216 字节，约耗时 209.9 秒。备份以及旁边的 SHA-256 校验文件保留在 SSD，不上传到 Note。它是整片 Flash 备份，含当时应用、分区表和数据分区，不只是一个 app.bin。

二次调整粒子与阻尼前，又把第一版液体应用另存为 .local-tools/white-liquid-before-density-tuning.bin，方便比较或回退。

05 / 复用现成物理核心，而不是从头做引擎

最初写过一个粒子位置约束原型。用户提出可以使用现成物理库后，转而比较已有实现：LiquidFun 提供二维刚体与液体粒子，Bullet 是通用三维物理库的例子；但本任务只需要一个二维液体容器。

最终选中 Vateva/Esp32FluidSimulation8x8：上游已经在 ESP32-S3 + QMI8658 上做了由加速度控制的 FLIP/PIC 液体，区别主要在于它使用 8×8 LED。直接移植它的物理核心，比引入完整通用引擎更贴近任务。

上游固定提交为 136ec526f98222504692033d1dfe92ea6c2c8fe3，MIT 许可。工程保留 grid.cpp、grid.h、particle.h，并记录来源与许可；去掉 Arduino、LED、按键和网络等无关依赖。

LiquidFun 只做了候选调查，没有接入最终固件。最终的压力求解、粒子与网格速度交换来自 FLIP 核心；屏幕、IMU 适配、表面重建、阻尼和调度由本工程完成。

“能否塞进 Flash”和“能否实时运行”需要分开判断。本次最终应用约 301 KiB，实际难点是帧预算、内存访问、浮点运算和整屏传输。

从 IMU 到位移

1 · 测量QMI8658 读取加速度，单位 m/s²。
2 · 映射轴方向、偏置、灵敏度与轻度滤波。
3 · 求解加速度积分成速度，再更新位置与压力。
4 · 显示粒子密度 → 连续白色液面 → RGB565 DMA。

不把加速度向量归一化：倾角小，屏幕平面内的重力分量也小；倾角大，驱动力更明显。加速度计也会反映手持晃动产生的加速度，因此不用把“角度”直接当作移动速度。该实现没有完整刚体姿态融合或三维容器旋转动力学。

// 最终 IMU 映射；轴符号延续实机工作的设置。
#define IMU_SWAP_XY 0
#define IMU_X_SIGN (-1.0f)
#define IMU_Y_SIGN (1.0f)
#define IMU_X_BIAS 0.0f
#define IMU_Y_BIAS 0.0f
#define ACCEL_GAIN 0.18f

// 轻度滤波，保留幅值差异。
ax += 0.45f * (IMU_X_SIGN * (x - IMU_X_BIAS) * ACCEL_GAIN - ax);
ay += 0.45f * (IMU_Y_SIGN * (y - IMU_Y_BIAS) * ACCEL_GAIN - ay);

读数中断超过 250 ms 时停止施加旧加速度，串口显示 STALE；正常为 IMU=OK。传感器配置参考原示例：4g 量程，250 Hz 加速度与陀螺仪采样；液体只消费加速度。

每次 FLIP 步进

  1. 积分加速度、限制每轴速度、更新位置。
  2. 用空间哈希进行两轮粒子分离，再处理四壁碰撞。
  3. 标记液体网格、清理速度与权重。
  4. 粒子速度传到网格，归一化，恢复固体边界条件。
  5. 计算密度，求解不可压缩性，再把网格速度传回粒子。
  6. 对求解后的速度执行阻尼与上限，防止压力修正重新注入过大速度。

双核与 DMA 的数据所有权

核心 1 上的物理任务以 40 Hz 目标频率运行。核心 0 的主任务读取 IMU，在互斥锁内更新输入并复制粒子快照，随后释放锁、绘制快照。这样渲染不会读到修改了一半的粒子数组，物理计算也可以和显示重叠。

物理任务若超出一个周期，会让出 CPU 并重新对齐调度，不无限追赶积压。显示使用 64 行 DMA 条带，收到传输完成信号后才复用缓冲区。物理任务栈为 4096 字节。

07 / 从 4.4 FPS 到 26.7 FPS

优化依据是板上计时，不使用 Mac 的执行速度推断 MCU 性能。串口分别报告物理计算与渲染耗时。早期单线程日志中的 physics 可能包含一帧内多次物理步进；最终双核日志报告单次物理步进，不能直接当作同一种指标比较。

阶段实测 FPS主要变化 / 发现
1000 粒子初版4.4每帧物理约 134 ms，渲染约 92 ms；Flash 够用，计算和传输是瓶颈。
热点运算与步进调整8.8减少物理追赶步数；安全实现快速逆平方根；降低重复浮点与条带开销。
600 粒子、低成本扩展15.2不再逐个输出像素做双线性插值；一份灰度样本扩展成 4×4 像素。
缓存密度核约 17用预计算的子像素核减少每帧重复浮点运算；减少压力迭代。
40 Hz + 64 行 DMA25.2单次物理约 8.6 ms，渲染约 24.4 ms；形成第一版可用效果。
900 小粒子 + 去孔洞16.9更细的压力网格和新增重建处理提高了单核负载。
最终双核26.7物理约 13.1 ms、渲染约 30–31 ms，可并行重叠；IMU 和空闲堆稳定。

utils.h 中的上游逆平方根实现原本用指针强转并假定 long 为 32 位；这不适合直接拿到 64 位 Mac 做验证。改为 uint32_t 和 memcpy 转换位表示，再做两次 Newton 修正，避免严格别名与位宽问题。热路径的 clamp 使用比较，网格源文件开启 -freciprocal-math。

密度核事先按 4×4 子像素相位缓存，最终每个核为 7×7。密度图只有 92×112，粒子足够细，但无需把 164,864 个物理屏幕像素都放进求解器。

08 / 三个体验问题的修复

问题一：液体内部像有气泡

用户看到的孔洞并不全是“粒子数量不足”。粒子分离、局部密度波动与显示阈值共同造成了断开的白色表面；只加粒子并不能保证内部连续。

  • 增加粒子数量并缩小半径，细化密度重建。
  • 调整绘制核的覆盖与阈值，让相邻粒子的贡献更容易连接。
  • 对黑色空气做从屏幕边界开始的八邻域连通标记，填白液体内部封闭的空洞；开放到外界的空气和液滴间隙仍保留。

这是明确针对“无气泡液体”外观的表面重建规则，不等同于物理求解器已完整模拟真实水体。完成灰度图后复用密度数组作为队列，避免再分配一份大缓冲区。

问题二：稍微倾斜就猛烈乱冲

原始灵敏度偏高，FLIP 动量保留也较强。更关键的是：压力修正本身会产生速度，原先仅在修正前限速，无法约束修正后的冲击。

  • ACCEL_GAIN 从 0.6 改为 0.18，即旧版的 30%。
  • FLIP_RATIO 从 0.94 改为 0.80，增加 PIC 的局部平滑作用。
  • 加入按时间步计算的 exp(-2 × dt) 速度阻尼。
  • 压力密度修正系数最终降到 0.05；在初始静止布局中校准参考密度，避免第一下 IMU 冲击改变参考状态。
  • 求解后继续施加阻尼，并把每轴速度限制在 ±0.35 m/s；墙面回弹从 0.15 降到 0.03。

问题三：液体量改为约 1/3 屏

600 个较大粒子改为 900 个小粒子。最终虚拟粒子半径约 1.9 mm，旧版约 3 mm。虚拟容器为 0.20×0.24 m，这些是模拟尺度，不是屏幕的真实尺寸。

仅缩小粒子时，原压力网格过粗，测试中液体仍会膨胀到接近半屏。把压力网格从 20×24 细化到 30×36 后，再微调半径，主机在连续摇晃、释放、重新静置的测试序列中得到 34.8% 覆盖率。初始布局和最终静置轮廓会略有不同，覆盖率不是强制裁切出来的固定矩形。

./scripts/idf.sh -C liquid -p /dev/cu.usbmodem31301 monitor

# 也可以合并为一次开发命令：
./scripts/idf.sh -C liquid -p /dev/cu.usbmodem31301 build flash monitor

monitor 使用 Ctrl+] 退出。串口被 monitor 占用时，先退出再执行下一次烧录。成功烧录的关键输出是数据哈希校验通过，随后 Hard resetting via RTS pin，板子复位进入新应用。

理解烧录偏移

本次构建生成的布局：bootloader 在 0x0，分区表在 0x8000，应用在 0x10000。常规烧录使用 idf.py flash 读取构建生成的参数；修改分区布局后不要继续照抄旧偏移。

# 脱离 idf.py 时，优先使用当前构建生成的参数文件。
PROJECT=/Volumes/ssd/main_link/work/ESP32-S3-Touch-AMOLED-1.8
PY="$PROJECT/.local-tools/espressif/python_env/idf5.5_py3.11_env/bin/python"
cd "$PROJECT/liquid/build"
"$PY" -m esptool --chip esp32s3 -p /dev/cu.usbmodem31301 \
  -b 460800 --before default_reset --after hard_reset \
  write_flash @flash_args

以下是需要回到本次开发前状态时使用的恢复命令，开发过程中没有执行恢复。它会恢复备份中的整片内容，包括旧数据分区。

cd /Volumes/ssd/main_link/work/ESP32-S3-Touch-AMOLED-1.8

# 先核对文件尺寸和校验值。
wc -c .local-tools/original-flash-20260910.bin
(cd .local-tools && shasum -a 256 -c original-flash-20260910.sha256)

"$PY" -m esptool --chip esp32s3 -p /dev/cu.usbmodem31301 \
  -b 921600 write_flash 0x0 .local-tools/original-flash-20260910.bin

11 / 本次踩到的坑与排查顺序

现象本次处理
没有串口检查 USB 数据线、重新插入、列出 /dev/cu.*；本次插入后即被识别，不需要先按 BOOT。
IDE 可能装过工具，但命令不可用先查已有 IDF 与 Python。最终复用 Python 3.11，另外在 SSD 安装 IDF，不依赖 IDE 状态。
首次下载报域名解析失败发生在受限执行环境；授权联网执行后正常下载，不是固件工程本身的错误。
FreeRTOS 编译错误连锁刷屏根因是包含顺序：freertos/FreeRTOS.h 必须在 freertos/semphr.h 之前。修正根因后恢复构建。
Mac 上快速逆平方根存在未定义行为移除指针别名转换和 32 位 long 假设，使用固定宽度整数与 memcpy。
白色区域破洞、缩小粒子后仍接近半屏联合处理显示核、封闭空气、参考密度和压力网格分辨率，不只堆粒子。
轻微倾斜冲击太强检查加速度增益、FLIP/PIC 比例、压力修正推力及求解后的速度，而不只在输入端限速。
能编译但运行不流畅分别测量物理和绘制耗时；缓存核、减少重复运算、优化 DMA 条带，最后利用双核重叠。
测试阈值因几何变化失效重新检查实际位移与边界，采用相对容器尺度的断言；不把旧半屏参数写死成新需求的标准。

后续调手感建议一次只改一组参数：先调 ACCEL_GAIN，再调阻尼与 FLIP 比例，最后调回弹。粒子半径、压力网格和数量是相互关联的，应一起看静置覆盖率与动态体积表现。
