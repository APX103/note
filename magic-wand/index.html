§0决策速览

所有"二选一/多选一"的悬而未决项，在这里一次定死。理由见后文对应章节。

决策项✅ 定案一句话理由
无线方式ESP-NOW（不用 BLE，不用星闪）无连接无配对、延迟毫秒级；仓库已有 ESP-NOW 对讲方案经验；和唤醒词同一块 S3 共存无压力。详见 §2。

杖头灯先用板载屏幕/LED 代替，后期外贴 1 颗 WS2812Demo 阶段验证交互逻辑，不必先做外形。
语音唤醒ESP-SR WakeNet 内置唤醒词（"Hi, 乐鑫"），离线S3 官方离线方案，免费且现成；自定义唤醒词要乐鑫定制服务，Demo 不值得。
手势识别IMU 6 轴 → int8 一维 CNN（约 3.4k 参数）比"特征工程 + 决策树"稳，比 RNN/Transformer 简单得多；3 个手势 + 背景类，一个小 CNN 足够。
端侧推理TFLite Micro；不行就手写前向（~100 行 C）模型小到可以退化为"权重数组 + 手写 conv1d"，无库依赖也能跑，双保险。
开发框架Arduino（arduino-cli，存量工具链）刷机流程已在 Mac 上验证过；ESP-SR 有 Arduino 库支持。若唤醒词这条路卡壳，备选 ESP-IDF（见 R1）。
原则：这是一个玩具 Demo。每个决策都选"最快能玩起来"的那条路，所有"以后再说"的东西集中放在 §9。
2026-09-19 更新：唤醒词已按"自研复刻 WakeNet"路线落地——ESP32 语音唤醒完全教程（33KB int8 模型、留出语音召回 100%、纯 C 运行时已本机对拍通过），全部代码在 wakenet/ 目录。M1 不再依赖 ESP-SR 内置词，"Lumos" 即唤醒词。

§1玩法与状态机

1.1 演示脚本（60 秒完整流程）

  1. 出场：魔杖静置，灯全灭，只监听唤醒词（省心：不会误触发任何东西）。
  2. 唤醒：说唤醒词 → 杖头灯亮起，金色呼吸，同时激活手势识别。
  3. 施法：对远处画一个圈（G1） → 杖头灯闪一下白光后熄灭，同时远程灯暖白渐亮——"魔法被发射出去了"。
  4. 收回：手臂横挥（G2） → 远程灯渐隐熄灭，杖头灯重新亮起——"魔法收回来了"。
  5. 谢幕：握杖摇两下（G3） → 远程 + 杖头全部熄灭，回到睡眠等下一次唤醒。
  6. 兜底：激活状态下 60 秒无任何操作，自动全灭回睡眠（防忘关）。

1.2 状态机

整个系统只有 3 个状态、4 类事件，一张图说清。魔杖和远程灯各自跑一份同构的小状态机，靠无线指令保持步调一致。

图 1 · 魔杖状态机。进入「杖灯亮」即杖头亮、远程灭；进入「远灯亮」即杖头闪白后灭、远程亮；回到「睡眠」即全部熄灭。G3 在两个激活状态下都有效（从「远灯亮」触发时走与超时同一条路径）。远程灯侧只被动接收指令切换亮灭，无独立决策。
当前状态事件动作下一状态

远灯亮G2 横挥发 LAMP_OFF；杖灯亮杖灯亮

§2无线选型：为什么定 ESP-NOW

候选三个：BLE、ESP-NOW、星闪（NearLink/SLE）。这是本方案唯一需要"拍板"的大分叉，先给结论再给对比。

✅ 定案：ESP-NOW。 它不是"蓝牙或星闪"二选一里的一个，但严格优于这两者在本玩具上的表现：免配对、免连接管理、点对点延迟几毫秒、代码量几十行，且和离线唤醒词同一块 ESP32-S3 共存。仓库里的 ESP-NOW 对讲方案（StickS3 ↔ AMOLED 板）已经把最不确定的路踩过了。
维度ESP-NOW ✅BLE（NimBLE）星闪 SLE
现有硬件可直接用是（StickS3 / AMOLED 板都支持）是（S3 带 BLE5）否，需另购 WS63/Hi3861 等新板
离线唤醒词生态ESP-SR 与 WiFi 同栈共存，成熟同左（BLE 与 WiFi 共存稍复杂）S3 上的 ESP-SR 用不上；星闪芯片无现成离线唤醒
连接管理复杂度无连接，注册对端 MAC 即收发需 Central/Peripheral 角色 + GATT 服务/特征值 + 连接参数，代码量数倍需 SLE 连接流程 + 新 SDK 学习成本
点对点延迟典型 <10ms受 connection interval 影响，几十~几百 ms低（理论优势）
室内距离~20–50m，玩具足够类似类似或更好（玩具无感）
团队/仓库既有经验已有 ESP-NOW 对讲设计文档无仅前期调研兴趣
为什么星闪留到 v2：星闪本身诱人（低延迟、抗干扰），但对这个 Demo 它带来的是"换全套硬件 + 换工具链 + 放弃现成唤醒词"三重成本，收益（延迟再降几毫秒）完全无感。等哪天做"真·量产魔杖"再把它当正式候选。
什么时候会推翻这个决定：如果以后要接手机 App 控制、或要做多房间穿墙遥控，再评估 BLE / 加网关。Demo 不预留这些接口（YAGNI）。

§4手势识别流水线（技术核心）

"手势"其实是动作模式分类：把杖挥动时 1 秒的 IMU 六轴数据喂给一个小 CNN，输出 4 类之一。全流程：上板采集 → PC 训练 → 量化部署。

图 2 · 系统架构。两块存量板，中间一条 5 字节的 ESP-NOW 指令信道 + ACK 回执。魔杖是唯一"有脑子"的设备，远程灯是纯执行端。

4.1 数据采集（上板采，不在 PC 端造数据）

  • 魔杖固件加一个"采集模式"：100Hz 从 BMI270 读 ax,ay,az,gx,gy,gz，串口 115200 原样吐 CSV，PC 上一个小 Python 脚本 collect.py 按文件落盘。
  • 每人每类录 ≥40 次，分 3 个 session（不同时间/手持角度/位置），外加背景类（拿着魔杖说话、走路、闲晃）。背景类和手势类一样重要，它决定了"什么时候不该触发"。
  • 命名约定：data/g1_circle/s02/r007.csv，一个文件一次动作。
ts_ms,ax,ay,az,gx,gy,gz
812345,0.12,-0.03,0.98,1.2,-0.4,0.1
812355,0.14,-0.02,0.97,3.8,-1.1,0.4
...

4.2 预处理与动作分段

  • 触发：加速度模长 |a| 相对静止基线的方差超过阈值 → 判定"动作开始"；连续 300ms 低于阈值 → "动作结束"。
  • 定长窗口：动作起点前 0.2s 起共 1.0s，重采样成固定 100 点 × 6 通道，不足补零。
  • 归一化：陀螺仪 ÷ 500dps、加速度 ÷ 4g 定幅缩放后 int8 量化。不搞减重力、不搞滤波——BMI270 数据对这种量级的手势足够干净，多一步预处理多一个坑。

4.3 模型（小到可以手写）

输入 : 6 通道 × 100 点（int8，1.0s @ 100Hz）
结构 : Conv1D(16, k=7) → ReLU → Conv1D(32, k=5) → ReLU → GAP → Dense(4) → Softmax
规模 : ≈ 3.4k 参数 · int8 全量化后 ~4KB · 单次推理 < 10ms
类别 : G1 画圈 / G2 横挥 / G3 双摇 / 背景(none)
  • PC 端 PyTorch 训练，导出 int8 tflite；上板用 TFLite Micro 跑。
  • 双保险：这个规模就算 TFLM 库出幺蛾子，也可以用脚本把 int8 权重导成 C 数组、手写 ~100 行 conv1d 前向，零第三方依赖。
训练第一大坑：验证集必须按 session 切分（session 1、2 训练，session 3 验证）。如果把同一次录制的相邻窗口随机分到训练/验证两边，准确率会虚高到 99%，上板现原形。

4.4 三个手势为什么这么设计（可换，但按此最稳）

手势动作IMU 特征（为什么不易混）触发效果
G1 画圈手腕画一个圆某轴角速度呈完整正弦周期（~0.5–1Hz），特征极强杖灭 · 远灯亮
G2 横挥手臂水平快速一挥x 轴加速度单脉冲 + y 角速度尖峰，短促（<0.4s）远灯灭 · 杖亮
G3 双摇上下摇两下（像摇体温计）两个清晰加速度峰 + 明显节奏间隔，与单脉冲可分全部熄灭

备选手势（如果某个不好分）：画 Z、竖挥、敲两下。原则：时长和轴分布差异越大越好分。

4.5 触发策略（防误触发三件套）

  1. 仅激活状态识别：唤醒之前手势模型完全不跑（还省电）。
  2. 置信度门槛：Softmax 最大概率 > 0.8 才算命中，否则当背景丢弃。
  3. 冷却期：命中后 800ms 内忽略新动作（一次挥动只会被切成一次窗口）。

§5无线协议（ESP-NOW）

5.1 帧格式

typedef struct __attribute__((packed)) {
    uint8_t magic;  // 0xA5 固定帧头，快速过滤环境里的其他 ESP-NOW 包
    uint8_t ver;    // 协议版本 0x01
    uint8_t seq;    // 发送序号，每次发送递增（接收端用它去重重发包）
    uint8_t cmd;    // 0x01 LAMP_ON | 0x02 LAMP_OFF | 0x03 ALL_OFF | 0x10 ACK
    uint8_t crc8;   // 覆盖前 4 字节
} wand_pkt_t;       // 共 5 字节（ESP-NOW 单包上限 250B，绰绰有余）

5.2 可靠性与绑定

  • ACK + 重发：远程灯收到合法指令立即回 ACK(seq)；魔杖 30ms 内没等到就重发，最多 3 次。
  • 天然兜底：就算 ALL_OFF 全丢，再摇一次 G3 即可，不设计复杂重传状态机。
  • 绑定：Demo 直接把对端 MAC 地址各写死一份（#define WAND_MAC / #define LAMP_MAC）。不搞扫描配对——两台设备一辈子只跟对方说话。
  • 加密：ESP-NOW 支持 PMK 的 CCMP 加密，一行配置的事，联调稳定后顺手打开。

§6固件架构

6.1 魔杖任务划分（FreeRTOS）

任务核心 / 优先级周期职责
task_audioCore0 / 最高连续mic → WakeNet，命中后向主任务发 EVT_WAKE
task_imuCore1 / 高10ms读 BMI270 → 滑窗 → 能量分段；激活状态下推理，命中发 EVT_G1/G2/G3
task_mainCore1 / 中事件驱动状态机（§1.2）+ 灯光特效 + ESP-NOW 收发 + 超时定时器

任务间只通过 FreeRTOS queue 传事件，没有任何共享变量——玩具级代码也要一眼能读。

核绑定理由：音频喂 WakeNet 对实时性最敏感（丢一帧就掉识别率），独占 Core0；WiFi/ESP-NOW 协议栈也在 Core0 但中断式工作，实测共存没问题（ESP-SR 官方 demo 即此拓扑）。IMU 与主逻辑在 Core1，互不打架。

6.2 灯光特效（体验的另一半）

时刻魔杖远程灯
唤醒金色呼吸渐亮（600ms）—
G1 施法白光爆闪一下（150ms）→ 熄灭暖白 800ms 渐亮 + 轻微烛光抖动
G2 收回金色呼吸渐亮600ms 渐隐至灭
G3 谢幕白光快闪两下 → 灭立即灭

施法时杖头的"爆闪一下再灭"是体验关键：给观众一个"魔法发射出去了"的视觉信号，而不是无声无息地转移。

6.3 远程灯固件

极简：ESP-NOW 回调（校验 + 去重 + 回 ACK）→ 灯光状态机 → 屏幕/WS2812 输出。没有 IMU、没有音频，单任务足够。

§7里程碑与验收标准

排序原则：最不确定的先做。唤醒词上板是全案最大风险点，第一周就见分晓，不行立刻降级保底。

阶段内容工作量验收标准
M0ESP-NOW 双机打通0.5 天StickS3 按键 → AMOLED 屏亮/灭；10m 隔一堵墙，连续 50 次成功率 ≥ 95%
M1唤醒词上板 ⚠️0.5–1 天安静房间 3m 内说唤醒词，10 次命中 ≥ 9 次；静置 1 小时 0 误唤醒。若 Arduino 的 ESP_SR 库在 StickS3 上跑不通 → 启动 R1 预案

M3手势模型上板1 天串口打印识别结果；现场每手势 10 次做对 ≥ 9 次；静置 10 分钟 0 误触发

总计约 3.5–4 个工作日。M0/M1 可并行（两块板互不干扰）。

§9刻意不做的事（范围控制）

  • ❌ 低功耗 / 深度睡眠优化 —— 玩具，插电或随手充电。
  • ❌ 手机 App / 云端 —— 没有需求，纯本地。
  • ❌ 自定义唤醒词（比如喊"荧光闪烁"）—— 需要乐鑫定制服务，等玩上瘾了再说。
  • ❌ 多灯组网 / 一对多 —— 就一盏远程灯。
  • ❌ OTA、配网、加密握手 —— Demo 明文跑，CCMP 一行配置顺手开，其他不碰。
  • ❌ 真实魔杖外形（3D 打印杖身、顶部灯珠工艺）—— 屏幕/外贴 WS2812 验证完玩法，外形是 v2 的事。
