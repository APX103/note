MCP 协议文件传输机制调研

调研日期：2026-08-27 ｜ 参考 MCP 规范最新稳定版 2026-07-28（次新版本 2025-11-25、2025-06-18）及官方工作组、SEP 提案与社区实践。

TL;DR

  • 结论：MCP 可以传文件，但截至 2026-07-28 版规范，协议层面没有专门的原语。所有文件传递都是建立在「工具参数是 JSON」「JSON-RPC 消息体」之上的事实约定，而非标准能力。
  • 当前主流四种做法：A. Base64 内联进工具参数（小文件）；B. 本地文件路径（stdio 同机）；C. URL 引用让 Server 自己下载；D. 两段式授权上传（预签名 URL / 不透明句柄，生产推荐）。
  • 核心设计原则：让文件字节绕开 LLM 上下文窗口，模型只接触引用/句柄。Base64 塞参数等于把文件内容当作 token 白白烧掉，还受单条消息大小限制。
  • 标准化正在进行中：File Uploads 工作组主导的 SEP-2631（files/authorizeUpload / files/authorizeDownload，"控制面走 JSON-RPC、数据面走 HTTPS 带外"）被认为是最终方案，但截至调研日仍是 Draft。SEP-2356（data URI 内联方案）已于 2026-06 关闭并被其取代。
  • 注意一个易混淆点：Resources 是服务器→客户端方向的，不能用来"客户端向服务器推文件"；Roots 已在 2026-07-28 中被废弃（它只声明目录范围，也不负责传字节）。

1. 先把问题拆清楚：两个方向、两类需求

"MCP 能不能传文件"实际包含两个相反的方向，答案完全不同：

方向含义现状
Server → Client
工具产出文件给用户		 处理完返回一张图、一段音频、一个 PDF 结果 基本已解决。工具结果的 Content 类型里就有 base64 的 ImageContent/AudioContent、EmbeddedResource（含 blob）、ResourceLink（只给 URI 让客户端再拉取）。官方工作组章程明确指出此方向"已由 Resources 与 BlobResourceContents 覆盖"，不再纳入新工作范围。
Client → Server
用户把文件交给工具处理		 上传一份 Excel/PDF/图片，让远端 MCP Server 解析、分析 至今无标准原语。这正是本文的重点，也是 File Uploads 工作组要解决的问题。
顺序也要澄清一下：MCP 里发起 tools/call 的是 Host（客户端），但「要处理的内容」通常源自用户。所谓"传文件到 MCP Server"，本质是 Client（Host）这一侧如何把用户选定的文件字节可靠地交到 Server 手里——而且最好不经过中间那个 LLM。

2. 为什么 MCP 至今没有原生文件上传

这是由协议的结构决定的，不是疏漏了一直没人做：

  • 工具输入就是 JSON Schema 约束的 JSON 对象。tools/call 的 arguments 只有 number/string/boolean/object/array 这些 JSON 类型，没有二进制类型。Content Types（image/audio/resource 等）只存在于工具结果、prompts 和 resources 里，输入参数没有对应物。
  • 二进制唯一内联手段是 base64 字符串，而它有三笔隐性成本：
    1. 烧上下文：若文件内容由模型在 arguments 里生成或回显（比如把刚才读到的文件转发给另一个 server），几 MB 的 PDF 会产生上百万 token，直接打爆 128K 甚至更大的上下文；社区在 GitHub Discussion #1197 里已有实测案例（约 195 万 token）。
    2. 消息体积：Streamable HTTP 有请求体上限，stdio 走按行分帧的 JSON-RPC，超大 base64 都容易出问题，且规范没有定义超限行为。
    3. 不可续传：一次失败就要整段重来，也没有进度语义。
  • 本指望用来传文件的 Roots 被废弃了。Roots 只是客户端向服务器声明"我允许你访问这些目录"，不搬运任何字节，而且依赖客户端实现（早期 Claude Desktop 曾直接对 roots/list 返回 Method not found）。2026-07-28 规范正式将 Roots/Sampling/Logging 列为 Deprecated，官方给出的替代说法很直白："pass directories or files via tool parameters"——用普通工具参数传路径，等于追认了"路径/引用型传参"这条民间路线。
  • 2026-07-28 还把协议改成了彻底无状态（去掉 initialize 握手与会话 ID）。这意味着未来文件机制被明确要求设计成不依赖会话状态的（SEP-2631 评审中大量讨论了这一点），也解释了为什么标准化迟迟未落地——底座先重构了。

3. 当前可落地的四种方案

方案 A：Base64 内联进工具参数（小文件）

最直接的做法：把文件内容编码成 base64 字符串放进某个 string 参数。

# Server 端（FastMCP 示例）
from fastmcp import FastMCP
import base64

mcp = FastMCP("image-tools")

@mcp.tool()
def thumbnail(image_b64: str, mime_type: str = "image/png") -> dict:
    """生成缩略图。image_b64 为不带 data: 前缀的裸 base64。"""
    raw = base64.b64decode(image_b64)
    ...
    return {"width": 128, "height": 128}
优点缺点
零基础设施依赖，任何 transport 都能用；协议兼容性最好 尺寸受限于单条 JSON-RPC 消息（实操建议 < 1MB，理想 < 几百 KB）；base33% 的体积膨胀；如果这串内容经手 LLM（生成或回显），token 成本爆炸；无进度/续传

适用：几 KB～几百 KB 的小图片、配置片段。远超这个量级请直接看方案 D。正在草案阶段的 SEP-2356 若复活，本质也是这条路的形式化版（统一为 RFC 2397 data URI 格式 data:<mediatype>;name=<filename>;base64,<data>）——可以预先把自己的参数设计成接收完整 data URI，将来无缝过渡。

方案 B：本地文件路径（stdio / 同机部署）

MCP 最经典的运行方式是宿主在本机以 stdio 拉起 Server 子进程，两者共享文件系统。此时"传文件"根本不需要搬字节，传个路径即可：

@mcp.tool()
def analyze_csv(path: str) -> str:
    """分析指定 CSV 文件。path 必须位于 workspace 目录内。"""
    p = Path(path).resolve()
    if not p.is_relative_to(WORKSPACE):   # 安全校验必须有
        raise ValueError("path outside workspace")
    return summarize(p.read_text())
优点缺点
零拷贝、零 token 开销；几十 GB 也无所谓；实现成本最低 仅限同一台机器；Server 拿到的是任意文件读权限，必须做路径规范化 + 目录白名单；云托管/SaaS 场景完全不可用；官方 filesystem reference server 即此类

适用：Claude Desktop / ZCode / Cursor 这类本地 IDE 与桌面宿主的场景——事实上这类宿主上的文件类 Server 绝大多数就是这么工作的。

方案 C：URL 引用，Server 自己去下载

客户端不给字节，给一个 Server 可访问的 URL（对象存储预签名链接、内网 HTTP 地址等），Server 在执行工具时自行拉取：

{
  "name": "analyze_document",
  "arguments": {
    "url": "https://oss.example.com/docs/report.pdf?X-Amz-Signature=...",
    "mime_type": "application/pdf"
  }
}
优点缺点
字节完全不过 LLM、不过 JSON-RPC；天然支持超大文件；对象存储生态现成 存在 SSRF 风险——Server 必须做目标域白名单或只接受自己签发的 URL；需要双方都能触达同一存储；签名有效期管理

适用：企业内部已有 OSS/S3/MinIO 基础设施的场景，是方案 D 的"省钱简化版"。与 D 的区别在于：D 由 Server 主动签发上传地址、闭环可控；C 由调用方随手给 URL，信任链更弱。

方案 D：两段式授权上传 / 不透明句柄（生产环境推荐）

这是社区经过长期实践收敛出的事实标准模式（GitHub Discussion #1197 中被称为生产级模式）：把「传字节」和「发起处理」拆成两步，JSON-RPC 里只流动一句柄。

 ┌──────┐          ┌─────────┐            ┌──────────┐        ┌──────────┐
 │ 用户 │          │Host/LLM │            │MCP Server│        │ 对象存储  │
 └──┬───┘          └────┬────┘            └────┬─────┘        └────┬─────┘
    │ 选定 report.pdf    │                      │                   │
    ├──────────────────►│ ① tools/call         │                   │
    │                   │   request_upload{}   │                   │
    │                   ├─────────────────────►│ 签发一次性上传凭证  │
    │                   │ ◄────────────────────┤                   │
    │                   │ {uploadUrl, fileId}  │───2.create key───►│
    │                   │                      │                   │
    │                   │ ② Host 自己 HTTP PUT multipart│◄────────┤
    │                   │    （不经 LLM！）       │    回执/ETag     │
    │                   │                      │                   │
    │                   │ ③ tools/call         │                   │
    │                   │   process(file_id:"…")│                  │
    │                   ├─────────────────────►│ 从存储读取并校验处理  │
    │                   │ ◄──resource_link(URI)─┤ ④ 结果只回句柄/URI │
 ┌──┴───┐               │                      │                   │
 └──────┘ ⑤ 宿主按 URI 取回成品展示                 │                   │

三个关键变体：

  • D1 · Server 签发预签名 URL：如上面时序，Server 提供 request_upload 类工具返回存储预签名 PUT 地址。务必封装成一个工具做完——Tigris 的实践表明模型不会自主串联多个原子工具，必须合并成单一高阶工具，甚至在返回文本里内嵌指令强制模型回显链接。
  • D2 · Host 中转直传：更彻底的形态——模型根本不知道上传这件事。Host 在人机确认环节拦截到「该工具有个 file 参数」，弹出原生文件选择器，宿主直接把字节 POST 到服务端存储，再把不透明 file_id 注入 arguments。模型全程只见到类似这样的小对象： 
    {
  "file_id": "file_01J9XY…",
  "name": "report.xlsx",
  "mime_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
  "size": 4281932,
  "sha256": "uU0nuZNN…"
}
    这就是将来 SEP-2631 定稿后的样子（见第 5 节），现在照此设计即可平滑升级。
  • D3 · 出参对称用 resource_link：处理完的大结果同样不要塞回 content，而是返回 {"type":"resource_link","uri":"mcp-file://…"} 让宿主另路取回，保证双向大流量都不碰 LLM 上下文。
优点缺点
字节零 token；支持任意大文件；句柄可加签名/时效/权限=可控攻击面最小；与 SEP-2631 设计同构，等于提前实现了未来的标准 实现量最大：要有存储介质、签发/校验逻辑、甚至分块与完成通知；跨厂商存储各有 API；Host 若要原生体验需配合改造

适用：一切面向公网或多人使用的 SaaS 型 MCP Server、处理文档/媒体的服务。OpenAI 与 Anthropic 双方成员参与的 SEP-2631 正是把这套民间实践写进规范（下节详述）。

4. 协议内相关原语盘点：哪些"看起来能传文件"但不能

排查规范时会遇到一堆名字沾边的原语，逐一澄清它们的真实方向和能力边界：

原语方向能不能承担"客户端→服务器传文件"
resources/read / ResourcesServer → Client❌ 反方向。Resource 由 Server 声明、Client 来读。BlobResourceContents 确实支持 base64 二进制，但那是给 Server 分发用的。
EmbeddedResource / ResourceLink（工具结果内容）Server → Client❌ 属于工具结果，恰好是反向通道；result 里拿来做 D3 的产物交付倒是正合适。
RootsServer → Client（列举目录）❌ 只声明"可访问范围"，不传字节；严重依赖客户端支持；2026-07-28 已 Deprecated，官方建议改用工具参数传路径/URI。
Elicitation（表单/URL mode）/ MRTR input_requiredServer → Client 请求补充输入⚠️ 半个。它能解决"中途让用户填点东西"，但表单值是字符串——最多装下一个 data URI 或路径。2025-11-25 新增的 URL mode elicitation 允许宿主打开一个外部页面完成带外交互（可承载上传），但它自身在上个版本又被 MRTR 模式重塑，仍是演进中的拼图。SEP-2356 的初稿正是想借 elicitation 请求声明 requestedFiles。
Tasks（实验性，现为 io.modelcontextprotocol/tasks 扩展）Client ↔ Server 任务生命周期❌ 只管异步任务的状态轮询与更新，不管载荷。上传过程若是长任务可用它汇报进度，但字节仍要走方案 C/D。
SamplingServer → Client 请求推理❌ 与文件无关，且已随 Roots 一同废弃。
一句话总结这张表：MCP 的"管道"里从来就没有为客户端上行的大载荷留过口子，它天生假设 Server→Client 下行、Client→Server 只有薄薄的 JSON 参数——所以才催生了上文各种带外模式。

5. 标准化进展：File Uploads 工作组与 SEP-2356 / SEP-2631

目前规范中尚无文件原语，但官方机器已经全速运转，值得跟踪：

5.1 时间线

  • 2024-12　社区痛点集中爆发：Discussion #1197「从客户端向服务器传文件的建议方式」成为主战场（持续活跃到 2026 年中）；同期 Issue #189 提出"参考 TUS 协议内置可恢复上传"。
  • 2026-04-23　File Uploads Working Group 正式立项（牵头人 Den Delimarsky @Anthropic，成员含 OpenAI 代表）。章程原文直指现状之痛："需要文件的 Server 今天只能靠说明书求用户提供 base64 字符串或本地路径，UX 千疮百孔"。工作组锚定两份 SEP，并列出 TypeScript 等 Tier-1 SDK 参考实现作为交付物；同时明确范围排除 Server→Client（已有 Resources 覆盖），并在章程里预留了对 streaming/chunked/presigned 等路线的评估空间。安全基准引用 OWASP ASVS V5。
  • 2026-03 ~ 05　SEP-2356「Declarative File Inputs」进入评审：在工具 inputSchema 旁挂 x-mcp-file 描述符（accept MIME 过滤 + maxSize 字节上限），让宿主据此弹原生文件选择器、并把选择结果以 RFC 2397 data URI 替换进对应 string 参数；配套 ClientCapabilities.fileInputs 能力协商与降级规则。评审中最尖锐的问题：模型幻觉风险——模型逐字生成 arguments 时可能编造 data URI 或试图吐出整份字节流，最终稿要求宿主对模型隐藏该字段、改为在确认环节注入真实值。
  • 2026-06-26　SEP-2356 被关闭，官方理由："in favor of #2631 which will likely be the more durable solution"——不再把文件字节内联进 JSON-RPC 消息体，哪怕形式优雅。
  • 2026-04 至今　SEP-2631「File Objects and Transfer」保持 Draft（作者为 OpenAI 成员 caseychow-oai，分配给 Anthropic 的 localden）。评审吸收 2356 的描述符词汇，重心转向传输契约本身；因 2026-07-28 无状态化改造，能力协商已被要求挪进 _meta。社区已在催问时间表（工作组原定五六月交付）。
  • 2026-07-28　现行最新稳定版发布，changelog 中没有任何文件原语；但同版把 Roots 送进废弃名单并给出了"目录/文件通过工具参数传递"的迁移指引，事实上终结了旧的想象空间，为 2631 让路。

5.2 SEP-2631 核心设计（未来的标准长这样）

设计哲学一句话：JSON-RPC 只当控制面，文件字节永远走 HTTPS 数据面带外传输。

// ① 能力协商（现在应放入 _meta）
"capabilities": {
  "files": { "upload": true, "download": true, "transports": ["https"] }
}

// ② 工具参数用 x-mcp-file 标注文件字段，值为 URI 字符串；
//    transferModes 决定允许内联 data: URI 还是强制带外上传
"x-mcp-file": { "transferModes": ["outOfBand"] }

// ③ 客户端请求上传授权（控制面）
{ "jsonrpc": "2.0", "id": 10,
  "method": "files/authorizeUpload",
  "params": {
    "name": "report.pdf",
    "mimeType": "application/pdf",
    "size": 248123,
    "digest": { "algorithm": "sha-256",
                "value": "uU0nuZNNPgilLlLX2n2r-sSE7-N6U4D6ZVe-_rYh2sU" }
  }
}

// ④ 服务器返回 FileTransferDescriptor（URL/token）

// ⑤ 客户端带外 POST multipart/form-data 直传端点

// ⑥ tools/call 里只出现句柄 URI：
{ "document": "mcp-file://server/file_01HXYZ" }

// ⑦ 下载侧对称地走 files/authorizeDownload 获取临时下载地址
//    注意：文件 URI 不走 resources/read，走专用命名空间解析

评审中尚未闭包、但大概率会进后续版本的安全增强：描述符必须可过期（防止永久有效的上传凭证变成攻击面）；签名覆盖策略而不只是元数据（把目标 key、Content-Type、大小上限一起签进去，类比 S3 presigned POST）；增加 files/completeUpload 完成确认步骤（服务器感知最终落库状态，同时消除"tools/call 先于上传完成"的竞态）；魔数/杀毒校验失败与配额超限的专用错误码；大文件分块与每请求上限通告。

给开发者的务实建议：尽管 SEP-2631 未合入，它的形状已经足够稳定（Anthropic/OpenAI 双方共同推进、取代 2356 的明确决议）。今天实现方案 D 时，按「参数收 URI 字符串 + 提供 authorize 类方法 + 句柄形如 mcp-file://」来设计接口，标准落地后就是无痛平移。同时保留 base64/data URI 兜底通道，这也是评审者的共识。

6. 选型决策与工程建议

你的 MCP Server 部署在哪？
│
├─ 和宿主同一台机器（stdio）
│    ├─ 处理的是本机文件？ ──────────────► 【B】文件路径 + 目录白名单
│    └─ 处理外源小文件（<几百KB）？ ──────► 【A】base64 / data URI 内联
│
└─ 远程/托管（Streamable HTTP）
     ├─ 双方都有对象存储权限？
     │    ├─ 想省事、信任调用方给的地址 ──► 【C】URL 引用（记得 SSRF 白名单）
     │    └─ 面向公网多租户/SaaS      ────► 【D】authorize + 直传 + 句柄
     └─ 暂时什么基础设施都不想搭？
          └─ 文件注定很小（<~200KB）────► 【A】，参数直接收 data URI 兼容未来标准
  • 铁律：数据不过模。任何情况下都不要让大文件的字节经由 LLM 的输入或输出来搬运。判断办法很简单——如果去掉模型、两个程序直连也能完成这个任务，那就不该把字节递给模型。
  • 小与大之间没有争议地带：< 200 KB 用 A 无伤大雅；一旦接近 MB 级，A 的每一条缺点都会同时引爆（消息体积、token、无法续传），直接跳 D。
  • 注意 2026-07-28 无状态化的连带影响：若你的上传流程依赖"先在会话里 create 了 file 再后续调用引用"，改成显式的自包含 file handle 放进每次调用的参数里，正符合新版"server-minted handles passed as ordinary tool arguments"的精神。
  • 为文件参数写清 description 并注明约束（格式、大小上限、示例 data URI）——在今天缺乏声明式标准的阶段，description 就是 Server 与宿主之间唯一的契约。

7. 安全清单

#要点说明
1永不信任客户端元数据mimeType、size、文件名都可伪造。服务端必须独立校验魔数（magic bytes）、解压深度、真实大小、摘要（SHA-256 校验或直接复算）。OWASP ASVS V5 是工作组钦定的基线。
2SSRF 防护凡是接受 URL 参数的工具（方案 C），目标必须在白名单内；更优做法是不接受外来 URL，只接受自己签发的 mcp-file:// 句柄。
3句柄三件套：绑定、时效、一次性upload URL / file_id 应绑定用户与租户、短期有效、最好一次性兑换；撤销策略明确。防止凭证泄露后被离线重放。
4授权签名覆盖策略签发上传凭证时把 bucket/key、Content-Type、maxSize 一并签入，杜绝"签了个前缀却传进了别的路径"。
5配额与速率限制文件数、总大小、并发 pending 上传数都要有上限——这是 2026 规范新增错误码分区留给实现的典型场景（-32000~-32019 区间自定义）。
6宿主侧确认涉及用户文件读取/上传的工具调用应在 UI 上显著呈现（哪个文件、发给谁），并把防"恶意/意外数据外泄"列为默认交互。
7路径穿越方案 B 必须对传入路径做 resolve + 白名单前缀比较，拒绝 ..、symlink 跳出等手法。
