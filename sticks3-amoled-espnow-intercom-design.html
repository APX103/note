0. 一句话需求与关键决策

需求：两块板通过 ESP-NOW 组成"按键说话、松开切换"的半双工对讲机——StickS3 用实体按键发起通话，AMOLED 用触摸屏虚拟按键发起通话；连接建立后保持长连接，掉线后每 5 秒低频扫描重连；同一时刻只有一方占用麦克风发送，另一方纯接收播放，互不抢占资源；全程基于 FreeRTOS 多任务，录音、播放、网络、UI 各自独立运行。

决策点选择理由
传输层ESP-NOW（无路由器、无关联、低延迟）点对点 10cm~几十米场景，延迟远低于 WiFi+MQTT
双工模型半双工 + 话权（floor）仲裁用户明确要求"一方说另一方只能听"；也省带宽一半
音频格式16 kHz / 16-bit / 单声道 PCM 起步两侧均已有该配置的实测验证代码（tuner、M5Unified）；后续可降 ADPCM
并发模型FreeRTOS：采集 / 播放 / 网络 / UI 分任务I2S 读写是阻塞的，单线程必然顾此失彼
连接语义握手 + 心跳模拟"长连接"ESP-NOW 本身无连接概念，靠应用层状态机补
重连策略掉线后每 5s 一轮短扫描（≤300ms）持续扫描会发热（用户明确要求规避）

2. 交互设计（PTT 与 UI）

2.1 交互时序（一次完整对话）

时序text
StickS3                                AMOLED
   │ ── HELLO(广播) ──────────────────▶ │   上电/重连：互相发现，绑定对端 MAC
   │ ◀─ HELLO_ACK ────────────────────  │   → 状态：已连接（心跳 1s 维持）
   │                                     │
   │ ── PTT_DOWN ──────────────────────▶ │   用户按住 StickS3 的 K1
   │ ◀─ PTT_ACK ───────────────────────  │   AMOLED 锁定为"接收方"，麦克风关闭
   │ ── AUDIO#1 ─ AUDIO#2 ─ … ────────▶ │   20ms 一帧连续发送，AMOLED 连续播放
   │ ── PTT_UP ────────────────────────▶ │   用户松开 K1，发送 flush 后释放话权
   │                                     │   两端回到空闲，AMOLED 现在可以按触摸说话
   │ ◀─ PTT_DOWN / AUDIO… / PTT_UP ────  │   （反向同理）

2.2 StickS3 界面与按键

  • K1（GPIO11 / M5.BtnA）按住 = 说话，松开 = 停止并释放话权；K2 长按 = 关机（沿用 8 月 IR 项目习惯）。
  • 屏幕四态：未连接（SEARCHING…）/ 已连接空闲（READY + 电池%）/ 我在讲（TX + 电平条）/ 对方在讲（RX + 电平条 + 丢包率）。
  • 抢话失败提示：按住 K1 但对方已先讲话 → 显示"BUSY 对方先讲"，本地麦克风不启动。

2.3 AMOLED 触摸界面

  • 屏幕下半部一个大圆钮 = PTT 虚拟按键：手指按下区域内 = 按下（发 PTT_DOWN），手指离开 = 松开（发 PTT_UP）。FT3168 的 press/release 事件天然映射，无需处理滑动。
  • 状态栏（上方）：连接状态、对端名称（STICK）、RSSI、电池；说话时大钮高亮 + 实时输入电平。
  • 听对方讲话时：显示波形/电平条（可直接搬 M5Unified Mic_FFT 的画法思路），大钮置灰表示"占用中"。
触摸 PTT 必须用"手指在区域内按下/抬起"原语（down/up），不要用点击计数——需求明确是"按住说话、松开即停"。FT3168 报点有偶发抖动，抬起判定加 50ms 去抖（期间视为仍按住）。

3. 连接管理（伪长连接 + 5 秒扫描）

ESP-NOW 是无连接协议，"长连接"在应用层实现：双方记住对端 MAC 后单向发数据即可，无需每次关联。状态机如下：

状态行为迁移
SEARCHING每 5s 发一轮广播 HELLO（连续 3 个，间隔 100ms），然后静默监听到本轮结束（总时长 ≤300ms）收到 HELLO/HEARTBEAT → 绑定 MAC → LINKED
LINKED心跳 HEARTBEAT 1s 一次（携带电池%、RSSI 回显）；音频/控制照常收发连续 3 次心跳丢失（3s）→ SEARCHING
  • 上电首轮：立即做 3 轮快速握手（不做 5s 等待），失败才进入 5s 慢周期——开机体验和省电兼顾。
  • 固定信道：双方约定死信道（默认 ch1），不启用信道跳变；ESP-NOW 收发双方必须同信道。
  • 加密可选：预共享 LMK（本地主密钥）启用 ESP-NOW 加密，防止邻设备串音；v1 可先明文+MAC 白名单。
  • 发热控制（用户明确要求）：只有 SEARCHING 态的每轮 ≤300ms 窗口内开射频扫描/广播；LINKED 态只维持 1s 心跳；绝不连续扫描。
MAC 绑定方式 v1 用"配置文件写死对端 MAC"（两台设备各烧各的固件时注入），v2 再做"首次发现即配对+按键确认"。这样把配对 UX 从首版范围里砍掉。

4. 半双工话权协议

控制帧（与音频帧共用 ESP-NOW 载荷，首字节区分类型）：

帧类型字段语义
HELLO / HELLO_ACK设备名、电池%发现与绑定
HEARTBEAT电池%、序号保活；3 丢即断
PTT_DOWN会话 ID（递增）请求话权；同时意味着"我马上要发音频"
PTT_ACK会话 ID对端确认进入接收态（话权授予）；20ms 内未收到 ACK 也照发（乐观锁，音频帧自带会话 ID 兜底）
AUDIO会话 ID、帧序号、时间戳、PCM 数据仅话权持有方发送
PTT_UP会话 ID、总帧数释放话权；接收方按序放完尾部数据后解锁 UI

4.1 仲裁规则（同时按下怎么办）

1先到先得

PTT_DOWN 先到者获得话权。后到方若本地也刚按下：比较双方 MAC（数值大者让），让方 UI 显示 BUSY。确定性仲裁，无随机退避、不会双讲。

2单向资源独占

话权持有方：麦克风 + I2S 输入 + ESP-NOW TX，本地扬声器静音（功放关闭）；接收方：扬声器 + I2S 输出，麦克风任务挂起。半双工下两块板的 codec 永远只跑一个方向，不存在 I2S 争抢——这正是"不抢占资源"的实现方式。

3释放与兜底

松开按键 → 发 PTT_UP（含总帧数，接收方把尾部放完再解锁）→ 本地释放麦克风资源 → 对端 UI 恢复可按。若 PTT_UP 丢失：接收方 500ms 无新音频帧即超时释放；话权最长 30s 强制回收（防按键卡死/掉线）。

5. 音频管线

5.1 参数与封包

项值说明
采样规格16 kHz / 16-bit / 单声道 PCM32 KB/s；两侧均有已验证实现；后续可换 IMA ADPCM（4:1 → 8 KB/s）
帧化20ms 音频 = 640 采样 = 1280 B拆 6 个 ESP-NOW 包（payload ≈ 213B + 8B 头，<250B 上限）
发送节拍每 20ms 发 6 包50 帧/s、300 包/s；1Mbps PHY 下占用约 3 成空口，安全
接收缓冲jitter buffer 60–120ms（PSRAM 环形队列）按帧序号重排、去重；欠载时做上一帧衰减重复（简易丢包隐藏）
延迟预算采集 20ms + 空口 ~10ms + jitter 80ms + 播放 20ms ≈ 130–200ms对讲机可接受（<300ms 即不觉得别扭）

5.2 两侧的采集/播放实现

  • StickS3：M5Unified 原生 M5.Mic.record()（队列式读取）+ M5.Speaker 播放；Mic_FFT 示例可直接当采集参考。
  • AMOLED：复用 tuner 的 esp_codec_dev 配置（es8311_codec_new → set_in_gain 24dB → read/write）；PA 使能后跳过前几帧统计。
两板 PSRAM 都有 8MB，jitter buffer 与发送队列放 PSRAM，不动内部 RAM（音频任务和 WiFi 缓冲都吃内部 RAM，别挤）。

6. RTOS 任务架构

用户的核心担忧："单线程的话，我按下来之后不知道该发声音还是该怎样"。方案：FreeRTOS 五任务 + 队列，音频 I/O 全部阻塞式独占跑在专职任务里，其余逻辑靠消息驱动，互不阻塞。

任务核心优先级职责 / 循环
mic_task0高话权持有时常驻：阻塞读 20ms 音频 → 打包 → 投递 tx_queue；无话权时挂起（vTaskSuspend）
spk_task0高从 jitter buffer 取整帧 → 阻塞写 I2S；欠载时静音填充
net_task1中发 tx_queue（控制帧+音频帧）；ESP-NOW 收包回调只做入队（不在 WiFi 任务里干重活）
ui_task1中按键/触摸轮询（StickS3 M5.update()；AMOLED FT3168 读点）→ PTT 状态机；屏幕 5–10Hz 刷新
conn_task1低连接状态机：心跳定时、5s 扫描调度、掉线重连

6.1 同步原语

  • tx_queue（FreeRTOS queue）：net_task 唯一发送出口，避免并发调 esp_now_send。
  • floor_mutex + 话权原子变量：ui_task 申请/释放，net_task 收到 PTT_DOWN 时授予/让位。
  • 事件组（event group）：LINKED / FLOOR_HELD / RX_STREAMING 三个 bit，任务间无锁等待。
  • I2S/codec 的打开与关闭串行化在一个函数里（谁拿话权谁开对应方向），半双工保证无并发访问。
两边工具链不同（AMOLED = ESP-IDF 原生 FreeRTOS；StickS3 = Arduino，底层同样是 FreeRTOS，xTaskCreatePinnedToCore 直接可用），任务模型可以完全对称移植。

8. 风险与开放问题

#风险/问题对策
1300 包/s 的 ESP-NOW 空口压力与丢包v1 先测实测丢包率；>5% 则上 IMA ADPCM（包数降 4 倍）或 8kHz
2ESP-NOW 与 WiFi/BLE 共存干扰两板无其他无线业务，固定信道；StickS3 用 BLE（空鼠）时勿并发
3AMOLED 的 PA 开启瞬态爆音开启后跳过前 2–3 帧（tuner 结论直接复用）
4发热（用户点名）已按"仅 SEARCHING 态 5s 一轮 ≤300ms 扫描"设计；LINKED 态 1s 心跳开销可忽略
5StickS3 250mAh 电池续航空闲态屏幕降亮度/息屏（按键唤醒）；粗估连续对讲 1–2h，v1 不做深睡
6PTT_UP 丢失 → 对端卡在接收态500ms 无音频帧超时释放 + 30s 话权强制回收
7双工具链协议不一致proto.c 共用 + 主机侧单元测试（帧序列化往返，仿 liquid 的主机侧测试纪律）

开放问题（等用户拍板）：① 对讲距离预期（同房间 / 隔墙）——决定是否开 ESP-NOW long-range 模式（TX rate 512kbps/256kbps）；② 要不要开机音量/静音键；③ AMOLED 是否也保留一个物理按键当备用 PTT（板上有 BOOT 键可复用）。
