DCMI 采集与 LCD 显示

数据怎么从传感器一路走到屏幕：DCMI 快照、DMA、缓存一致性、字节序、显示路径。

6.1 采集：快照模式 + 一帧一停

每帧流程：
  HAL_DCMI_Stop()                                  // 清 ENABLE（硬件在帧尾停）
  HAL_DCMI_Start_DMA(SNAPSHOT, 帧缓冲, 字节数/4)    // 重新使能后硬件自动等下一帧头
  等待 HAL_DCMI_FrameEventCallback → frame_ready   // VSYNC 帧完成中断
  → CPU 任意慢地读缓冲（显示/处理），无撕裂
为什么快照模式没有竞态：RM0433 的行为——传输中清 DCMI_CR_ENABLE，硬件在帧尾才真正停；重新使能后硬件自动等到下一个帧起始才开始搬运。OpenMV 依赖这个特性（其源码注释原话），因此不需要 VSYNC EXTI 门控也能拿到完整帧。省掉了中断同步的整类 bug。

DMA 通道：DMA2_Stream1、请求 DMA_REQUEST_DCMI、FIFO 满 + 字对齐 + INCB4/单拍 burst。108×80×2 = 17280 字节一次搬完（NDTR 上限 65535 远够）。

6.3 缓存一致性：帧缓冲必须 MPU 非缓存

主循环开了 D-Cache，而帧缓冲是 DMA 写、CPU 读的共享内存。不处理的表现：读到旧帧/脏数据，且现象随机。解法（H7 标准操作）：

MPU region: 0x24040000, 64KB, Normal, NON-cacheable, NON-bufferable, TEX=1
// 链接脚本把 .frame_buffer 段钉在这个地址（第 4 章）

不想动 MPU 的偷懒选择：捕获前 SCB_CleanInvalidateDCache() 手动同步——能用但每帧几微秒开销，还容易漏。

6.4 字节序：这条链路天生零转换（除了那个 dummy 字节）

OV 传感器 8-bit DVP RGB565：每像素两字节，高字节(R5G3)在前 → DCMI 按字节顺序进内存
ST7735 SPI 写 GRAM：高字节在前
⇒ 帧缓冲可以直接交给 LCD，一个字节都不用换
本模组的例外：实测每帧开头多吐 1 个 dummy 字节，像素配对应从 buffer[1] 开始。不修的话画面颜色全错（被误判成「红蓝反」）。定位方法见第 7 章坑 3。固件里显示时 +1 即修复。

6.5 显示：整体复用原厂 lcd.c 路径

自写过一个 ST7735 胶水层（引脚、SPI 参数、时序与原厂逐行一致），结果黑屏——SPI「发送成功」不等于屏幕收到（第 7 章坑 2）。最终决策：显示这种调通即用的外设，直接用已验证路径：

  • 原厂 gpio.c / spi.c / tim.c（CubeMX 外设初始化）原样进工程
  • 原厂 BSP/ST7735/ 全套（st7735.c 组件 + lcd.c 封装 + font.h 字库）原样进工程
  • 初始化序列照抄原厂 LCD_Test：RST 拉高 → RegisterBusIO → Init(TFT96 ctx) → 背光渐亮
  • 画面更新用 ST7735_FillRGBRect(x, y, data, w, h)（逐行 SetCursor + 整行发送）

两个细节：① 状态条 1 秒刷一次——每帧重刷「黑底→文字」会肉眼可见地闪；② 缩放放在传感器 ISP 里做（5.7 节），CPU 与 DMA 带宽全省。

6.7 照明 LED 与 KEY

  • KEY（PB1，高有效）切换白光照明（PE2 高=亮），15 秒自动关闭——LED 贴着传感器会加热模组
  • P9/IR 引脚（PG3/PE9）永远悬空：极性未标注，驱动低电平疑似让 IR 常亮（发烫+画面偏红的教训）
